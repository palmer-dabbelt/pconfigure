\section{Introduction}

\pconfigure\ is designed to be a replacement for GNU \texttt{autoconf}
and GNU \texttt{automake}.  \pconfigure\ reads a configuration file
(called a \texttt{Configfile}, like a \texttt{Makefile}) and generates
a \texttt{Makefile} that's suitable for processing by GNU
\texttt{make} -- in other words, \pconfigure\ fits into the same place
in the toolchain that the combination of \texttt{autoconf},
\texttt{automake}, and a run of \texttt{./configure} does.

Despite this, \pconfigure\ follows a significantly different design
philosophy than the GNU tools do: \pconfigure\ is designed to limit
the flexibility of the build system, while the GNU tools provide full
shell access at any point during the build configuration.
\pconfigure\ limits the flexibility of the build system in the hope
that \pconfigure\ configuration files from all projects will look
somewhat similar and will therefor be easier to understand for users
-- contrast this to the GNU tools, where each project's build
configuration files look very different and are therefor difficult to
understand.  The general idea is that \pconfigure\ is a build system,
while the GNU tools are a framework for creating your own,
project-specific build system.

\subsection{Building a project that uses \pconfigure}

If you're just trying to build a project that uses \pconfigure, you
should be able to run
\begin{verbatim}
$ cd PROJECT_SOURCE_DIRECTORY/
$ pconfigure
\end{verbatim}
and then proceed as if you would when runn the rest of the GNU
toolchain.  Specifically, running
\begin{verbatim}
$ make
$ make install
\end{verbatim}
will build the code and install it to the default installation
directory.  Additionally, you can run
\begin{verbatim}
$ make check
$ ptest
\end{verbatim}
to run the project's test cases and print the results of running those
test.  If you get errors while running \pconfigure, Section~\ref{err}
lists some commen errors and may be useful to help with
troubleshooting.  Additionally, Section~\ref{cl} contains a list of
command-line options that may be useful to you.  A full list of the
generated \texttt{make} targets is shown in Section~\ref{make}.

Some projects vendor \pconfigure\ and commit the \texttt{Makefile}
that builds it, in which case there is nothing to run first: type
\texttt{make} and the build gets itself a \pconfigure\ before it
configures.  Section~\ref{cmd:bootstrap} says how a project asks for
that.

Note that for a properly written \pconfigure\ project it will not be
necessary to run \texttt{make install} before running \texttt{make
  check}.  Some buggy projects will silently run old code in this
case, so be sure to consult your project's documentation before
attempting that.

A \texttt{CDPATH} in your environment is ignored.  \pconfigure\
removes it before running anything while it configures --- an
executable \texttt{Configfile}, a \texttt{GENERATE} script, a
backtick --- and every \texttt{Makefile} it writes says
\texttt{unexport CDPATH}, so no recipe sees it either.  Those all
\texttt{cd} into relative paths, and under a \texttt{CDPATH} such a
\texttt{cd} can end up in some other directory of the same name and
prints where it went into output that is being read.

\subsection{Using \pconfigure\ in your project}

In order to use \pconfigure\ in your project you'll need a bit more
knowledge about how \pconfigure\ works.  The primary means by which
you'll be interacting with \pconfigure\ is by modifying it's
configuration file.  By default, \pconfigure\ will read
\texttt{Configfile} in the current working directory, parse every line
(until there is an aborting error), and then return.
\pconfigure\ configuration files are also refered to as
\texttt{Configfile}s, much the same way as \texttt{make} configuration
files are referred to as \texttt{Makefiles}s.

A \texttt{Configfile} file is line-oriented, and a \texttt{\#}
character at the beginning of a line signifies a comment, and blank
lines are ignored.  All other lines are of the format
\begin{verbatim}
COMMAND OPERATION VALUE
\end{verbatim}
where \texttt{COMMAND} is one of the options listed in
Section~\ref{cmd}; \texttt{OPERATION} is either \texttt{=}, which
sets something, or \texttt{+=}, which adds to it; and \texttt{VALUE}
is a free-form text value.  Each command takes exactly one of the two,
as its section's heading shows, and there is no \texttt{-=}: nothing
can take back what an earlier line added, so the way to drop something
is to delete the line that added it.  A line written with the wrong
operator is a fatal error that names the line and gives it back with
the right one.  If \texttt{value} starts and ends with a \texttt{`} character
then it is executed as a shell out (the syntax here is just like BASH
and Ruby).

What a shell out prints takes its place in the line, and the line is
then read exactly as though that had been typed there, gaps and all.
A shell out that prints nothing is the usual answer from some of them
(\texttt{pkg-config --cflags} says nothing about a library the compiler
already finds), so a line whose whole value came from shell outs that
printed nothing is not treated as a line with its value left off.
\texttt{COMPILEOPTS}, \texttt{LINKOPTS}, \texttt{CONFIGUREOPTS} and
\texttt{MAKEOPS} add nothing, and \texttt{CROSS\_COMPILE} is set to
nothing.  Every other command names something -- a target, a file, a
directory, a language -- and is an error naming the line, since an empty
name is not a name: an empty \texttt{LIBDIR} would put every library at
the root of the filesystem.  The command and its operator are checked
first either way, so a misspelled command is still reported as one.

A shell out that fails --- exits with anything other than 0, is killed
by a signal, or names a command that isn't installed --- stops
\pconfigure\ with an error naming the line and the command's exit
status.  This is how a \texttt{Configfile} finds out that a package it
needs isn't there: \texttt{ppkg-config foo --cflags} fails when
\texttt{foo} is missing, and carrying on would write a
\texttt{Makefile} that builds without \texttt{foo}'s flags.  A command
that is allowed to fail says so itself, with \texttt{ppkg-config}'s
\texttt{--optional} (see Section~\ref{prog:ppkg-config}) or by ending
it with \texttt{|| true}.  An unterminated \texttt{`} is an error
naming the line too.

A UTF-8 byte order mark at the very start of a \texttt{Configfile},
which some editors write without being asked, is ignored.  Anywhere
else in the file those bytes are an error on the line they appear on.
So is a NUL byte anywhere in a line, which usually means the file was
saved as UTF-16; both rules apply to what an executable
\texttt{Configfile} prints as well.

By default, the following configuration files are loaded in this order
\begin{verbatim}
Configfiles/local
Configfile.local
Configfiles/main
Configfile
\end{verbatim}
The general idea is that \texttt{*local} are configuration files that
should not be checked in to revision control because they're local to
a specific instance.  This is useful for setting things like
compile-time options that you want and other people don't (debug info,
for example).  The \texttt{Configfiles} directory is designed for
complicated projects that may have many configuration files, while
it's expected that simple projects will just use a singe configuration
file and call it \texttt{Configfile}.

Note that \pconfigure\ will silently skip any of these files that
don't exist so you only need to create the ones that make sense for
your project.  It's not expected that you make either
\texttt{Configfiles/local} or \texttt{Configfile.local} as these will
be specific to end-user systems.

Only a file that doesn't exist is skipped.  One that exists but can't
be read, or that is a directory, is a fatal error naming it, since
reading it as empty would write a \texttt{Makefile} missing everything
it declares.

Skipping is per file, though: if none of the four exists, \pconfigure\
refuses to run, names the files it looked for, and writes nothing.
That is almost always a run from the wrong directory (a project's
\texttt{src/} instead of its top, say), and carrying on would write a
\texttt{Makefile} for an empty project and exit successfully.  A run
that is given something else to read is not refused: a
\texttt{--config} names a file of its own, and Configfile lines given
on the command line describe a project with no file behind them.

\subsection{Writing your first \texttt{Configfile}}

The \texttt{Configfile} format is designed to be as terse as possible.
In order to achieve this there are a number of implicit rules that
\pconfigure\ uses to traverse your source tree and attempt to
determine exactly how you want your code built.  These rules depend on
exactly which language is currently being used, a list of which can be
found in Section~\ref{lang}.

\pconfigure\ was originally designed to link C code.  Most of the
other backends are at least partially based on the C backend which
makes C a good example for how to use \pconfigure, which is why this
example is written using C.  The same general structure applies to
\texttt{Configfile}s for all languages, but each language will handle
commands slightly differently so it's important to read
Section~\ref{lang} which will tell you exactly what your language is
expected to do.

A simple example \texttt{Configfile} for C is shown here
\begin{verbatim}
LANGUAGES   += c
COMPILEOPTS += -Wall

BINARIES    += hello
SOURCES     += hello.c
\end{verbatim}
I'll try to explain each line below.

\section{Command-Line Options \label{cl}}

Almost every option here is a \texttt{Configfile} command that has
been given a spelling for the command line, and does exactly what
writing that command at the top of the first file read would do ---
which is what lets one tree be configured two ways without editing
anything in it.  \texttt{pconfigure --help} prints the same list in
short form.

An option that takes a value and is given none is a fatal error that
says which option wanted one.

Any other word is a \texttt{Configfile} line, written as one quoted
word: \texttt{pconfigure 'LANGUAGES += c'}.  It is read the way the
same line in a file would be, as though it were at the top of the
first file read: runs of white space are just the space between two
words, white space at either end is dropped, a line that is empty or a
comment does nothing, and anything in backticks is run while
configuring, with a command that fails stopping the run.  The
backticks are run once every option has been read, so a
\texttt{--ppkg-config} given after the line still names the
\texttt{ppkg-config} it runs.  Options are matched exactly as they
were typed, and so is the value after one: neither is tidied or
expanded.  A word that is neither an option nor a line that can be
read is a fatal error that names it and counts it from the first word
after \texttt{pconfigure}.

\subsection{\texttt{--help} \label{cl:help}}

Prints a short description of every command-line option and exits
without touching anything else --- the \texttt{Makefile} in particular
is not written.  \texttt{-h} is the same thing spelled shorter.

\subsection{\texttt{--verbose} \label{cl:verbose}}

Sets \texttt{VERBOSE} for the whole project before any
\texttt{Configfile} is read, see Section~\ref{cmd:verbose}.  The
generated \texttt{Makefile} then echoes each command as it runs it,
rather than the short label that stands in for it.

\subsection{\texttt{--debug} \label{cl:debug}}

Sets \texttt{DEBUG} for the whole project before any
\texttt{Configfile} is read, see Section~\ref{cmd:debug}.  This is
about \pconfigure\ rather than about the build: it prints what
\pconfigure\ is doing while it writes the \texttt{Makefile}, and the
\texttt{Makefile} it writes is the same one either way.

\subsection{\texttt{--phc <path>} \label{cl:phc}}

Sets \texttt{PHC} for the whole project before any \texttt{Configfile}
is read, see Section~\ref{cmd:phc}.
\texttt{<path>} can't be empty: there is no header compiler with no
name, and a \texttt{Configfile} can't write \texttt{PHC =} with
nothing after it either.  Leave the option off to keep the default.

\subsection{\texttt{--ppkg-config <path>} \label{cl:ppkg_config}}

Uses \texttt{<path>} as \texttt{ppkg-config} (see
Section~\ref{prog:ppkg-config}) when a \texttt{Configfile} runs it in
backticks.  The word \texttt{ppkg-config} is replaced wherever it
appears as a word of its own inside a backticked command, so
\texttt{`ppkg-config --cflags x`} runs \texttt{<path>} instead, and
so does \texttt{`true | ppkg-config --cflags x`}: a word starts and
ends at a blank, at either end of the command, or at one of the shell
operators \texttt{|}, \texttt{;}, \texttt{\&}, \texttt{<},
\texttt{>}, \texttt{(} and \texttt{)}, which covers \texttt{\$(}
too.  Text that only contains it is left as written: a ppkg-config
named by its path, such as \texttt{/opt/bin/ppkg-config}, runs that
path, a script called \texttt{tools/ppkg-config-shim} runs that
script, and \texttt{myppkg-config} or a quoted
\texttt{'ppkg-config'} is not touched.  The path goes in quoted, as a
single word, so a \texttt{<path>} with a space in it -- or a
\pconfigure\ installed under such a directory, for the default below
-- still names one program.

Without this option the \texttt{ppkg-config} sitting beside the
running \pconfigure\ is the one that runs, named by its absolute path
the same way \pconfigure's other helper tools are (see
Section~\ref{prog:ppkg-config}).  A tree that vendors \pconfigure\ and
builds it into \texttt{src/pconfigure/bin} therefore needs nothing
installed: the copy that matches the \pconfigure\ doing the
configuring is the copy that answers.  \texttt{\$PATH} is still asked
when there is no such sibling, which is the case a layout that keeps
\pconfigure\ apart from its tools leaves.

There is no \texttt{Configfile} command for this one, and it is
deliberately not one: which \texttt{ppkg-config} answers a question is
a property of the \pconfigure\ that is running rather than of the
project being configured, so it is the person running the build who
gets to say.

\subsection{\texttt{--config <filename>}}

Loads a configuration file, see Section~\ref{cmd:config} for more information.
Calling \texttt{--config <filename>} is exactly the same as inserting a
\texttt{CONFIG += <filename>} before any file-based configurations are
specified..  Specifically, the configurations will be loaded in the following
order:

\begin{verbatim}
Files listed by --config
Configfiles/local
Configfile.local
Configfiles/main
Configfile
\end{verbatim}

\subsection{\texttt{--cross-compile <prefix>} \label{cl:cross_compile}}

Sets \texttt{CROSS\_COMPILE} for the whole project before any
\texttt{Configfile} is read, see Section~\ref{cmd:cross_compile}.
Calling \texttt{--cross-compile <prefix>} is exactly the same as
putting \texttt{CROSS\_COMPILE = <prefix>} at the top of the first
file that gets read, which is what lets one tree be configured for
one machine and then for another without editing anything in it.

\subsection{\texttt{--strict <version>} \label{cl:strict}}

Sets \texttt{STRICT} for the whole project before any
\texttt{Configfile} is read, see Section~\ref{cmd:strict}.  Calling
\texttt{--strict <version>} is exactly the same as putting
\texttt{STRICT = <version>} at the top of the first file that gets
read, which is how a tree gets held to a version without being edited
-- and how a project that is thinking about writing the line down
finds out what it would have to fix first.

\subsection{\texttt{--version}}

Prints the version number of \pconfigure\ and exits without touching
anything else.  Specifically, this doesn't touch the \texttt{Makefile}
at all.

\subsection{\texttt{--srcpath <dirname>} \label{cl:srcpath}}

Allows for the seperation of the source and build directories.  By
default, \pconfigure\ will place output file in the same directory as
the rest of your project, this allows them to be seperated.  Running
\begin{verbatim}
$ pconfigure --srcpath $DIRNAME
\end{verbatim}
duplicates the functionality of running
\begin{verbatim}
$ $DIRNAME/configure
\end{verbatim}
in the land of GNU tools.

\texttt{\$DIRNAME} has to be a directory.  A Configfile that isn't
there is read as an empty one, so a path that doesn't exist would
otherwise configure an empty project and exit successfully; instead
\pconfigure\ refuses it, naming the path and saying whether it is
missing or isn't a directory.  It can't have whitespace in it either:
the source tree's path goes on the front of every target the
\texttt{Makefile} names, and \texttt{make} would split each of them
in two, so a directory with a space in its name is refused rather than
configured into a \texttt{Makefile} that can't build anything.
Rename it, or name a symlink to it that has no space in its name.  The
same goes for a \texttt{SRCPATH} written in a Configfile.

Nor may it start with a \texttt{-}, for the reason a \texttt{SRCDIR}
may not: every source path starts with it, and a compiler reads
\texttt{-sp/src/main.c} as an option rather than a file.  A directory
that really is called \texttt{-sp} is written \texttt{--srcpath ./-sp}
or \texttt{SRCPATH = ./-sp}, which keeps its \texttt{./} all the way
to the compile line.

\section{\texttt{make} Targets \label{make}}

\subsection{\texttt{make all} \label{make:all}}

Builds every target specified by \texttt{BINARIES},
\texttt{LIBRARIES}, \texttt{HEADERS}, \texttt{LIBEXECS}, and
\texttt{TESTEXECS}.

\subsection{\texttt{make install} \label{make:install}}

Installs all targets built by \texttt{make all} (see
Section~\ref{make:all}) to the specified \texttt{PREFIX} path.  Note
that this may require re-linking some targets in order to deal with
something like \texttt{-rpath}.  Exactly what is rebuilt and how
depends on the language, see Section~\ref{lang} for more information.

What lands under the prefix is given a fixed mode, the way
\texttt{install -m} would give it: 0755 for programs, scripts and
shared libraries, and 0644 for headers and static archives.  That
doesn't depend on the umask the tree was built under, so a tree built
under \texttt{umask 077} still installs files everyone can read and
run.  The copies in the build tree keep whatever mode the build gave
them.

\texttt{DESTDIR}, said on \texttt{make}'s command line, puts the whole
install under a staging directory, the way it does for any other
package.  It can't have whitespace in it.  Every installed file is a
\texttt{make} target whose name starts with \texttt{DESTDIR}, and
\texttt{make} splits target names at whitespace, so a staging
directory called \texttt{stage dir} would have installed into a
\texttt{dir} inside the source tree.  It can't have a \texttt{:},
\texttt{;} or \texttt{\%} in it either, which \texttt{make} reads as
rule syntax in those same names: the first two would have stopped
\texttt{make} with an error that never mentions \texttt{DESTDIR},
and a \texttt{\%} would have let
\texttt{make install} work and then \texttt{make uninstall} remove
nothing.  The \texttt{Makefile} stops with an error saying so instead,
whatever was being built.  A symlink to the staging directory names
the same place without the character in the way:

\begin{verbatim}
$ ln -s "$PWD/stage dir" /tmp/stage
$ make DESTDIR=/tmp/stage install
\end{verbatim}

\subsection{\texttt{make check} \label{make:check}}

Builds and runs every test specified by the \texttt{Configfile}, or
just the tests of one test suite when the project named one with
\texttt{DEFAULT\_TEST\_SUITE} (see Section~\ref{cmd:default_test_suite}).

A test whose result is current is not run again, and a set of results
that has already been scored is not scored again --- unless the set
itself changed.  Moving a test into a suite, adding an
\texttt{INCLUDE\_TEST\_SUITES}, or pulling in a subproject whose
tests already ran on their own all change which results \texttt{make
  check} is about without making any of them newer, so \pconfigure\
writes down what each set holds, in \texttt{\$OBJDIR/check-all-scope}
and \texttt{\$OBJDIR/check-suite-\$name-scope}, and the next
\texttt{make check} scores the new set.  Those files are only
rewritten when what they say changes, so a reconfigure that leaves
every set as it was leaves \texttt{make check} with nothing to do.

What it reports on is the results of those tests and no others, named
outright the way a suite's are (see Section~\ref{make:report_suite}).
\texttt{\$CHECKDIR} also holds the last result of every test that was
ever run there, including one a \texttt{Configfile} has since stopped
naming, and taking out a test that was failing would otherwise leave
\texttt{make check} failing about a test that no longer exists.

A test is run so that it shares the jobserver of the \texttt{make}
that ran it, which is what lets a test that runs a \texttt{make} of
its own fit inside the outer \texttt{-j}.  It still runs nothing under
\texttt{make -n check}, which prints the \texttt{ptest} command of
each test that is out of date and leaves its result alone, nor under
\texttt{make -t check}, which marks the old results current without
running anything.

\subsection{\texttt{make check-\$suite} \label{make:check_suite}}

Builds and runs the tests of one test suite (see
Section~\ref{cmd:test_suites}).  There is one of these per suite the
build declares, and a suite nobody joined has one too --- it runs
nothing and reports that nothing ran.

\subsection{\texttt{make report-\$suite} \label{make:report_suite}}

Reports on the tests of one test suite, the way \texttt{make report}
reports on the whole build.  What it prints is that suite's tests and
no others: every suite's results land in \texttt{\$CHECKDIR}
together, so a report that read the directory would say the same thing
whichever suite it was asked about.

\subsection{\texttt{make reconfigure} \label{make:reconfigure}}

Runs \pconfigure\ again, rewriting the \texttt{Makefile}s from
whatever the \texttt{Configfile}s say now.

Nothing else in a build does this.  What a \texttt{Makefile} says is
what the \texttt{Configfile}s said the last time somebody ran
\pconfigure, and it goes on saying it until somebody says otherwise
--- a build that reconfigured itself when it noticed a
\texttt{Configfile} had moved would be deciding, without being asked,
to throw away and rebuild whatever the new options touched.  This is
how you ask.

Options go in \texttt{PCONFIGURE\_ARGS}, so a tree that is normally
configured with an extra \texttt{Configfile} doesn't have to go around
the rule to say so:

\begin{verbatim}
$ make reconfigure PCONFIGURE_ARGS="--config debug"
\end{verbatim}

Without them it runs \pconfigure\ the way it was last run.  The
\texttt{Makefile} records the options the run that wrote it was given
as the default for \texttt{PCONFIGURE\_ARGS}, so a tree configured
with \texttt{--config debug} is reconfigured with it until somebody
says otherwise --- and saying otherwise is giving
\texttt{PCONFIGURE\_ARGS} again, empty for a \pconfigure\ with no
options at all:

\begin{verbatim}
$ make reconfigure PCONFIGURE_ARGS=
\end{verbatim}

\texttt{--debug} is the one option left out of that record (see
Section~\ref{cl:debug}): it asks this run of \pconfigure\ to explain
itself, and a reconfigure that make starts later, perhaps from the
middle of a build, has not been asked to.

The options are recorded in the \texttt{Makefile} of the project
\pconfigure\ was run in, and only there.  A path in one of them is a
path from that directory, so a subproject's own \texttt{Makefile}
keeps an empty default.

The \pconfigure\ that runs is the one that wrote the
\texttt{Makefile}, named by its absolute path the same way its helper
tools are, rather than whatever the \texttt{PATH} calls \pconfigure.
A tree that vendors \pconfigure\ and builds it into
\texttt{src/pconfigure/bin} has never installed one, so the
\texttt{PATH} may have no answer at all, and an installed copy that
does answer may well be a different version from the one this tree was
configured with.  Under \texttt{AUTORECONFIGURE} this is also the
recipe \texttt{make} uses to remake the \texttt{Makefile} when a
\texttt{Configfile} is newer, so it has to work wherever the rest of
the build does.  Reconfiguring with some other \pconfigure\ means
running that one by hand.  A project that pins its own with
\texttt{BOOTSTRAP} (Section~\ref{cmd:bootstrap}) runs the one it
builds instead.

That path, and the paths of the helper tools beside it, go into the
\texttt{Makefile} quoted as a single shell word, with any \texttt{\$}
doubled for \texttt{make}.  A \pconfigure\ installed under a directory
whose name has a space or a \texttt{\$} in it therefore builds,
checks and reconfigures like one installed anywhere else.

A project that asked for \texttt{AUTORECONFIGURE}
(Section~\ref{cmd:autoreconfigure}) still needs this.  What that moves
into the build is which headers a source reads; what a
\texttt{Configfile} says is still read when somebody asks for it to be
read.

\subsection{\texttt{make clean} \label{make:clean}}

Removes every target generated by \texttt{make all} (see
Section~\ref{make:all}) and by \texttt{make check} (see
Section~\ref{make:check}).

That includes the whole of \texttt{\$CHECKDIR}, for every project the
build pulled in, and not only the results of the tests the
\texttt{Configfile}s name today: a test that has been taken out left
its last result there, and nothing else would ever remove it short of
\texttt{make distclean}.

It also includes what a target that has since been taken out of a
\texttt{Configfile} left in \texttt{BINDIR}, \texttt{LIBDIR} or
\texttt{TESTEXECDIR}.  Those directories are not swept whole the way
\texttt{\$CHECKDIR} is; instead every configure writes down, in
\texttt{OBJDIR/output-names}, the files a project builds into them,
and a file on that list that no target builds any more and that is
still there gets removed by name.  A program or a library whose line
went away is gone after the next \texttt{make clean}, then, and a
\texttt{-l} left in a \texttt{LINKOPTS} for a library the build no
longer makes stops finding the old copy.  Only a directory the build
still writes into is cleaned this way: a file in one a \texttt{BINDIR}
or \texttt{LIBDIR} has since moved away from is still
\texttt{make distclean}'s, and so is one left by a target that was
dropped while there was no list to put it on.

\subsection{\texttt{make cache-clean} \label{make:cache_clean}}

Removes what is left in an object directory that the build no longer
knows how to make, and leaves everything else where it is.  A tree
that has been reconfigured for years accumulates objects compiled from
sources that have gone away and programs linked under names nothing
uses any more; short of \texttt{make distclean}, which throws away the
whole build, nothing else takes those.

It works by reading the \texttt{Makefile} back.  Every path under an
object directory that the \texttt{Makefile} still names as something
it can build is kept --- along with the paths named in the dependency
fragments, for a project that works its dependencies out during the
build (see Section~\ref{cmd:autoreconfigure}) --- and every other file
under there goes, followed by whatever directories that left empty.

Some of what is under an object directory has no rule behind it and
would be thrown away by exactly that reasoning, so those are spared by
name: a vendored subproject's output directory and its install prefix
(Section~\ref{buildsys:prefix}), the record of where the test results
live, the list of what the build wrote into \texttt{BINDIR} and
\texttt{LIBDIR} that \texttt{make clean} reads (see
Section~\ref{make:clean}), the \texttt{Makefile}s a \pconfigure\
run from above left in here, the bookkeeping an \texttt{AUTORECONFIGURE} build keeps for
working its dependencies out, the record each \texttt{GENERATE} keeps
of the recipe that wrote its dependency fragment (without which the
next configure would throw the fragment away and run \texttt{--deps}
again) --- though only for the \texttt{GENERATE}s configured now, so
that one deleted from the \texttt{Configfile} has its record reclaimed
along with its output --- and the scratch directory a test was
given --- which is a fixture somebody deliberately did not want copied
around, and usually one that is expensive to make twice.
\texttt{make clean} is what removes that last one, along with the
test it belongs to.

The install prefix is the one worth knowing about, and it is why the
rule about where a prefix may point (Section~\ref{buildsys:prefix}) is
enforced rather than suggested.  A prefix holds a \texttt{bin}, a
\texttt{lib} and an \texttt{include} tree that no rule in the
\texttt{Makefile} names --- only the files a
\texttt{SUBPROJECT\_TARGETS} named outright get one --- so a prefix
this target could not be told about is a toolchain deleted from
underneath a build stamp that still says the tree is installed.
Nothing later puts it back, and the first thing to fail is a compile
against a header that was there yesterday.

The object directories it walks are the ones of the project
\pconfigure\ ran in.  A subproject's \texttt{Makefile} names
everything through the variable its parent sets, so reading that file
back would find nothing it still knows how to build and decide that
the whole of that project's cache was stale; a subproject that wants
one of these gets it from a \pconfigure\ run of its own (see
Section~\ref{cmd:subprojects}).

\subsection{\texttt{make distclean} \label{make:distclean}}

Recursively removes \texttt{BINDIR}, \texttt{OBJDIR}, \texttt{LIBDIR},
\texttt{TESTEXECDIR}, and \texttt{CHECKDIR}.  This completely removes every file
\pconfigure\ could have touched.

\texttt{HDRDIR} is not on that list, because it is a source directory
as well as an output one: a \texttt{HEADERS} with nothing under it
installs a header straight out of it (see Section~\ref{cmd:headers}),
and nothing in the build could write that header again.  What the
build does put there --- the copies a \texttt{HEADERS} with a
\texttt{SOURCES} under it makes, \texttt{HEADERSRC} included --- is
removed one file at a time instead, along with any directory that
leaves empty, \texttt{HDRDIR} itself included.  So an include
directory that only ever held copies goes, and one holding a header
somebody wrote stays with that header in it.

Since every one of those directories is removed whole, \pconfigure\
refuses a source it can see in one of them.  A \texttt{SOURCES},
\texttt{TESTSRC}, \texttt{HEADERSRC} or \texttt{GENERATE} that reads
a file out of one is refused, pointing at that line.  So is a file
that one of those was found to read when \pconfigure\ scanned it ---
a header a C or C++ source includes, a file a script or a test
pastes in with \texttt{\#include} --- pointing at the line that
built what reads it, since no line names the file itself.  The usual
way to get here is \texttt{SRCDIR = .} with a \texttt{lib} of library
code or headers beside the sources: nothing in the
\texttt{Configfile} names \texttt{lib} as an output directory,
because it is the default \texttt{LIBDIR}, and the first
\texttt{distclean} would have taken those files with it.  Moving the
sources under a directory of their own, or the libraries somewhere
else with a \texttt{LIBDIR}, is the way out.  This is asked once
every \texttt{Configfile} has been read, since a later
\texttt{LIBDIR} can still move the library directory, and it is asked
of the file's directory with its symlinks resolved too, because
\texttt{rm} follows a symlink it meets partway along a path.

What is asked about is what \pconfigure\ itself reads, and that
leaves two gaps.  Under \texttt{AUTORECONFIGURE} the headers a source
reads are worked out by \texttt{pdeps} while the build runs, so a
header no line names isn't asked about at all.  And a file found by
scanning that sits in an object directory isn't either, because a
vendored tree installs its headers there under names no rule in the
Makefile builds, and those can't be told apart from one somebody
wrote; a file in an object directory that a line names is still
refused.  A file anything in the build writes is output, wherever it
lands, and is never refused.

\subsection{\texttt{make uninstall}}

Removes every target created by \texttt{make install} (see
Section~\ref{make:install}), and takes the same \texttt{DESTDIR}
with the same restriction on it.

\section{Commands \label{cmd}}

\subsection{\texttt{LANGUAGES += \$lang}}

First, this flushes the current target.

If \texttt{LANGUAGES += \$lang} has not yet been run, then \$lang is
added to the list of known language backends.

\$lang is then set as the last added language.  This is used for two
distinct reasons: to manage exclusive languages, and to set
language-global command-line options.

The reason that all languages aren't just added to the language list
all the time is because some languages interact in odd ways.  An
example iss the interaction between C and C++ where C++ can build some
C files and C can build some C++ files: it would be impossible to
determine which compiler to use.  Another example is Scala and Chisel.

The other use of \texttt{LANGUAGES} is to set the ``last language
pointer'' so you can modify that language's language-global
command-line options.  For example, you may have
\begin{verbatim}
LANGUAGES += c
COMPILEOPTS += option1
...
LANGUAGES += c
COMPILEOPTS += option2
\end{verbatim}
when you want to build a whole bunch of targets with \texttt{option1},
and then want to build another set of targets with \texttt{option2}.
Overloading the whole \texttt{LANGUAGES} target to both add to the
language list and to set a pointer to the current language allows this
sort of behavior.

\subsection{\texttt{BINARIES += \$name} \label{cmd:binaries}}

This (and its many variants described below) is the mechanism
\pconfigure\ uses for tracking targets.  When called it first flushes
any currently existing target and then sets the current target to
\texttt{\$BINDIR/\$name}.

Note that everything except for the target's name is decided when the
target is flushed.  This includes the target's linker command, which
can only be decided based on the source languages that were attached
to that target.

When a \texttt{BINARIES} target is flushed it will build a
staticly-linked executable (as opposed to a static or shared library).

\texttt{\$name} is a path as much as a \texttt{SOURCES} is: it says
where the target is built, where it is linked and where
\texttt{make install} puts it.  So it may have a directory in it --
\texttt{BINARIES += tools/run} is a program in \texttt{\$BINDIR/tools}
-- but a name that climbs out of the project with a \texttt{../}, one
that starts from the root, and one that is a \texttt{make} expansion
are all fatal errors, since each would build, install and later remove
a file somewhere nothing in this build owns.  The same holds for every
variant below and for \texttt{HEADERS}.

For \texttt{BINARIES} and the variants below that build something,
\$name is also normalized before it is used, so the spelling doesn't
change which file it is: \texttt{./main} and \texttt{main} are one
target, and two lines that name it from different sources are caught
as the same target asked for twice.  A trailing \texttt{/} is dropped,
so \texttt{main/} builds \texttt{\$BINDIR/main}.  A name that is a
directory rather than a file -- \texttt{.}, \texttt{tools/.} or
\texttt{tools/main/..} -- is a fatal error, since there is nothing there
to build.

\subsection{\texttt{LIBRARIES += \$name} \label{cmd:libraries}}

Largely the same as \texttt{BINARIES += \$name} with two major
differences: the resulting output binary is stored to
\texttt{\$LIBDIR} instead of \texttt{\$BINDIR} and a library is built
instead of a stand-alone binary.

Whether a shared library or a static archive is built is decided by
\$name alone.  A name ending in \texttt{.a} builds a static archive;
any other name builds a shared library, whether that's the
\texttt{.so} of Linux or the \texttt{.dylib} of macOS.  Either is
found by a \texttt{DEPLIBS} the same way, through the \texttt{-l} it
puts on the link line, so a program linking against a static archive
carries the archive's code from then on and never looks for it again.

An archive is put together by \texttt{\$\{AR\}} rather than by the
linker.  That's \texttt{make}'s own variable, so it's \texttt{ar}
unless the environment or \texttt{make}'s command line says otherwise
-- \texttt{make AR=llvm-ar} is how to switch to LLVM's -- and under a
\texttt{CROSS\_COMPILE} it's the \texttt{ar} that prefix names
instead, the same way the compiler is (see
Section~\ref{cmd:cross_compile}).  Each member is named after the
source it was compiled from, \texttt{one.c.o} for \texttt{one.c}, so
\texttt{ar t} and \texttt{ar x} see one member per source; two sources
with the same file name in different directories get a number on the
second.

An archive is built from the same position-independent objects a
shared library is, so it can be linked into a shared library as well
as into a program.  What it can't do is remember what it needs, so a
\texttt{DEPLIBS}, \texttt{LINKOPTS} or \texttt{FRAMEWORKS} written
under one is a fatal error, which names the line and the targets it
belongs on instead: whatever links the archive has to ask for those
libraries itself.  A \texttt{LINKER} written under one is a fatal
error too, since no linker ever runs for an archive; it belongs on
the targets that link the archive's code.

\begin{verbatim}
LIBRARIES += libsub.a
SOURCES   += sub.c

BINARIES  += app
DEPLIBS   += sub
DEPLIBS   += m
SOURCES   += main.c
\end{verbatim}

Note that \pconfigure\ will automatically determine the necessary
compiler flags to build shared objects on your platform.  For example,
Linux and C will result in \texttt{-fPIC} being appended to both the
compiler and linker flags.

\subsection{\texttt{LIBEXECS += \$name} \label{cmd:libexecs}}

Exactly the same as \texttt{BINARIES += \$name}, except that the
resulting output binary is stored to \texttt{\$LIBEXECDIR} instead of
\texttt{\$BINDIR}.

\subsection{\texttt{TESTEXECS += \$name} \label{cmd:testexecs}}

Exactly the same as \texttt{LIBEXECS += \$name}, except that the
resulting output binary is stored to \texttt{\$TESTEXECDIR} and is
never installed: it's built by \texttt{make all} (see
Section~\ref{make:all}) and removed by \texttt{make clean}, but
\texttt{make install} (see Section~\ref{make:install}) ignores it
entirely.  This is meant for binaries that exist only to be run by
\texttt{TESTS} (see Section~\ref{cmd:tests}), which have no business
being installed alongside the binaries a user actually wants.  Just
like every other target, \texttt{TESTS} attached to a
\texttt{TESTEXECS} target are passed the binary as
\texttt{\$PTEST\_BINARY}.

\subsection{\texttt{PHONY += \$name} \label{cmd:phony}}

Declares a target that is a name and nothing else: \texttt{make
\$name} works, nothing is compiled, and nothing is installed.

This exists so that a project with tests and nothing to hang them off
can still have them.  A \texttt{TESTS} belongs to the thing it
exercises (see Section~\ref{cmd:tests}), and the thing an integration
test exercises is several other projects at once rather than any one
program --- so the project that owns such a test often builds nothing
itself.  Without this the only way through was a binary that does
nothing, which builds and installs a program nobody wants:

\begin{verbatim}
SUBPROJECTS += fs
SUBPROJECTS += vm

PHONY       += integration
TESTDEPS    += fs/libexec/mkfs
TESTDEPS    += vm/bin/vm
TESTSRC     += boots-a-real-image.bash
\end{verbatim}

A \texttt{TESTDEPS} (see Section~\ref{cmd:testdeps}) written under one
of these is the only thing that says what the name stands for, since a
phony target has no sources to be made out of.  Those are what
\texttt{make \$name} builds, and they are built before its tests run
the same way they would be under any other target.

A \texttt{PHONY} is deliberately not part of \texttt{make all}: a name
that stands for a set of things to build before some tests run has no
business being built by a plain \texttt{make}, and everything it names
is built by whoever builds it anyway.

Tests written under one are handed \textit{no}
\texttt{\$PTEST\_BINARY}, because there is no binary --- the variable
is empty rather than pointing at something that isn't a program.  A
test under one of these names what it needs by path, which is what its
\texttt{TESTDEPS} already said, and anchors those paths on
\texttt{\$PTEST\_SRCDIR} (see Section~\ref{cmd:tests}): the project
it belongs to, absolute, which is what
\texttt{\$(dirname "\$PTEST\_BINARY")} is for a test that has a
binary and cannot be for a test that hasn't.

The name is rooted at the project that asked for it, like every other
target, so two projects in one build can each have one called
\texttt{integration} without arguing about whose rules win.  A
\texttt{PHONY} has nothing to compile, so a \texttt{SOURCES} under one
is a mistake and gets the warning in Section~\ref{warn:sources-orphan}.

The name can't be one of the goals pconfigure writes into every
Makefile itself: \texttt{all}, \texttt{clean}, \texttt{distclean},
\texttt{cache-clean}, \texttt{install}, \texttt{uninstall},
\texttt{check}, \texttt{report} or \texttt{reconfigure}, nor
\texttt{check-\$suite} or \texttt{report-\$suite} for a suite the
build declares (see Section~\ref{cmd:test_suites}).  make would read
the two rules as one, so \texttt{make clean} would build whatever the
\texttt{PHONY} stands for before cleaning anything, and asking for the
\texttt{PHONY} would also clean.  Each of these is refused, pointing
at the \texttt{PHONY}'s line --- a subproject's too, since its
Makefile is also run from inside it, where the name is not under the
subproject's directory.  A \texttt{./} in front makes no difference:
make drops it from every target it reads, so \texttt{./clean} is
\texttt{clean} to make and is refused the same way.

\subsection{\texttt{SOURCES += \$name} \label{cmd:sources}}

Adds a \texttt{\$SRCDIR/\$name} to the list of sources that will be
linked into the current target.  In addition to that source, a number
of other sources will be implicitly discovered and linked into the
current target.  See Section~\ref{lang} for a discussion of exactly
how these dependencies are determined for each language.

Note that you can link a single source file into a target multiple
times if it's been compiled with different command-line options.  For
example, the following snippit
\begin{verbatim}
BINARIES    += target
SOURCES     += main.c
COMPILEOPTS += -DTEST
SOURCES     += main.c
\end{verbatim}
will build \texttt{test.c} two times: once with \texttt{-DTEST} and
once without it.  Both of these will be linked into the final
executable.  Be sure to take this into account when structuring your
\texttt{\#define}s.

A source is named by the path it reaches rather than by how the line
spelled it, so \texttt{main.c}, \texttt{./main.c} and
\texttt{util/../main.c} are all the same source: written under the
same options they are compiled once and linked once, just as
\texttt{main.c} written twice is.  The \texttt{..} is taken off as
text, so \texttt{gone/../main.c} names \texttt{main.c} whether or not
there is a directory called \texttt{gone}.

Calling \texttt{SOURCES} without a target is a fatal error.

Neither may the file's name hold a quote, a space or a shell
metacharacter; see Section~\ref{odd:quoting}.  A quote, a shell
metacharacter or one of \texttt{make}'s own (\texttt{\#}, \texttt{:},
\texttt{=} and the rest) is refused when \pconfigure\ reads the line
(see Section~\ref{cmd:make-special}).

\subsection{\texttt{TESTS += \$name} \label{cmd:tests}}

\texttt{TESTS} is the same as \texttt{BINARIES} (see
Section~\ref{cmd:binaries}), but the resulting binary is built at
\texttt{make all} and is not installed by \texttt{make install}.
Instead, it is run at \texttt{make check} and the results are
collected into \texttt{\$CHECKDIR}.  These results can then be listed
by running \texttt{ptest} (see Section~\ref{prog:ptest}).

A test is run with nothing on its standard input, so one that reads it
sees end-of-file at once rather than waiting on the terminal of
whoever typed \texttt{make check} or taking the input of the script
that ran it.

A test that finds it cannot run at all --- a cross compiler that is
not installed, a hypervisor the host does not have --- says so instead
of passing or failing.  It prints a line of its own beginning
\texttt{SKIP:}, with the reason after it, and exits zero.  Either
output stream will do, since both are captured into the same place.
\texttt{ptest} then counts that result as a skip rather than as a pass
(see Section~\ref{prog:ptest}), which is what tells a suite that
stopped running half of itself apart from one that passed.

Exiting zero in silence instead is what makes those two the same
number, and the number that goes wrong that way is the one nobody
looks at: a passing suite is not read, so a toolchain that went
missing takes tests out of service and the report goes on saying they
all passed.  A nonzero exit is not the alternative.  Nothing is wrong
with the tree when a test skips, and whether a particular skip is
acceptable is a question about a particular machine that
\pconfigure\ has not been told the answer to --- so the run does not
fail, and the count is left where whoever asked for it can see it.

Written as \texttt{TESTS[\$suite]} the test joins a test suite (see
Section~\ref{cmd:test_suites}) rather than only being part of every
test the project has.  The name in the brackets belongs to the command
rather than to the value: what comes after the operator is a filename
either way.  It is written after the command and against it, with no
space before the \texttt{[} and nothing after the \texttt{]} but the
space before the operator.  A line that gets any of that wrong is
refused saying which, and when the name's place or the spacing round
it and the operator was its only mistake it is given back written the
way it should have been.

A test runs with its working directory set to the directory
\texttt{make} was run in, which is not necessarily the directory the
test's own project sits in.  Running \texttt{make} at the top of a
build runs every subproject's tests from the top; running it inside a
subproject runs that subproject's tests from there.  Nothing handed to
the test says which of those happened, so a test that names a file by
a relative path is asking a question with two answers.

What a test is given instead is \texttt{\$PTEST\_BINARY}, the absolute
path of the binary the test was attached to.
\texttt{\$(dirname "\$PTEST\_BINARY")} is therefore the absolute path
of the directory that binary was built into -- \texttt{\$BINDIR}, or
\texttt{\$TESTEXECDIR} for a \texttt{TESTEXECS} target (see
Section~\ref{cmd:testexecs}) -- and everything else in the project sits
a fixed distance from there.  That is the supported way for a test to
find its own project, and it reads the same whether the build came
from the top or from the subproject.

A test is also given \texttt{\$PTEST\_SRCDIR}, the absolute path of
the directory the project that owns the test is rooted at -- whatever
its \texttt{SRCPATH} says, which is the project's own directory unless
it said otherwise.  That is the same anchor said a different way, and
it is the only one a test written under a \texttt{PHONY} (see
Section~\ref{cmd:phony}) has: there is no binary under one of those, so
\texttt{\$(dirname "\$PTEST\_BINARY")} would be \texttt{dirname ""},
which is \texttt{.} -- the working directory the paragraph above says
not to trust, arrived at without anything having gone visibly wrong.

A test is also given \texttt{\$PTEST\_TMPDIR}, an empty directory of
its own that is removed once the test finishes.  Anything the test
writes belongs there: the working directory is shared with every other
test in the build, and with the build itself.  It is removed even if
the test left parts of it read-only, as a Go module cache or a git
object store will, and whether it could be removed has no bearing on
the test's result.

What the test left in there is what gets collected: \texttt{\$CHECKDIR}
holds one tarball per test, and a test's own is the contents of its
\texttt{\$PTEST\_TMPDIR} once it has finished.  A test is given
\texttt{\$PTEST\_CHECKDIR}, the absolute path of the directory its own
result is about to land in --- which is where every other test of the
same target lands too, so it is how a test that was ordered after
another one with a \texttt{DEPTESTS} (see Section~\ref{cmd:deptests})
reads what that one left behind.  Nothing is there yet for a test with
no \texttt{DEPTESTS}: what makes a predecessor's result exist by the
time a test runs is having waited for it.

A test is also given \texttt{\$PTEST\_SCRATCH\_DIR}, a directory of
its own that is \textit{not} collected.  It is the place for what a
test makes that is too big to copy around --- a disk image, a
populated tree, a rootfs --- and it is the exact opposite of
\texttt{\$PTEST\_TMPDIR} in all three of the ways that matter.  It is
not emptied before a run, it is not removed after one, and nothing in
it is tarred into the result.

Each of those is there for a reason worth saying outright.  Collecting
a multi-gigabyte fixture costs as much as the test that made it did,
and what it buys is a second copy of something already sitting on
disk.  The system temp is usually a different volume from the tree as
well, so a fixture that was cheap to make with a copy-on-write clone
stops being cheap the moment it is handed through there --- which is
why this directory is inside the project, under \texttt{\$OBJDIR},
beside the test's own compiled self.  It is not in the check directory
because a bare \texttt{ptest} walks that one with \texttt{find} and
reads every file it lands on as a result tarball (see
Section~\ref{prog:ptest}), so an image left in there would be handed
to \texttt{tar} as though it were somebody's verdict.

What that costs is that a test does not start with an empty one.  A
fixture too expensive to collect is usually too expensive to build
twice, so surviving into the next run is the point rather than an
oversight --- and a test that wants it clean is the test that knows
that, and clears it itself.  \texttt{make clean} removes it along with
the test it belongs to; \texttt{make cache-clean} deliberately leaves
it alone, since reclaiming a stale object cache should not throw away
the one thing in the tree that was expensive to make.

Because the scratch directory is the test's own name with
\texttt{.scratch} on the end, a second test of the same target can't be
named that, or named anything inside it: \texttt{TESTS += t} and
\texttt{TESTS += t.scratch} would be compiled to the same path, one as
a program and one as a directory.  \texttt{pconfigure} refuses the
later of the two lines and names the other.  A test whose name merely
ends in \texttt{.scratch}, with nothing beside it that the name belongs
to, is fine.

\subsection{\texttt{HEADERS += \$name} \label{cmd:headers}}

The \texttt{HEADERS} command creates a target that's meant for
installing, but it's quite different than the \texttt{BINARIES}-based
targets.  The idea behind \texttt{HEADERS} is to allow libraries to
install headers into the system.  There are two ways headers can be
installed: from \texttt{\$HDRDIR} and from \texttt{\$SRCDIR}.

Standard practice for C is to build a special set of headers that are
installed into the system that contain the public API for a library.
\pconfigure\ facilitates this by allowing these custom headers to
simply be built and installed.  The following command
\begin{verbatim}
HEADERS += libname.h
\end{verbatim}
will copy \texttt{\$HDRDIR/libname.h} into \texttt{\$PREFIX/\$HDRDIR}
when \texttt{make install} is run, and will do nothing else at any
other time.

\texttt{\$HDRDIR} here is the one in the source tree: with
\texttt{--srcpath} (see Section~\ref{cl:srcpath}) or a
\texttt{SRCPATH} the header is read out of the checkout, which is
where a compile that includes it finds it too, rather than out of the
build directory.

As with \texttt{BINARIES} (see Section~\ref{cmd:binaries}), the name
may have a directory in it but may not climb out of the project, start
from the root or be a \texttt{make} expansion.

C++ ABI compatibility necessitates that exactly the same headers are
used when the library is built as when it is linked against, which
makes writing a custom set of headers pointless.
\pconfigure\ facilitates this by allowing headers to be copied from
other locations at install time.  The following snippit
\begin{verbatim}
HEADERS += libname/class.h
SOURCES += class.h
\end{verbatim}
will copy \texttt{\$SRCDIR/class.h} to
\texttt{\$PREFIX/\$HDRDIR/libname} when \texttt{make install} is run.
Note that in order for this to work you'll have to include the dummy
``h'' language, which includes a ``header compiler'' that really just
copies the header --- \texttt{phc}, whose path
Section~\ref{cmd:phc} says how to change.

When the header is installed under the name it already has, which is
the usual case, \texttt{HEADERSRC} (see Section~\ref{cmd:headersrc})
says both of those lines at once.

\subsection{\texttt{COMPILEOPTS += \$opt} \label{cmd:compileopts}}

\texttt{COMPILEOPTS} is used to change the compile-time options.  This
maps to the \texttt{CFLAGS} variable in the GNU toolchain.
\texttt{COMPILEOPTS} has different behavior depending on exactly which
state \pconfigure\ is in:

When \pconfigure\ has a current source, then the list of compile-time
options for just that source is appended with \texttt{\$opt}.
That does not include the sources found behind its headers (see
Section~\ref{cmd:autodeps}): those are built with the target's
options, because they are the same sources whichever of the target's
files happened to read the header, and building one of them a second
way for every source with options of its own would put two copies of
it on the link line.  A source the \texttt{Configfile} also names
outright is the exception, and is built the way its own
\texttt{SOURCES} line says, options and all, however it is reached.

When \pconfigure\ has no current source but a current target, then the
list of compile-time options for all sources linked into that target
(both explicitly and implicitly) is append with \texttt{\$opt}.

When \pconfigure\ has no current source or target, then the list of
compile-time options for all sources built with the current languages
is appended with \texttt{\$opt}.

When \pconfigure\ has no current source, target, or language then a
fatal error is thrown.

An \texttt{\$opt} is a piece of a command line, and it is read as the
words the shell will split it into, so one line can carry several
flags.  The shell's quotes and backslashes come off those words before
\pconfigure\ reads one as a directory, a file or a macro name, just as
they do before the compiler sees it, whether the quote opens after
the flag or before it: \texttt{-I'src/lib'} and \texttt{'-Isrc/lib'}
are both the directory \texttt{src/lib}, and \texttt{-DMSG='"hi"'}
defines \texttt{MSG}.  A function-like \texttt{'-DLOG(x)=(x)'} or
\texttt{'-DLOG(x)'} defines \texttt{LOG}, the name being what comes
before the parameter list.  An include directory a subproject names is written from that
subproject's own directory: the relative directory of a \texttt{-I},
\texttt{-isystem}, \texttt{-iquote}, \texttt{-idirafter} or clang's
\texttt{-isystem-after}, with the directory stuck on or as the next
word, gets the subproject's
directory put on the front.  Those same directories are where
\pconfigure\ looks for the headers a source reads, so editing a header
found in any of them rebuilds what was compiled against it.  They are
searched in the order the compiler searches them, which goes by the
kind of flag rather than by the order the lines were written in: a
quoted \texttt{\#include} looks in the includer's directory and then
every \texttt{-iquote}, and an angled one in neither; then both look
along every \texttt{-I}, every \texttt{-isystem}, every
\texttt{-isystem-after} and last every \texttt{-idirafter}.  An
\texttt{\#include} that names its header by an absolute path, in either
spelling, is looked for at that path and nowhere else, as the compiler
does: a header in the project reached that way is the header it would
be by any other name, whether the path goes through a symlink to the
project or not, and one outside it, a system header included by its
full path among them, is still a header editing which rebuilds the
source.  One that names nothing is passed over, and the compiler says
so.

A file named by \texttt{-include} or \texttt{-imacros}, which the
compiler reads ahead of every source, is a header of every source
too: editing it, or a header it includes, rebuilds what was compiled
with it, and what it \texttt{\#define}s is seen by the
\texttt{\#ifdef}s \pconfigure\ follows in the source.  It is looked
for where the compiler looks, in the top of the tree and then along
the include path the way a quoted \texttt{\#include} is.  A subproject's relative one that names a file in
the subproject's own directory gets that directory put on the front;
one that doesn't is left to be found along the include path by the
name it was written with.

A header is named by the path it reaches rather than by how the
include and the directory it was found through spelled it, just as a
source is: \texttt{"extra.h"} and \texttt{"./extra.h"}, or a header
found through \texttt{-Isrc/lib}, \texttt{-Isrc/lib/} or
\texttt{-I./src/lib}, are the one header, and the source behind it is
built and linked once.  A \texttt{..} that climbs out of the project
is kept, so a header reached with \texttt{"../../shared/shared.h"}
is still found where it is, and a change to it still rebuilds what
includes it.

\subsection{\texttt{LINKOPTS += \$opt}}

\texttt{LINKOPTS} is just like \texttt{COMPILEOPTS}, but it sets
linker options instead of compiler options (essentially it's
\texttt{LDFLAGS} in the GNU toolchain).  See
Section~\ref{cmd:compileopts} for a description of
\texttt{COMPILEOPTS}.

Note that some languages (Chisel, for example) have slightly different
semantics as to what's considered a compile-time option and what is
considered a link-time option.  Check Section~\ref{lang} for exactly
how your language interprets these argumuents.

For most languages (those that use standard compile and link
semantics), setting \texttt{LINKOPTS} for a source won't do anything,
you should instead set it on the target that source will be linked
into.  Setting it on a static archive is a fatal error, for the same
reason: an archive isn't linked either (see
Section~\ref{cmd:libraries}).  A \texttt{LINKOPTS} written above every
target is still fine in a project that builds one, since it's meant
for everything else that gets linked.

A file \texttt{LINKOPTS} has the linker read is an input to the link
like any object: a prebuilt archive or object named outright, a linker
script after \texttt{-T}, or the file after \texttt{--version-script},
\texttt{--script}, \texttt{--dynamic-list},
\texttt{--retain-symbols-file}, \texttt{--just-symbols} or
\texttt{--export-dynamic-symbol-list}, whether passed through
\texttt{-Wl,} or \texttt{-Xlinker}.  Editing one relinks what was
linked with it.  Only a file that is there when \pconfigure\ runs is
watched this way, and only these flags: a file the link writes, like
the one \texttt{-Map} names, is no input, and taking it for one would
relink on every build.  A file this build makes itself is waited for
only when its path is a word of its own on the link line: named
outright, like \texttt{LINKOPTS += gen/libv.a}, or after a separate
\texttt{-T} or \texttt{-Xlinker}.  One stuck onto a flag, like
\texttt{-Wl,--version-script=gen/x.map} or \texttt{-Tgen/x.ld}, isn't
waited for, so on a clean build the link can run before that file has
been made.

\subsection{\texttt{ENTITLEMENTS = \$plist} \label{cmd:entitlements}}

Names the entitlements a binary should carry, as a path to a property
list relative to the project that asks for it.

Entitlements are a macOS idea: they're how a program says it wants
something the kernel doesn't hand out by default -- access to the
hypervisor, for instance -- and the only place they can live is inside
the program's code signature.  \pconfigure\ signs every Mach-O it
links, so it's the one that has to put them there; a signature applied
without them doesn't leave whatever was there before alone, it drops
it.

\begin{verbatim}
LANGUAGES    += c

BINARIES     += vmm
ENTITLEMENTS  = vmm.plist
SOURCES      += vmm.c
\end{verbatim}

The plist is a prerequisite of the link, so changing what a program is
allowed to do re-links and re-signs it.  Nothing else in the project
is affected: a target that doesn't ask for entitlements doesn't get
any, and the entitlements one target names aren't inherited by the
next one.

Note that macOS only reads entitlements off an executable.  Setting
this on a \texttt{LIBRARIES} target is accepted, and the library is
still signed, but the entitlements go nowhere.

A link that produces something other than a Mach-O -- anything built
under a \texttt{CROSS\_COMPILE} (see
Section~\ref{cmd:cross_compile}), or with a \texttt{LINKER} pointed
somewhere else -- is left unsigned, because there is nothing there for
a signature to mean.  \texttt{codesign} does not refuse such a file:
it signs it ``generic'', which hangs an ad-hoc signature off it in
extended attributes that the machine the thing is going to run on
knows nothing about, and accepts \texttt{--entitlements} while
ignoring it.

On every other platform this is parsed and ignored, so a
\texttt{Configfile} that needs it on macOS doesn't have to know which
machine is reading it.

\subsection{\texttt{SUBPROJECTS += \$dirname} \label{cmd:subprojects}}

Pulls in another project that lives in a subdirectory -- a git
submodule, usually.  \texttt{\$dirname} is relative to the
\texttt{Configfile} that names it, and the project it points at needs
no idea that it is being used this way.

The directory may not have a quote, a space or a shell
metacharacter in its name; see Section~\ref{odd:quoting} for
what happens if it does and why it is not caught earlier.

Nor may two subprojects in one run have directories whose names differ
only in their punctuation, such as \texttt{lib-a} and \texttt{lib\_a},
or \texttt{a-b} and \texttt{a/b}.  Each project's \texttt{Makefile}
finds its own directory through a make variable spelled from the
directory's name with every run of punctuation turned into one
underscore, so those pairs would share one.  \pconfigure\ refuses
the pair, naming both \texttt{SUBPROJECTS} lines; rename one of the
directories.

Nor may the directory start with a \texttt{-}.  Every path in the
subproject's build starts with its directory, and the compilers,
\texttt{mkdir} and \texttt{rm} in its recipes read a word starting
with a \texttt{-} as an option rather than a file, so a tree checked
out as \texttt{-dep} is refused rather than left to fail inside
\texttt{make}.  Writing it \texttt{./-dep} does not get around this,
since the directory is normalized before anything is built from it;
check the tree out under another name.
A vendored tree is the exception: its directory reaches its recipes
only as the argument of a \texttt{\$(MAKE) -C}, which takes the word
after it whatever it looks like, so a vendored tree checked out as
\texttt{-k} builds.

It may not be the project itself or any directory that contains it,
it may not climb out of the project, and it may not be inside an object
directory.  A \texttt{SUBPROJECTS += ..} in a subproject names the
project that pulled it in, which would make the two each other's
subproject, so it is refused whether \pconfigure\ runs at the top or
inside the subproject.  The rule about object directories is the
other end of the sentence that lets a vendored tree install into
an object directory (Section~\ref{buildsys:prefix}): \pconfigure\
owns every byte under one, and \texttt{make distclean} is an
\texttt{rm -rf} of it rather than anything finer --- so a tree
checked out in there is one \texttt{distclean} away from being gone,
and whatever had not been pushed goes with it.  The object directory
asked about is the one in force where the line was written, which
inside a subproject is that subproject's own.

Those last two are asked of the directory as well as of the name,
because a symlink is where the two stop agreeing: \texttt{rm -rf
sub/obj} follows a symlinked \texttt{sub}, since \texttt{rm} declines
to walk through a symlink only when it is the last thing on the path.
A link that stays inside the project is left alone --- linking a
vendored tree into place from elsewhere in the same checkout is a real
thing to do --- and a path that does not resolve at all is left to
whoever reads the \texttt{Configfile} that is not there.  The rule
against the project itself or a directory containing it is asked of
the directory too, for links that stay inside the project: a
\texttt{self} linking to \texttt{.}, or an \texttt{up} in a
subproject linking to \texttt{..}, is refused at the line just as
\texttt{.} or \texttt{..} would be, rather than reading the same tree
again and again under a longer name each time.

Nor may a subproject be inside any other directory \texttt{make
distclean} removes whole: where the binaries, the libraries and the
test results go, for every project whose \texttt{distclean} would
reach it.  That is asked once every \texttt{Configfile} has been read rather than at
the line, because a \texttt{LIBDIR} further down can still move the
library directory onto the tree, and the error points at the
\texttt{SUBPROJECTS} line either way.  A project that builds nothing
of its own has no library directory for \texttt{distclean} to
remove, so \texttt{SUBPROJECTS += lib/dep} is fine there and refused
in a project with a target; a \texttt{LIBDIR} somewhere else, or the
tree checked out somewhere else, is the way out.  \texttt{BOOTSTRAP}
is held to the same rule, since its tree is read as a subproject.
This rule resolves symlinks too, in the tree and in the output
directory both, for the reason given above: a \texttt{dep} that is a
symlink to \texttt{lib/dep} is refused just as \texttt{lib/dep}
would be, because \texttt{rm -rf lib} takes the checkout either way.

An absolute path is refused, since it names the same directory
however the project is read and so is never relative to the
\texttt{Configfile} that wrote it.  Climbing out, on the other hand,
is judged against the project \pconfigure\ was run in rather than
the one whose \texttt{Configfile} has the line.  That is what lets a
wrapper project name the tree it wraps when the tree is checked out
beside it: a \texttt{SUBPROJECTS += ../tree} in \texttt{wrap} names
the top's \texttt{tree} when \pconfigure\ runs at the top, and is
accepted there.  Run inside \texttt{wrap} the same line names a
directory beside the checkout and is refused, so a project laid out
that way is configured from the top.  A path that wanders and comes
back, like \texttt{x/../b}, is fine either way.

How it gets built is worked out from what is in the directory, the
same way the language that builds a source file is worked out from
what the file is called.  A directory with a \texttt{Configfile} in it
is a \texttt{pconfigure} project, and the rest of this section is
about those; a directory that looks like somebody else's build system
is handled by that build system, which is what
\texttt{BUILD\_SYSTEMS} (Section~\ref{cmd:build_systems}) is for.
Nothing has to be said about a subproject from inside the subproject.

A \texttt{pconfigure} subproject's \texttt{Configfile} is read exactly
as it would be if you had run \texttt{pconfigure} inside it.

A single run of \texttt{pconfigure} reads every project and writes a
\texttt{Makefile} for each one, and each project's \texttt{Makefile}
includes its subprojects'.  There is no recursive \texttt{make}: a
build from the top has the whole thing in one dependency graph, so
\texttt{make -j} can schedule across projects.  Subprojects nest,
and a project that gets asked for twice is only read once.  Which
project a directory is goes by the directory rather than the
spelling, so a \texttt{vendor/a} that is also named through a
symlink \texttt{a} to it is one project, read once.

A subproject's \texttt{Makefile} goes into that subproject's object
directory, under a name built out of where the subproject sits in the
run that wrote it: a \texttt{SUBPROJECTS += src/pconfigure} produces
\texttt{src/pconfigure/obj/Makefile.src.pconfigure}.  Every path in it
is written relative to a variable that the file defaults to nothing
and the parent sets before including, so it means the same thing
whether \texttt{make} was run at the top or in the subproject.

The \texttt{Makefile} at the top of the subproject is left alone,
because that one belongs to a \pconfigure\ run standing in the
subproject.  You can \texttt{cd} into a submodule, run \pconfigure\
there while you work on it, and \texttt{make}: what you get is a build
of that project and nothing else, with the same targets the build from
the top has and the subset of the dependencies that live inside it.

The two coexist.  They disagree about how to spell every path --- from
the top the subproject is a directory that other things are built
beside, and from inside it is the whole of the world --- and they
agree about which files those paths name, so the objects, libraries
and binaries they build are shared rather than duplicated.

Everything else a configure writes for a build to read is named the
same way and for the same reason: the fragments that say what a source
includes, the files that tell \texttt{pdeps} and
\texttt{psubdeps} what to ask, and the record of the command that
built a script, a test or a \texttt{.pc} file, which is how a changed
option gets one of those built again.  Two runs describing one tree
from two distances are two answers, and a file they shared would hold
whichever of them ran last --- which the other build would then read
as a set of paths measured from somewhere it is not standing, or, for
a record of a command, as that command having changed, so that
configuring one run rebuilt the other's scripts and ran its tests
again.

A tree configured by an older \pconfigure\ has a \texttt{Makefile} at
the top of each of its subprojects that the parent wrote, from back
when the parent wrote that file.  Nothing includes those any more.
\pconfigure\ says so rather than deleting them; delete them, or run
\pconfigure\ in the subproject to replace one with a \texttt{Makefile}
for building that project on its own.

That goes for a path belonging to some \textit{other} project in the
run too, not just for the project's own.  A header that one
subproject compiles against and a sibling owns is worked out as
\texttt{b/src/b.h} from the top, and a \texttt{Makefile} that says
that is a \texttt{Makefile} that only works from the top --- from
inside the subproject there is no \texttt{b} to find.  So every
project in the run gets a variable of its own, each project's
\texttt{Makefile} says where all of them are as it sees them, and
every one of those is a default: the first \texttt{Makefile}
\texttt{make} reads is the project \texttt{make} was run in, so its
answers are the ones that win.  Saying where another project is does
not pull that project's rules in; a subproject still has no idea how
to build a sibling's output, which is what keeps it buildable on its
own.

Dependencies between projects don't have to be written down.  A
\texttt{-l} on a link line that names a library some project in the
build produces becomes a \texttt{Makefile} dependency on it, and
\texttt{ppkg-config} is answered out of the build tree, so a project
can ask about a package one of its subprojects provides and be told
where that subproject's output actually is.

A subproject is built and installed as part of whoever pulled it in,
into the same \texttt{PREFIX}, and \texttt{make check} from the top
runs its tests along with everyone else's.

\subsection{\texttt{BUILD\_SYSTEMS += \$name} \label{cmd:build_systems}}

Makes a build system available to \texttt{SUBPROJECTS}, so that a
subdirectory holding a third-party tree can be pulled into this build
and still be built by whatever build system it came with.  The build
systems that come with \texttt{pconfigure} are listed in
Section~\ref{buildsys}.

In full, they are:

\begin{itemize}
\item \texttt{pconfigure} itself, for a tree that says how to build
  itself the \pconfigure\ way (Section~\ref{buildsys:pconfigure});

\item \texttt{kconfig}, for Linux's build system and everything that
  copied it (Section~\ref{buildsys:kconfig});

\item \texttt{buildroot}, for Buildroot
  (Section~\ref{buildsys:buildroot});

\item \texttt{autotools}, for a tree with a \texttt{configure} in it,
  or a \texttt{configure.ac} that one can be made out of
  (Section~\ref{buildsys:autotools});

\item \texttt{cmake}, for a tree with a \texttt{CMakeLists.txt} in it
  (Section~\ref{buildsys:cmake});

\item \texttt{cargo}, for a Rust crate --- a tree with a
  \texttt{Cargo.toml} in it (Section~\ref{buildsys:cargo});

\item \texttt{meson}, for a tree with a \texttt{meson.build} in it
  (Section~\ref{buildsys:meson}).
\end{itemize}

The last four install what they built, and where they are allowed to
install it is one question with one answer for all of them: see
Section~\ref{buildsys:prefix}.

This stands in the same relation to \texttt{SUBPROJECTS} that
\texttt{LANGUAGES} stands in to \texttt{SOURCES}.  It does not say
which subproject gets built which way -- that is decided by what is
in the directory, and only build systems that have been asked for are
ever considered.  Vendoring a kernel next to your own code is
therefore all one file:

\begin{verbatim}
BUILD_SYSTEMS += kconfig

SUBPROJECTS   += linux
CONFIGUREOPTS += --defconfig x86_64_defconfig
CONFIGUREOPTS += --configure CONFIG_KVM=y
\end{verbatim}

Nothing is added to the tree you vendored, and nothing in it has to
know that \texttt{pconfigure} exists.  \texttt{linux} is built the
\texttt{kbuild} way because there is a \texttt{Kconfig} in it; a
subproject with a \texttt{Configfile} in it would still be read as a
\texttt{pconfigure} project even with the line above in scope.

There is an implicit \texttt{BUILD\_SYSTEMS += pconfigure} at the
bottom of every project, and it is asked first: a tree that says how
to build itself the \texttt{pconfigure} way meant it.  After that,
build systems are asked in the order they were named, and the first
one that recognizes the directory gets it.  A \texttt{SUBPROJECTS}
that nobody recognizes is an error that lists what was asked.

Everything about a vendored tree is left alone.  In particular
\texttt{pconfigure} does not write a \texttt{Makefile} there: that
file already exists and belongs to the tree, and it is the file the
vendored build system reads.  The rules that drive the build go into
the \texttt{Makefile} of the project that pulled the subproject in,
the build happens in that project's object directory rather than in
the tree, and \texttt{make distclean} throws that away without
touching the tree at all.

Where in there it happens is named after the tree and after nothing
else: a subproject vendored at \texttt{src/linux} builds into
\texttt{\$obj\_dir/linux}.  Which build system was picked is not part
of the name, since nobody chose it --- it was worked out from what is
in the directory --- and neither is the source directory, which every
subproject that lives where the sources live is under and which
therefore tells no two of them apart.  Taking the source directory
off is also what keeps a vendored tree's output clear of
\pconfigure's own object files, which keep the path they were
compiled from and so all live under \texttt{\$obj\_dir/src}.  A tree
vendored somewhere else keeps the path it was vendored at:
\texttt{vendor/br} builds into \texttt{\$obj\_dir/vendor/br}.

Two subprojects that would build into the same directory are a fatal
error.  \texttt{src/linux} and \texttt{linux} differ only by the part
that comes off the front, so both of them ask for
\texttt{\$obj\_dir/linux} --- and two trees sharing an output
directory would each be running somebody else's build system over the
other one's files, with nothing anywhere saying so.

A vendored tree belongs to exactly one project in the run.  Two
\texttt{SUBPROJECTS} lines in one \texttt{Configfile} that name the
same tree are the same tree, and a \texttt{CONFIGUREOPTS} after the
second lands on it.  The same tree named by two different projects is
a fatal error that points at both lines: say a subproject \texttt{a}
has \texttt{SUBPROJECTS += k} and the top also has
\texttt{SUBPROJECTS += a/k}.  Each project builds what it vendors into
its own object directory, from rules in its own \texttt{Makefile}, so
there is no one build the second line could be talking about.  Keep
whichever line should own the tree and put the tree's
\texttt{CONFIGUREOPTS} and \texttt{SUBPROJECT\_TARGETS} under it.

Unlike a \texttt{pconfigure} subproject, a vendored tree is built with
a recursive \texttt{make}.  There is no way to fold somebody else's
build system into this one's dependency graph, so the rule that
builds it just runs \texttt{\$(MAKE) -C} and lets that build system do
what it does.  What \texttt{pconfigure} does instead is work out, at
configure time, every file that build could possibly read, and hang
the recursive \texttt{make} off all of them -- so \texttt{make} at the
top of a tree that is already built does no work at all, and
\texttt{make} after you touch a file down inside the vendored tree
does.

That list of files is a guess, and it is meant to be.  Being generous
costs one \texttt{stat} per file that didn't matter; being short just
means the sub-\texttt{make} gets entered more often than it strictly
had to, and the sub-\texttt{make} is the thing that decides what
actually gets rebuilt.  Nothing is ever built or skipped on the
strength of the guess.

\subsection{\texttt{CONFIGUREOPTS += \$opt} \label{cmd:configureopts}}

Passes an option to whichever build system or subproject was named
most recently, in the same way that \texttt{COMPILEOPTS} passes an
option to whichever \texttt{LANGUAGES} or \texttt{BINARIES} was named
most recently.

After a \texttt{BUILD\_SYSTEMS} it applies to every subproject that
ends up being built that way; after a \texttt{SUBPROJECTS} it applies
to that subproject alone, on top of whatever its build system was
already given.  What an option means is up to the build system it
reaches; see Section~\ref{buildsys}.

An option the build system refuses is a fatal error that names the
line it was written on.  Some of what an option says can only be
checked once a \texttt{SUBPROJECTS} has given it a tree and a project
to be inside --- whether a prefix is inside the object directory,
whether a \texttt{--setup-script} is there, what a \texttt{--depend}
names --- and for one written after a \texttt{BUILD\_SYSTEMS} that is
a later line, or the end of the project.  The refusal still names the
line that wrote the option, since that is the one to fix.

\subsection{\texttt{MAKEOPS += \$name=\$value} \label{cmd:makeops}}

Puts a variable on the command line of the \texttt{make} that builds a
vendored subproject, where it beats whatever that tree's own
\texttt{Makefile} has to say about it.  This is how somebody else's
build system gets told something it never asked to be told:

\begin{verbatim}
SUBPROJECTS += linux
MAKEOPS     += ARCH=arm64
MAKEOPS     += KCFLAGS=-O2 -g
\end{verbatim}

Like \texttt{CONFIGUREOPTS} (see Section~\ref{cmd:configureopts}) this
lands on whichever \texttt{SUBPROJECTS} was written last, or on a whole
\texttt{BUILD\_SYSTEMS} when it was written after one of those --- in
which case every subproject built that way gets it.

One \texttt{MAKEOPS} is one variable, whatever is in its value: the
line reaches \texttt{make} as a single argument, so a value with a
space in it arrives with the space still in it rather than becoming a
second word that \texttt{make} reads as a goal or a flag of its own.
The value is not taken apart in any other way, so
\texttt{\$(abspath x)} and \texttt{\$(PATH)} mean what they say and
are worked out by \texttt{make} --- note that this is
\texttt{\$(PATH)} and not \texttt{\$PATH}, since \texttt{make} reads
a lone \texttt{\$} as naming a one-character variable.

The variable reaches every invocation of the tree, the configuration
as well as the build, because a tree told \texttt{ARCH=} for one and
not the other configures for one machine and then builds for another.
Changing one re-configures and rebuilds the tree, the same way
changing a \texttt{CONFIGUREOPTS} does and for the same reason (see
Section~\ref{cmd:configureopts}).

A \texttt{MAKEOPS} written where nothing is run by \texttt{make} is a
fatal error: there is no \texttt{make} being run there for a variable
to go on the command line of.  That is a \texttt{pconfigure}
subproject, whose rules come out of this same run; a \texttt{cargo}
one, whose build is a \texttt{cargo} command
(Section~\ref{buildsys:cargo}); a \texttt{meson} one, whose build
is a \texttt{ninja} command (Section~\ref{buildsys:meson}); and a
\texttt{cmake} one whose generator writes something other than
\texttt{Makefile}s (Section~\ref{buildsys:cmake}).  It is refused rather than dropped,
since a variable that was quietly dropped is a build that is wrong in
exactly the way the variable was written to prevent.

A \texttt{MAKEOPS} has to be a variable, and that is checked when the
line is read rather than left for \texttt{make} to find in the middle
of a build.  One with no \texttt{=} in it is a fatal error, since
\texttt{make} would take it for a goal to build.  So is one with
nothing in front of its \texttt{=}, or of the \texttt{:=},
\texttt{+=}, \texttt{?=} or \texttt{!=} that \texttt{make} also reads
as an assignment: \texttt{MAKEOPS += =arm64} and \texttt{MAKEOPS +=
:=arm64} set no variable at all.  What else a name may hold is left to
\texttt{make}, which allows a good deal more than a shell does.

\subsection{\texttt{SUBPROJECT\_TARGETS += \$path}
\label{cmd:subproject_targets}}

Names a file that a vendored subproject produces, so that the rest of
the build can wait for that file rather than for the whole tree.

Everything else about such a tree hangs off a single stamp that says
it has been built, and a stamp is not something anything else can
usefully name.  This turns a file the tree happens to write into a
target with a rule behind it, which a \texttt{TESTDEPS}, a
\texttt{--depend} or a link line can then ask for like any other path:

\begin{verbatim}
BUILD_SYSTEMS      += kconfig

SUBPROJECTS        += linux
MAKEOPS            += ARCH=arm64
SUBPROJECT_TARGETS += arch/arm64/boot/Image

PHONY              += integration
TESTDEPS           += linux/build/arch/arm64/boot/Image
TESTSRC            += boots.bash
\end{verbatim}

\texttt{\$path} is relative to the directory the tree builds into,
which for a \texttt{kconfig} or \texttt{buildroot} tree is the
\texttt{O=} it was handed:
\texttt{\$obj\_dir/\$dirname/build}.  A path that
climbs out of there is a fatal error, since it would be claiming that
this tree builds a file it never touches.

A \texttt{TESTDEPS} names the same file with that directory on the
front, which is what the example above is doing: the \texttt{linux}
in it is the one in the object directory rather than the vendored
tree itself (see Section~\ref{cmd:testdeps}).

However many of these are named, exactly one rule ever recurses into
the tree: they all wait on the same stamp, which is the only thing
that runs the tree's own build system.  A rule per output would be a
\texttt{make -j} running somebody else's build system several times
over in the same directory at once.

Naming an output does not make \pconfigure\ believe anything about
it.  If the tree finishes and the file is not there, the build stops
and says which \texttt{SUBPROJECT\_TARGETS} was wrong, rather than
letting whatever wanted the file run without it.  A plain
\texttt{make} is what asks --- these are part of \texttt{make all},
which costs nothing since the tree has built them by then --- so a
name that is wrong is complained about at the first build rather than
whenever something happens to want that file.

A file the tree's configure step writes, such as a \texttt{kconfig}
tree's \texttt{.config} or an \texttt{autotools} tree's
\texttt{config.status}, already has a rule: the one that runs that
configure step.  Naming it here is allowed, and gets no second rule
--- the one already there is what builds it, and is what anything
that asks for the file waits on.

A \texttt{SUBPROJECT\_TARGETS} needs a \texttt{SUBPROJECTS} above it
rather than a bare \texttt{BUILD\_SYSTEMS}: it names a file in one
tree's output directory, so it has to say which tree.  It also can't
be written under a \texttt{pconfigure} subproject, which has no one
file that says it has been built --- a \texttt{pconfigure} subproject's
outputs already have rules of their own, so name those instead.

\subsection{\texttt{BOOTSTRAP = \$dirname} \label{cmd:bootstrap}}

Names a vendored \pconfigure\ source tree that this project builds
itself with, so that a fresh checkout can be built by typing
\texttt{make} and nothing else.

A project whose build system has to be built first hands whoever
clones it a problem before it hands them a build.  They have to find
out that \pconfigure\ exists at all, get one, and get one new enough
for the \texttt{Configfile}s in front of them --- none of which the
tree says out loud.  \texttt{BOOTSTRAP} moves all of that into the
\texttt{Makefile}, where it becomes one more thing \texttt{make} knows
how to build:

\begin{verbatim}
BOOTSTRAP  = src/pconfigure

LANGUAGES += c
BINARIES  += hello
SOURCES   += hello.c
\end{verbatim}

A \texttt{BOOTSTRAP} is a \texttt{SUBPROJECTS}
(Section~\ref{cmd:subprojects}) plus the two things nothing else
needs.  The tree is read as a subproject, its \texttt{Makefile} is
included, and the \pconfigure\ in it is built out of the same
dependency graph as everything else --- editing one of its sources
rebuilds it as part of the build that wanted it, and \texttt{make -j}
schedules across it.  There is no recursive \texttt{make} anywhere in
this.  Everything a subproject does, this does, which is worth knowing
in both directions: its tests run under \texttt{make check} and it
gets installed into the same \texttt{PREFIX}.  A project that wants
\texttt{make check} to mean only its own tests says so with
\texttt{DEFAULT\_TEST\_SUITE} (Section~\ref{cmd:default_test_suite}).

The two extra things are a way to build a first \pconfigure\ with no
\pconfigure\ in hand, and a \texttt{Makefile} that says so.

\texttt{\$dirname} is relative to where \pconfigure\ was run and has
to be inside the tree, usually as a git submodule.  It points at
\pconfigure's source rather than at a \pconfigure\ binary because a
binary is something somebody already built, which is exactly what a
fresh checkout has not got.  The directory is checked for an
executable \texttt{bootstrap.sh} while the \texttt{Configfile} is
being read, since the usual way to get this wrong is a submodule
nobody has checked out yet.

Being inside the tree means what it means for \texttt{SUBPROJECTS},
and is asked the same way: a path that climbs out with \texttt{../},
one inside the object directory, and one that reaches outside the
project or into the object directory through a symlink are all fatal
errors, as is a shell metacharacter or a directory starting with a
\texttt{-}.  The vendored \pconfigure\ is the
last tree anybody wants a \texttt{make distclean} to remove.  An
absolute path is a fatal error here too, even one that names a
directory inside the tree, because it ends up in the committed
\texttt{Makefile} and names that directory only where this checkout
happens to sit.

With one of these, \pconfigure\ writes two files instead of one.
Everything it generates goes into \texttt{Makefile.pconfigure}, and
the \texttt{Makefile} in its place holds only what the
\texttt{BOOTSTRAP} line said: where the vendored source is, how to
bootstrap a \pconfigure\ out of it, how to run that \pconfigure, and
an \texttt{include} of the other half.

That second file is the one to commit.  \texttt{make} remakes what it
includes before it reads it, so a checkout holding nothing but the
sources and that \texttt{Makefile} bootstraps \pconfigure, configures
itself and builds, in one \texttt{make}.  And because everything in it
comes from the one \texttt{BOOTSTRAP} line, it says the same thing
next year that it says today --- a generated file in revision control
that changed whenever a \texttt{Configfile} did would be a merge
conflict on every branch.  \pconfigure\ rewrites it only when it would
say something new.

\texttt{Makefile.pconfigure} is written when it isn't there and left
alone once it is.  These projects are no different from any other
about that: what a \texttt{Makefile} says is what the
\texttt{Configfile}s said the last time somebody ran \pconfigure, and
running it again is \texttt{make reconfigure}
(Section~\ref{make:reconfigure}).  The rule is the same one every
project gets, pointed at the \pconfigure\ this project builds rather
than at the one that wrote the \texttt{Makefile} --- pinning a
\pconfigure\ and then reconfiguring with somebody else's would be
pinning nothing at all.  It takes the same \texttt{PCONFIGURE\_ARGS},
and so does the first configure:

\begin{verbatim}
$ make PCONFIGURE_ARGS="--config debug"
\end{verbatim}

Options given to that first \texttt{make} are recorded in
\texttt{Makefile.pconfigure} like any others, so a plain \texttt{make}
after it --- including one that runs \pconfigure\ again under
\texttt{AUTORECONFIGURE} --- keeps them.

\texttt{make distclean} takes back \texttt{Makefile.pconfigure} along
with everything else \pconfigure\ wrote, and leaves the committed
\texttt{Makefile} alone: a tree it had removed that from is a tree
nobody could type \texttt{make} in any more.

\texttt{make clean} takes back \texttt{Makefile.pconfigure} as well.
A clean deletes the vendored \pconfigure\ and the tools beside it,
which are build outputs like any other, and the
\texttt{Makefile.pconfigure} left behind could not build them again:
some of what it needs to do that, the clean has just taken.  So the
\texttt{make} after a clean bootstraps and configures the way the first
one in a fresh checkout does, which is slower than an ordinary rebuild
and is the only one of the two that works.

Bootstrapping clears out the vendored tree first, its own
\texttt{Makefile} included.  That matters because a bootstrap
normally runs in a tree this project has already configured, which
leaves a \texttt{Makefile} written to be included from up here ---
and \pconfigure\ refuses to write over one of those from inside the
subproject, since standing down there what this project calls the
directory cannot be recovered.  Nothing is lost: the bootstrap writes
one of its own, and the next \pconfigure\ run from up here writes
the version that gets included.  \texttt{make clean} takes away the
vendored \pconfigure, so this is the path every \texttt{make clean}
followed by \texttt{make} goes down.

A \texttt{BOOTSTRAP} belongs in the \texttt{Configfile} of the project
\texttt{make} is run at.  Written in a subproject it is a fatal error,
since a subproject's \texttt{Makefile} is included by the one above it
and a second copy of these rules down there would be a second recipe
for the same file.  It doesn't work alongside \texttt{SRCPATH}, which
is the restriction \texttt{SUBPROJECTS} already has and for the same
reason.  And a tree that doesn't build a \pconfigure\ is a fatal error
too: the committed \texttt{Makefile} runs a path and has nothing else
to go on, so a \texttt{BOOTSTRAP} aimed one directory too high or too
low would configure, build, and then fail in the middle of some later
\texttt{make} with a shell saying it can't find a program.

\subsection{\texttt{DEPLIBS += \$libname} \label{cmd:deplibs}}

Adds an internal library dependency to the list of link options.  This
is the same as calling
\begin{verbatim}
LINKOPTS += -l$libname
\end{verbatim}
and nothing more: the \texttt{Makefile} dependency on
\texttt{lib\$libname.so} comes from the \texttt{-l} itself, so a
library that reaches the link line some other way -- from
\texttt{LINKOPTS}, or from \texttt{ppkg-config} -- gets one too.

A \texttt{DEPLIBS} written under a static archive is a fatal error,
since an archive is never linked; see Section~\ref{cmd:libraries}.

\subsection{\texttt{TESTDEPS += \$path} \label{cmd:testdeps}}

Names something that has to be built before this target's tests are
run.  This is \texttt{DEPLIBS}' opposite number for the test side, and
it takes a whole path rather than a library name because what a test
wants built first is usually a program rather than a library -- and
there's no short name that covers everything a test could possibly
need.

\texttt{\$path} is relative to the project that names it, the same way
a \texttt{SOURCES} is, and it applies to every \texttt{TESTS} written
underneath the same target -- so the useful place to put one is
directly after the \texttt{BINARIES} or \texttt{TESTEXECS} line:

\begin{verbatim}
BINARIES  += vm
TESTDEPS  += libexec/mkfs
TESTSRC   += boots.bash
TESTSRC   += mounts.bash
\end{verbatim}

\texttt{\$path} has to name something inside the project that wrote
it.  A \texttt{../} that climbs out of the project, or a path that
starts from the root, is a fatal error -- and it is one whether the
project is being built on its own or as part of something bigger,
since a rule whose meaning changed with where \texttt{make} was run
would be no rule at all.

There are two things to reach for when what a test needs was built by
somebody else, and both of them already exist.  If the test needs
another project's \textit{output}, that is a dependency of the build
rather than of the test: put it on the link line, where every other
cross-project dependency goes, usually through \texttt{ppkg-config}
(see Section~\ref{prog:ppkg-config}).  If the test is really about two
projects at once, it is an integration test, and it belongs to the
project that has both of them -- from up there, the path to either
one is an ordinary path that never leaves the tree:

\begin{verbatim}
SUBPROJECTS += fs
SUBPROJECTS += vm

BINARIES    += integration
TESTDEPS    += fs/libexec/mkfs
TESTDEPS    += vm/bin/vm
TESTSRC     += boots-a-real-image.bash
\end{verbatim}

A file that a vendored subproject was said to produce (see
Section~\ref{cmd:subproject_targets}) is named from the object
directory that tree builds into rather than from the project:

\begin{verbatim}
SUBPROJECTS        += src/linux
SUBPROJECT_TARGETS += arch/arm64/boot/Image

PHONY              += integration
TESTDEPS           += linux/build/arch/arm64/boot/Image
TESTSRC            += boots.bash
\end{verbatim}

The object directory is on the front of every one of those paths and
so tells none of them apart: what it adds to the line is the answer
to a question --- where does this project keep its build output ---
that the line was not asking, and the answer is the same one every
time.  Writing it out anyway still works, and both spellings come out
as the same prerequisite, since there is one name for that file in
the \texttt{Makefile} whichever way it was asked for.

Only a file a \texttt{SUBPROJECT\_TARGETS} named is read this way.
That set is exactly the paths with a rule behind them, so a project
that has a directory of its own named after one of its vendored trees
still reaches its own with everything it wrote before.

Like everything else in a \texttt{Configfile} this is read where it
is written, so the \texttt{SUBPROJECTS} and its
\texttt{SUBPROJECT\_TARGETS} have to be above the tests that wait for
them.  A \texttt{TESTDEPS} read first is a fatal error rather than a
path in the project that nothing builds, since which of the two lines
should move is not something \pconfigure\ can pick for you.

A \texttt{TESTDEPS} can also be written in the test itself, as a
\texttt{\#pconfigure} directive (see Section~\ref{directive}).  That is
what to reach for when one test of a target needs something and the
others don't: written here the line lands on the target, and every
test underneath reads it.

A \texttt{TESTDEPS} waits for something the \textit{build} makes.  A
test that has to wait for another \textit{test} --- because what it
wants is whatever that test left behind rather than anything a rule
produces --- wants a \texttt{DEPTESTS} instead (see
Section~\ref{cmd:deptests}).

\subsection{\texttt{DEPTESTS += \$test} \label{cmd:deptests}}

Names a test that has to have run before this one does.  This is what
to reach for when two tests share something that costs too much to
make twice: the first one makes it, and the second one reads what the
first one left behind.

\begin{verbatim}
PHONY     += integration
TESTSRC   += builds-an-image.bash
TESTSRC   += boots-that-image.bash
DEPTESTS  += builds-an-image.bash
\end{verbatim}

\texttt{\$test} is a test of the same target, spelled exactly the way
that test's own \texttt{TESTS} or \texttt{TESTSRC} line spelled it.  A
path that climbs out of the check directory is a fatal error: it would
be reaching for a test belonging to some other target, and an order
between two targets' tests only holds when one \texttt{make} happens to
build both, which is no order at all.  Two tests that share state are
one suite however they got written, and a suite belongs to whoever has
all of it --- which is what a \texttt{PHONY} (see
Section~\ref{cmd:phony}) is for.

Unlike \texttt{TESTDEPS} (see Section~\ref{cmd:testdeps}) and every
other command shaped like it, this one goes under a single test rather
than under the target.  A target-wide one would be read by every test
underneath it, and one of those tests is the one being waited for ---
so what it asked for would be a test waiting for itself.  The waiting
is a property of the one test that does it, so that is where the line
goes: directly under that test's own \texttt{TESTSRC}, as above.
Written anywhere else it is a fatal error rather than a line that
attaches itself to whatever happens to be open.

\subsubsection{What this promises, and what it doesn't}

All \pconfigure\ does here is put the two tests in an order and re-run
the second one whenever the first one runs.  The tarball the first
test leaves behind is an ordinary prerequisite of the second test's
rule, so \texttt{make} orders them, \texttt{make -j} keeps them from
overlapping, and a change that re-runs the first one re-runs the
second one too --- a test that passed against state that has since
been rebuilt would otherwise go on claiming to have passed.

What it does \textit{not} do is look at how the first test went.  A
test that fails is still a test that finished, and its check target is
a target that was made: \texttt{make check} builds every result and it
is \texttt{make report} that has an opinion about what they say (see
Section~\ref{prog:ptest}).  So a failed predecessor does not stop its
successors --- they run, and they are the ones that decide what a
predecessor's failure means to them.  That is deliberate: only the
tests know whether the state they wanted got made.

Passing the state along is between the two tests as well.  What the
first test wrote into \texttt{\$PTEST\_TMPDIR} is what \pconfigure\
collects, so \texttt{\$PTEST\_CHECKDIR} (see Section~\ref{cmd:tests})
is where the second one finds it:

\begin{verbatim}
tar -xf "$PTEST_CHECKDIR/builds-an-image.bash" -C "$PTEST_TMPDIR"
\end{verbatim}

That route copies the state twice --- once into the predecessor's
result and once back out again --- which is fine for a file and is the
wrong shape entirely for the case a \texttt{DEPTESTS} usually exists
for, where the state is expensive precisely because it is large.  For
that, the predecessor writes into its
\texttt{\$PTEST\_SCRATCH\_DIR} (see Section~\ref{cmd:tests}) and the
successor reads it where it lies.  A test's scratch is named after the
test and they are all siblings, the same way every test of a target
leaves its result in one check directory:

\begin{verbatim}
image="$(dirname "$PTEST_SCRATCH_DIR")/builds-an-image.bash.scratch/disk.img"
\end{verbatim}

Nothing is copied, so what it costs does not grow with how big the
state is.  What it gives up is the collection: that directory is not
in the predecessor's result, so a run that is read back later says
what the test decided and not what it was looking at.

\subsubsection{Orders that can't happen}

A \texttt{DEPTESTS} naming a test no \texttt{TESTS} line ever wrote is
a fatal error, and so is a set of them that waits in a circle.  Both
are things \texttt{make} has an answer for --- \texttt{No rule to make
target} for the first, and quietly dropping an edge for the second ---
and neither answer names the \texttt{Configfile} line that caused it.
The second is the worse of the two by a distance: the build works, and
the order it was asked for silently isn't the order it used, which is
the whole thing a \texttt{DEPTESTS} was written to be sure of.

\subsection{\texttt{TEST\_SUITES += \$name} \label{cmd:test_suites}}

Declares a test suite: a name for some of the project's tests, which
\texttt{make check-\$name} runs and \texttt{make report-\$name}
reports on (see Sections~\ref{make:check_suite}
and~\ref{make:report_suite}).

A project that can't run all of its tests everywhere has nowhere to
say so while there is only one set of them.  \texttt{make check} has
to mean the same thing on every machine it is typed on, so the tests
that want a network, or a card, or an hour go in under the same name
as the ones that want nothing --- and what usually happens next is
that they are left out of the \texttt{Configfile} entirely, which
means nobody runs them at all.

\begin{verbatim}
TEST_SUITES      += network

BINARIES         += crawler
SOURCES          += crawler.c
TESTSRC          += parses-a-page.bash
TESTSRC[network] += fetches-a-page.bash
\end{verbatim}

\texttt{\$name} is what the suite's \texttt{make} targets are called,
so it holds letters, digits, \texttt{-}, \texttt{\_} and \texttt{.}
and nothing else.  Naming a suite that has already been declared gets
back to it rather than declaring a second one, the same way a second
\texttt{BUILD\_SYSTEMS} line does.

A suite that nothing joined is not an error: the name is a promise
about what \texttt{make check-\$name} means, and an empty suite keeps
it by running nothing.  Making that suite the one \texttt{make check}
means is an error, though, and Section~\ref{cmd:default_test_suite}
says why.

\subsubsection{Which tests are in a suite}

A test is in a suite four ways.  Three of them are things somebody
wrote down, and the fourth is not a choice.

The first is the ordinary one: the test said so, with
\texttt{TESTS[\$name]} or \texttt{TESTSRC[\$name]} (see
Sections~\ref{cmd:tests} and~\ref{cmd:testsrc}).  A name no
\texttt{TEST\_SUITES} line declared is a fatal error --- it would be a
test in no suite at all, which is indistinguishable from a suite
nobody has joined yet.

The second is \texttt{INCLUDE\_TEST\_SUITES} (see
Section~\ref{cmd:include_test_suites}).

The third is being written without a suite.  Most tests can run
anywhere, and a project where every one of them has to name every
suite is a project whose lists drift apart the first time somebody
adds one --- so a plain \texttt{TESTS} or \texttt{TESTSRC} is in
every suite it could run in.  Every suite it \textit{could} run in:
a test that waits for another one with a \texttt{DEPTESTS} (see
Section~\ref{cmd:deptests}) can't run where the test it waits for
doesn't, so it joins the suites that already have all of them.  That
is the case this is really for --- one expensive test that needs the
network and a handful of cheap ones that read what it left behind:

\begin{verbatim}
TEST_SUITES      += network

BINARIES         += crawler
SOURCES          += crawler.c
TESTSRC[network] += fetches-a-page.bash
TESTSRC          += parses-what-was-fetched.bash
DEPTESTS         += fetches-a-page.bash
\end{verbatim}

\texttt{parses-what-was-fetched.bash} is in \texttt{network} and in
no other suite, because the only test it waits for is only there.  It
did not have to say so, and it does not have to be edited when a
second suite shows up.

The fourth is being waited for by a test that is in the suite, which
follows from what a \texttt{DEPTESTS} is: \texttt{make} builds the
result of the test being waited for before it runs the test that
waits.  A suite that didn't claim it would run it anyway and then not
report it.

\subsubsection{\texttt{INCLUDE\_TEST\_SUITES += \$name}
              \label{cmd:include_test_suites}}

Says that this suite runs another suite's tests as well as its own.
The machine with the network can also run everything the machine
without it can, and writing that down as membership means naming every
test twice:

\begin{verbatim}
TEST_SUITES         += quick

TEST_SUITES         += everything
INCLUDE_TEST_SUITES += quick
INCLUDE_TEST_SUITES += network
\end{verbatim}

This says nothing about order and nothing about when anything runs.
The tests of an included suite are the same tests, run once, reported
under both names; making one test wait for another is what a
\texttt{DEPTESTS} is for.

The line goes directly under the \texttt{TEST\_SUITES} line of the
suite that does the including.  Written anywhere else it is a fatal
error rather than a line that attaches itself to whichever suite was
declared furthest up the file.

What gets included is every test of the build that is in the suite
named, not just the ones that live beside the line that named it.  A
suite of one name is one suite in a build with subprojects (see
Section~\ref{cmd:subprojects}), because there is one rule with that
name for somebody to run --- so a subproject's test that joined
\texttt{quick} is in this \texttt{everything} for the same reason it
is in this \texttt{quick}.  The subproject does not have to have heard
of \texttt{everything}, and a build whose subprojects each declare
every suite the top includes is a build where they didn't have to.

Naming a suite this project never declared is a fatal error, which the
paragraph above does not take back: what an inclusion reaches across a
build is tests, so the suite being included still has to be one this
project's own \texttt{TEST\_SUITES} declared.  A suite is allowed to
include one that a line further down declares, though:
the suites of a project are a set, and nothing about them depends on
which line came first.  Two suites that include each other are two
names for one set of tests, which is a strange thing to write and a
perfectly clear thing to mean, so it is allowed.

\subsubsection{\texttt{DEFAULT\_TEST\_SUITE = \$name}
              \label{cmd:default_test_suite}}

Says which suite \texttt{make check} and \texttt{make report} mean.
Without one they mean every test the project has, which is what they
have always meant.

\begin{verbatim}
TEST_SUITES        += quick

DEFAULT_TEST_SUITE  = quick
\end{verbatim}

This is for the project whose tests mostly can't be run on a fresh
checkout.  The tests that need something special are exactly the ones
a stranger to the project should not be handed by default, and a
sentence in a \texttt{README} about it is a sentence that gets read
after the build has already gone red.  Nothing is taken away: the
machine that can run the rest asks for them by name.

Naming a suite the project never declared is a fatal error, and this
is the one of the three where it has a symptom worth naming: a
\texttt{make check} that runs no tests at all and says they all
passed.

Naming a suite that is declared and has no tests in it is a fatal
error for the same reason, since it is the same \texttt{make check}.
An empty suite is otherwise fine (see
Section~\ref{cmd:test_suites}) --- \texttt{make check-\$name} was
asked for by name, and running nothing is what the name was promised
to mean.  Nobody asks for \texttt{make check} by name, so nothing
coming back from it is read as the tests having passed rather than as
there being none.  What counts as having tests is every test the rule
would run, which includes the ones an
\texttt{INCLUDE\_TEST\_SUITES} brought in and the ones a subproject
put in a suite of the same name.

\subsection{\texttt{AUTODEPS = bool} \label{cmd:autodeps}}

Allows the automatic dependency generation inside \texttt{pconfigure}
to be disabled for a particular target.  The general idea here is that
sometimes this won't work: one example is a project with two shared
libraries, where one library depends on the other.  You really don't
want everything to be compiled into the depending shared library, but
there's no good way to tell \texttt{pconfigure} that.

Luckily that case is simple enough where you really do just want to
put \textit{everything} inside a single folder into the library, so
it's easy to write a bash script that generates all the
\texttt{SOURCES} lines and then disable automatic dependency
generation all together.

What this turns off is what gets \textit{built}: the sources sitting
behind a target's headers stop being compiled and linked in alongside
it.  The headers themselves are still prerequisites of the objects
built from them either way, since that is a question about when to
rebuild rather than about what to link, and there is no target that
wants to be left as it was when a declaration it was compiled against
moves.  A build that skipped those would hand you a program with one
translation unit compiled against the old header and the rest against
the new, which is not a failure \texttt{make} has any way to notice.

That leaves nothing for this to do on a target where nothing is
linked, which is what a \texttt{BASH} target is, and writing it there
is a warning (see Section~\ref{warn}).

\subsection{\texttt{AUTORECONFIGURE = bool} \label{cmd:autoreconfigure}}

Moves the question of what a source depends on out of \pconfigure\ and
into the build.

Ordinarily \pconfigure\ reads every source when it runs, works out
which headers each one includes and which sources sit behind those
headers, and writes the answers into the \texttt{Makefile}.  That
answer is true when it is written and stays in the file until somebody
runs \pconfigure\ again --- so a source that grows an \texttt{\#include}
has changed it, and nothing in the build knows.  What follows is a
program built partly against a header it no longer reads, or a link
that is missing the source behind a header it has started reading, and
in neither case does \texttt{make} have anything to notice.

With this on, the \texttt{Makefile} says only what the
\texttt{Configfile}s said: the targets, and the sources named under
them.  Beside each of those sources it writes a rule that produces a
piece of \texttt{Makefile}, and an \texttt{include} of it.
\texttt{make} remakes what it includes before it reads it, so the
answer is worked out by the build that is about to need it --- and the
piece of \texttt{Makefile} names the pieces belonging to the sources
behind its own headers, so the walk \pconfigure\ used to do by reading
files is done by \texttt{make} reading one fragment after another.

What comes out is the same build.  The objects are the same, in the
same order, compiled with the same command lines; only when the work
happens has changed.  That is deliberate, and it is what makes this
something you can turn on for an existing project without reading the
diff of what it builds.

A \texttt{BASH} or \texttt{perl} script is followed the same way.  The
files it \texttt{\#include}s are pasted into it by \texttt{pbashc} or
\texttt{pperlc}, so they are what it depends on, and the build works
them out by reading the script the way the compiler does: a script
that starts including a file is rebuilt when that file changes, and
one that stops including a file can have the file deleted without
\texttt{make} stopping on it.  \texttt{HEADERS} copied by
\texttt{phc} are the exception, and keep the list \pconfigure\ found:
\texttt{phc} installs a header as it stands, so nothing it includes
is part of what it installs.

\begin{verbatim}
AUTORECONFIGURE  = true

LANGUAGES       += c++
BINARIES        += hello
SOURCES         += hello.c++
\end{verbatim}

It belongs to the project rather than to a target, so it means the
same thing wherever in the \texttt{Configfile} it is written --- for
what that project builds.

A \texttt{SUBPROJECTS} (Section~\ref{cmd:subprojects}) inherits it,
because who works out the dependencies is a property of the build
rather than of one \texttt{Configfile}: a subproject's
\texttt{Makefile} is included by the one \texttt{make} was run on, so
both halves are read by the same \texttt{make}.  A subproject that
writes its own \texttt{AUTORECONFIGURE} still wins, the way it does
with a \texttt{PREFIX}.

That inheritance is the one thing about this command that does depend
on where the line sits, because a subproject is read at the point its
line appears: a tree pulled in above the line was read while the
answer was still the other one.  Rather than let that be a silent
difference, \pconfigure\ refuses it and says which line to move.  The
spelling that catches people is \texttt{BOOTSTRAP}
(Section~\ref{cmd:bootstrap}), which reads the tree it names as a
subproject --- so a \texttt{Configfile} that opens with one has
already read a project by its second line.

The program that writes the fragments is \texttt{pdeps}, which lives
next to \pconfigure\ and is not something to run by hand.  The
fragments, and the context files \texttt{pdeps} reads to find out what
is being built, go under \texttt{\$OBJDIR}, and \texttt{make
distclean} takes them with everything else.

\subsubsection{A \texttt{Configfile} that changed}

Under \texttt{AUTORECONFIGURE} the build runs \pconfigure\ again when
one of the \texttt{Configfile}s it was written out of has changed.
That is the other half of the same promise: a source growing an
\texttt{\#include} was already noticed, and the line saying which
sources there are is the input nothing was watching.  It covers every
\texttt{Configfile} the run read, including those of every
\texttt{SUBPROJECTS} --- a subproject cannot be configured from inside
itself, so its \texttt{Configfile} changing re-runs the \pconfigure\
at the top of the tree.

That holds whichever project asked.  A subproject that says
\texttt{AUTORECONFIGURE = true} under a top that does not gets the same
watch, over every \texttt{Configfile} the run read rather than only its
own, because what it builds is written out of the \texttt{Configfile}
above it as well: its \texttt{SUBPROJECTS} line and everything it
inherits are there.  It is the same list a top that asks watches when
one of its subprojects says \texttt{false}.

The \pconfigure\ it runs is given the options the last one was, the
same default \texttt{make reconfigure} has
(Section~\ref{make:reconfigure}).  A tree configured with
\texttt{--config}, \texttt{--verbose}, \texttt{--cross-compile} or
\texttt{--srcpath} stays configured that way when a
\texttt{Configfile} changes; a build that dropped them would be a
different build that nobody asked for.

What it does not cover is an input that is not a \texttt{Configfile}.
An executable \texttt{CONFIG} that enumerates a directory is written
out of that directory as much as out of any file, and a file appearing
in it changes nothing this rule is watching.  \texttt{CONFIG\_DEPS}
(Section~\ref{cmd:config_deps}) is how such a \texttt{Configfile} says
so.

It also runs \pconfigure\ again when one of the \texttt{Makefile}s it
wrote for a \texttt{SUBPROJECTS} has gone missing, which is what
deleting a subproject's object directory does --- by hand, or by
running a vendored \pconfigure's own \texttt{bootstrap.sh}, which
starts from an empty one.  Nothing else writes those files, so before
this a deleted object directory was a tree that stopped on ``No rule
to make target'' until somebody configured it by hand.

Without \texttt{AUTORECONFIGURE} nothing of the sort happens, and that
is deliberate rather than an omission: the header graph is frozen at
configure time too, so a \texttt{Makefile} that rewrote itself would
fix one half of the answer and leave the other half stale without
saying so.

The other files a configure leaves in an object directory for the
build to read are a different case, and not only an
\texttt{AUTORECONFIGURE} one: the record of what goes into each link,
the command each script, compiled test and header copy was last made
with --- which is what rebuilds one when its options or its
\texttt{SOURCES} change, since its name does not --- the link each
program and library in the build tree and under the prefix was last
copied from, which is what copies it again when an option goes back
to a value an earlier build used and names the link that build left
behind, the context files
\texttt{pdeps} works from, the options a vendored tree was
configured with, what each \texttt{make check} stands for, and the
files a bare \texttt{ptest} reads (see Section~\ref{prog:ptest}).  The
\texttt{Makefile} knows what
each of them says, so it has a rule that writes a missing one back
exactly as the configure wrote it, without running \pconfigure.
Deleting the object directory of the project \pconfigure\ ran in, or
any part of one, costs a rebuild of what was in there and nothing
more.  A subproject's whole object directory also takes the
\texttt{Makefile} its parent includes, and putting that back is the
configure described above.

A \texttt{Configfile} that never existed before is noticed the day it
is written, since the names are looked up afresh on every run.  One
that is deleted is not --- the same \texttt{\$(wildcard)} that lets an
absent \texttt{Configfile.local} be named at all is what makes its
removal invisible.  And a \texttt{Configfile} that is a program is on
its own for whatever \emph{it} reads: \pconfigure\ never opened those
files and cannot name them.

\subsubsection{What it does not do}

It covers C and C++.  Every other language still works its
dependencies out when \pconfigure\ runs, so a \texttt{BASH} target
whose script grows an \texttt{\#include} needs a reconfigure the way it
always did.

A header that the build itself makes is found whether or not it
exists when the fragment naming it is written, as long as it is one
\pconfigure\ knows about: the output of a \texttt{GENERATE} or the
copy a \texttt{HEADERSRC} makes.  Those are the headers a
\texttt{make clean} or a deleted object directory takes away, and the
fragment worked out afterwards still names them, so the object waits
for the header to be made again and is recompiled when it changes.
What such a header includes in turn is only found once it exists, and
the fragment naming it is worked out again when it does.  A header
made any other way --- by a rule \pconfigure\ did not write --- is
found only if it exists when the fragment is written, which is the
same hazard a configure-time scan has.

A fragment waits on the source it describes and on the file recording
the options it was written under, and on nothing else this build
builds.  That is deliberate rather than an oversight: \texttt{make}
brings a makefile it includes up to date before it has finished
reading the build, out of the rules it already holds --- which came
from a \texttt{Makefile} that may be the very thing that has gone out
of date.  Anything a fragment waited on would be built from those
rules, ahead of the reconfigure that would have corrected them, and a
source file added since would take the tree down at the link rather
than being compiled.  What it costs is that rebuilding \texttt{pdeps}
does not on its own rewrite the fragments \texttt{pdeps} wrote; a
reconfigure does, and one happens whenever the recorded options
change.

A header that shadows the one a source was built against is noticed
too, even though nothing the fragment waits on changes when it
appears.  An \texttt{\#include "x.h"} is looked for beside the source
before the \texttt{-I} directories, and down those in order, so a
\texttt{src/x.h} written after a build that found \texttt{inc/x.h},
or an \texttt{inc1/x.h} ahead of an \texttt{inc2/x.h}, changes what
the source reads.  Each fragment remembers the places its scan looked
and found nothing, and the next \texttt{make} --- run by hand or
after a reconfigure --- works the fragment out again when a file is
in one of them, whatever its date.  The same holds for what a
\texttt{BASH} or Perl script includes.  Something there that is no
header, a directory, is passed over the way the compiler passes over
it, and the build settles rather than looking again.  A place whose
name holds a space or a glob or \texttt{make} metacharacter is not
watched, and a header turning up there is noticed only after a
\texttt{make clean}.

\subsubsection{Sources that go away}

Deleting a source leaves the fragment written about it behind, and
nothing that reads that source has necessarily changed --- what pulled
it in was a header, and the header is still there.  So \texttt{make}
reads a fragment naming a file that is no longer present.  It does not
stop: the source is named through \texttt{\$(wildcard)}, which is a
prerequisite while the file exists and nothing at all when it does
not, and \texttt{pdeps} answers for a missing source by writing a
fragment that says nothing.  What was built from it stops being built.

The link is not redone on its own.  \texttt{make} has no notion of a
prerequisite that went away, only of the ones still named being older
than what was built from them, so a target whose object list shrank is
relinked the next time anything it still names is rebuilt.  That is
equally true of a \texttt{Makefile} with the objects written into it,
and is not something this changes either way.

\subsection{\texttt{ABRT\_IS\_FAIL = bool} \label{cmd:abrt_is_fail}}

Changes how \texttt{ptest} (see Section~\ref{prog:ptest}) scores a
test that was killed by \texttt{SIGABRT}: ordinarily that is an
\texttt{EROR}, the same bucket a missing binary or an unreadable
result lands in, because a crash can just as well mean the harness
never got a straight answer out of the test as it can mean the test
ran and found a bug.  \texttt{ptest} has no way to tell those two
apart on its own, so by default it doesn't try.

\begin{verbatim}
ABRT_IS_FAIL = true

LANGUAGES += c++
TESTS     += checks-an-invariant
SOURCES   += checks-an-invariant.c++
\end{verbatim}

A project whose tests fail by calling a libc \texttt{assert()} --
rather than catching whatever they expect to go wrong and turning it
into an \texttt{exit 1} themselves -- has every one of those failures
looking exactly like the crash \texttt{EROR} is for, every time,
which is the case this exists for: every \texttt{ptest} invocation
that reads this project's results -- the whole-project
\texttt{check}/\texttt{report} pair and any \texttt{TEST\_SUITES}' (see
Section~\ref{cmd:test_suites}) own, in this project's
\texttt{Makefile} and in any parent's that pulls it in as a
subproject -- names its check directory with
\texttt{--abrt-is-fail-dir} rather than \texttt{--check-dir}, so an
exit status of \texttt{128+SIGABRT} there is counted in \texttt{NFAIL}
instead.  It is said per directory because a parent's report is one
\texttt{ptest} run over every project it pulled in, and each of those
gave its own answer: a parent that says \texttt{ABRT\_IS\_FAIL} does
not rescore its subprojects' crashes, and a subproject that says it
keeps that when the report is run from above.  It changes nothing about a crash from any other signal, or
about what \texttt{make check} itself does when a test is red --
only which column a \texttt{SIGABRT} lands in.

Like \texttt{AUTORECONFIGURE} (see Section~\ref{cmd:autoreconfigure})
it belongs to the project rather than to one target, so it means the
same thing wherever in the Configfile it is written.  Unlike
\texttt{AUTORECONFIGURE} there is nothing it changes about how a
source is read, so -- not being able to disagree with a reading that
already happened -- it has nothing to refuse: whichever line runs
last wins, the ordinary rule for a value written more than once.

\subsection{\texttt{VERBOSE} \label{cmd:verbose}}

Writes a \texttt{Makefile} whose recipes are not silenced, so
\texttt{make} echoes each command as it runs it instead of only the
short label that stands in for it --- \texttt{cp -f obj/bin/hello/...
bin/hello} rather than \texttt{CP\ \ \ \ bin/hello}.  What gets built
is exactly the same either way; only what scrolls past changes.

This is a property of a whole \texttt{Makefile} rather than of one
target: if any target in a project is verbose then that project's
\texttt{Makefile} is, so writing it under a \texttt{BINARIES} still
unsilences everything around it.

\subsection{\texttt{DEBUG} \label{cmd:debug}}

Prints what \pconfigure\ is doing while it writes the
\texttt{Makefile}: the name of each target as it is built, and the
paths of the rules that come out of it.  This is about \pconfigure\
rather than about the build --- the \texttt{Makefile} it writes is the
same one either way, and \texttt{VERBOSE} is what to reach for when
the question is about \texttt{make}.

Both of these are written without a value, and writing one at all
turns it on: \texttt{VERBOSE = false} turns verbose output on just as
surely as \texttt{VERBOSE = true} does.  See Section~\ref{warn} for
why that is a warning rather than something \pconfigure\ quietly
does what you meant with.

\subsection{\texttt{CROSS\_COMPILE = \$prefix} \label{cmd:cross_compile}}

Says which machine the targets below this are being built for, by
naming the toolchain that builds for it.  \texttt{\$prefix} is what
every program in that toolchain is called before its own name --
\texttt{aarch64-linux-gnu-}, for a toolchain whose compiler is
\texttt{aarch64-linux-gnu-gcc}.  This is the spelling \texttt{kbuild}
has used for as long as anybody has been cross-compiling anything, and
it's spelled that way here for the same reason: a toolchain is a set of
programs that were named together, so naming the set is less to say
and less to get wrong than naming each program.

Unlike \texttt{COMPILEOPTS} this lands on whatever target is open
rather than on the current language, which is what makes it mean the
same thing everywhere it can be written:

At the top of a \texttt{Configfile}, before any target, it applies to
the whole project -- and to every project that \texttt{Configfile}
pulls in with a \texttt{SUBPROJECTS} after it, the same way a
\texttt{PREFIX} carries down.  Not to the ones pulled in above it,
though: a subproject is read where its line is, so one written above
a top-level \texttt{CROSS\_COMPILE} keeps the toolchain it was read
with.  When a library in that subproject, or in any subproject under
it, is still built with the toolchain the subproject was handed and
that isn't the toolchain the line names, the line is an error naming
it, the subproject and the library, since the project would be linked
against a library built for another machine; it belongs above the
first \texttt{SUBPROJECTS} or \texttt{BOOTSTRAP}, or the subproject
can name the same toolchain itself.  A subproject that builds no
library, that only pulls in others, or whose libraries each name
their own toolchain is built the same wherever the line is written,
and is no reason to refuse it.

After a \texttt{BINARIES}, \texttt{LIBRARIES}, \texttt{LIBEXECS} or
\texttt{TESTEXECS} it applies to that one target, and to the
\texttt{TESTS} written under it.

After a \texttt{SOURCES} it applies to that one file.

Written with nothing after the \texttt{=} it takes back whatever was
inherited, which is how a project that cross-compiles builds the one
tool that has to run on the machine doing the building:

\begin{verbatim}
CROSS_COMPILE  = aarch64-linux-gnu-

TESTEXECS     += guest/hello
SOURCES       += hello.c

BINARIES      += mkimage
CROSS_COMPILE  =
SOURCES       += mkimage.c
\end{verbatim}

It can also be given on the command line, see
Section~\ref{cl:cross_compile}, which is how the same tree gets
configured for one machine and then for another without being edited.

What a prefix means is up to the language: \texttt{c} and \texttt{c++}
run \texttt{\$prefix gcc} and \texttt{\$prefix g++} in place of
\texttt{\$\{CC\}} and \texttt{\$\{CXX\}}, and \texttt{\$prefix ar} in
place of \texttt{\$\{AR\}} for a static archive, a vendored \texttt{kconfig}
subproject is handed \texttt{CROSS\_COMPILE=\$prefix} on its
sub-\texttt{make}'s command line (see Section~\ref{buildsys:kconfig}),
and a language with no notion of a toolchain ignores it.  A target
that a \texttt{CROSS\_COMPILE} applies to is also left unsigned on
macOS, since what comes out of the link isn't a Mach-O; see
Section~\ref{cmd:entitlements}.

\subsection{\texttt{COMPILER = \$cmd} \label{cmd:compiler}}

Sets the command used to compile to \texttt{\$cmd}, replacing whatever
the language would otherwise have run.  Where a
\texttt{CROSS\_COMPILE} says which machine something is being built
for and lets the language work out what to run, this says what to run
and leaves the rest alone -- so it's the one to reach for when a
toolchain isn't named the way a toolchain usually is, or when the
compiler is a wrapper script of your own.

Like \texttt{COMPILEOPTS} (see Section~\ref{cmd:compileopts}) it
applies to whatever \pconfigure\ is in the middle of:

When \pconfigure\ has a current source, only that source is compiled
with \texttt{\$cmd}.

When \pconfigure\ has no current source but a current target, every
source linked into that target -- both the ones written down and the
ones found -- is compiled with \texttt{\$cmd}.  The exception is a
source found behind a header that some other language compiles, like
a \texttt{.c++} behind a C program's header: \texttt{\$cmd} was said to
the target's language, so that source is compiled with its own
language's compiler instead (see Section~\ref{lang:cxx}).  A
\texttt{CROSS\_COMPILE} on the target still applies to it.

When \pconfigure\ has no current source or target, every source built
with the current language is compiled with \texttt{\$cmd}.

When \pconfigure\ has no current source, target, or language then a
fatal error is thrown.

An object file is named after what built it, so two targets that share
a source but not a compiler get an object file each rather than
fighting over one.

\subsection{\texttt{LINKER = \$cmd}}

\texttt{LINKER} is just like \texttt{COMPILER}, but it sets the
command used to link instead of the command used to compile.  See
Section~\ref{cmd:compiler}.  Setting it on a static archive is a
fatal error, since an archive is put together by \texttt{ar} rather
than linked (see Section~\ref{cmd:libraries}); one written above
every target is still fine in a project that builds one.

\subsection{\texttt{PHC = \$path} \label{cmd:phc}}

Sets the header compiler --- the program that installs a
\texttt{HEADERS} target, which really just copies the file (see
Section~\ref{prog:phc}).  It defaults to the \texttt{phc} that was
installed alongside the running \pconfigure, named by its absolute
path so that the tool matching the \pconfigure\ writing the
\texttt{Makefile} is the one that runs.

Like \texttt{CROSS\_COMPILE} this lands on whatever context is open,
so a subproject inherits it from whoever pulled it in until it says
otherwise.  \texttt{--phc} (see Section~\ref{cl:phc}) sets it for the
whole project from the command line.

Each header is also copied into place while \pconfigure\ runs, so
that what includes it can be scanned, and that copy runs the header
compiler.  A \texttt{PHC} that names a program that can't be found or
run is therefore an error at configure time, and the message names the
\texttt{PHC} line or the \texttt{--phc} that chose it.

\subsection{\texttt{PREFIX = \$prefix}}

Sets the \texttt{\$PREFIX} variable to \$prefix.

This works in the same manner as the \texttt{--prefix=\$prefix}
argument to GNU's toolchain does: it changes the directory in which
built files are expected to be installed.  There's no support for
things like \texttt{--bin-prefix}, instead binaries are installed to
\texttt{\$PREFIX/\$BINDIR}.  This keeps things consistant between the
installed image and the build directory's image.

The prefix has to be an absolute path with no whitespace in it, and a
\texttt{Configfile} line that writes anything else is an error.  It is
compiled into every program as \texttt{\_\_PCONFIGURE\_\_PREFIX} and
\texttt{\_\_PCONFIGURE\_\_LIBEXEC} and linked into installed ones as
the run-time library search path, so a relative prefix would be looked
up from whatever directory the program was started in; and it is
pasted unquoted into compile lines and install recipes, where a space
splits it in two.  For the same reason a prefix can't have any of the
characters \texttt{make} or the shell read specially in it ---
\texttt{:}, \texttt{\#}, \texttt{=}, \texttt{\$}, \texttt{\%},
a backslash or a quote among them --- since it is part of the name of
every file \texttt{make install} writes.  Repeated slashes and a trailing one are dropped, so
\texttt{/opt/thing/} and \texttt{/opt//thing} mean exactly what
\texttt{/opt/thing} does; a prefix of \texttt{/} on its own is kept,
and installs to \texttt{/bin} and \texttt{/lib} rather than
\texttt{//bin} and \texttt{//lib}.

A subproject (Section~\ref{cmd:subprojects}) installs into the prefix
of the project that pulled it in, as that prefix stood at the
\texttt{SUBPROJECTS} line --- a subproject is read where its line is
--- unless its own \texttt{Configfile} sets one, at the top or on a
single target.  A program is installed with a run-time search path
under its own prefix, so a \texttt{PREFIX} below a subproject that was
already read, which would put the program somewhere other than where
that subproject's libraries install, would leave it unable to find
them.  That is an error naming the line, the subproject and the
library, wherever the line is: at the top of the \texttt{Configfile} or
under a single target.  Set the prefix above the first
\texttt{SUBPROJECTS} or \texttt{BOOTSTRAP}, or give the subproject the
same \texttt{PREFIX} in its own \texttt{Configfile}.

What is compared is where each library really installs, in the
subproject and in every subproject under it, and only a library still
on the prefix the subproject was handed counts: that is the library
the line would have reached had it been written above.  A
\texttt{PREFIX} that changes nothing is accepted, and so is one below a
subproject that installs no library, that only pulls in others, or
whose libraries were each given a \texttt{PREFIX} of their own --
those install in the same place wherever the line is written.

Note that it's probably not sane to have \texttt{PREFIX} in the middle
of a \texttt{Configfile}.  See Section~\ref{err::prefix} for more
information.

\subsection{\texttt{LIBDIR = \$val}}

Sets the \texttt{LIBDIR} variable to \texttt{\$val}.  By default it is
set to \texttt{lib}.

It may not start with a \texttt{-}, which the \texttt{mkdir} in front
of every library copied there would read as an option.  Writing
\texttt{./-lib} does not help, because \texttt{make} takes the
\texttt{./} back off the name of each library before its recipe runs,
so \pconfigure\ refuses both spellings; pick a directory with another
name.

A target is linked with its \texttt{LIBDIR} on the library search
path, which is how a \texttt{DEPLIBS} finds a library this build
produced without anybody having to say where it came out.  A
\texttt{LIBDIR} that nothing in the project builds into is left off:
the directory is never created, and a linker asked to search one that
isn't there warns about it.

The \texttt{LIBDIR} is searched ahead of any directory a
\texttt{LINKOPTS} adds with \texttt{-L}, so a library this project
builds wins over one of the same name somewhere else --- typically an
older copy of it that a previous install left in a directory
\texttt{pkg-config} points at.

\subsection{\texttt{HDRDIR = \$val}}

Sets the \texttt{HDRDIR} variable to \texttt{\$val}.  By default it is
set to \texttt{include}.

\subsection{\texttt{SRCDIR = \$val}}

Sets the \texttt{SRCDIR} variable to \texttt{\$val}.  By default it is
set to \texttt{src}.

A \texttt{SRCDIR} starting with a \texttt{-} is refused, because every
source path starts with it and a compiler reads \texttt{-src/main.c}
as an option rather than a file.  A directory that really is called
\texttt{-src} is written \texttt{SRCDIR = ./-src}, which keeps its
\texttt{./} all the way to the compile line.

\subsection{\texttt{STRICT = \$version} \label{cmd:strict}}

Says how much of what \pconfigure\ used to let a project get away with
it should still let this one get away with.  \texttt{\$version} is a
\pconfigure\ version, and every warning that existed as of that
version becomes a hard error:

\begin{verbatim}
STRICT = v0.13
\end{verbatim}

A handful of \texttt{Configfile} lines are accepted and then quietly
do something nobody meant; they're listed in Section~\ref{warn}.  None
of them can simply be made errors, because every one of them is
something some project is relying on without knowing it and a build
system that stops building last week's project isn't much of a build
system.  So they're warnings: the message goes to \texttt{stderr},
\pconfigure\ carries on, and the \texttt{Makefile} that comes out is
the one that would have come out anyway.

\begin{verbatim}
./Configfile:5 'COMPAT = 1.0'
  warning: COMPAT is read and then thrown away -- it has never done anything
  delete the line; a project that wants to say which pconfigure it was written against wants STRICT
  ('STRICT = v0.13' makes this an error)
\end{verbatim}

A project that would rather be told loudly writes the \texttt{STRICT}
line, and the same message comes out saying \texttt{error} where it
said \texttt{warning}, followed by the version that did it and where
that was asked for -- the \texttt{Configfile} and line of the
\texttt{STRICT}, or the command line for a \texttt{--strict}:

\begin{verbatim}
./Configfile:5 'COMPAT = 1.0'
  error: COMPAT is read and then thrown away -- it has never done anything
  delete the line; a project that wants to say which pconfigure it was written against wants STRICT
  ('STRICT = v0.13' at ./Configfile:1 is what makes this an error)
\end{verbatim}

Nothing else changes about it, and \pconfigure\ stops there rather than writing a
\texttt{Makefile}: a warning that a project has asked to be an error
is an error, and half a \texttt{Makefile} is worse than none.

The default is \texttt{v0.12}, the release these were first written
down in, which promotes nothing at all.  That's the whole
compatibility story from here on.  Each warning carries the version it
was added in, so asking for a version asks for everything found up to
that point and nothing found since: a project pinned at
\texttt{v0.13} keeps building when \texttt{v0.14} finds a new edge
case, and hears about that one as a warning like everybody else until
it decides to move the number.

A version is written the way a release is written, and read the way a
person writes it: the leading \texttt{v} is optional and a component
that isn't there is zero, so \texttt{v0.13}, \texttt{0.13} and
\texttt{v0.13.0} are one version, and \texttt{v0.12.1} is a version
too.  Anything older than \texttt{v0.12} is \texttt{v0.12}, since
there was never a \pconfigure\ that behaved differently and asking for
one is asking for the oldest behavior there is.

Anything that isn't a version at all -- \texttt{banana},
\texttt{v0..1}, \texttt{v1.2.3.4} -- is a fatal error that names the
line, rather than a warning.  This is the one command that can't
afford to be wrong quietly: a misspelled \texttt{STRICT} that got
ignored would turn every warning below it back off, which is the
opposite of what the line was written to do.

Like \texttt{CROSS\_COMPILE} (see Section~\ref{cmd:cross_compile})
this lands on whatever context is open rather than on the current
language, so a project pulled in by a \texttt{SUBPROJECTS} (see
Section~\ref{cmd:subprojects}) inherits it the same way it inherits a
\texttt{PREFIX}, and a subproject that isn't ready for it writes its
own \texttt{STRICT} to relax back -- somebody else's tree is somebody
else's tree.  The place to write it is the top of a
\texttt{Configfile} even so, since a warning is about a line rather
than about a target and the line could be anywhere.

It can also be given on the command line, see
Section~\ref{cl:strict}.

\subsection{\texttt{CONFIG += \$file} \label{cmd:config}}

When \texttt{Configfiles/\$file} exists and is executable, the output
of that executable is treted as a \texttt{Configfile} and used as
input for \pconfigure.  When the executable terminates,
\pconfigure\ resumes parsing the current file at the next line.

When \texttt{Configfiles/\$file} exists and is not executable, that
file is parsed as a \texttt{Configfile} and used as the input for
\pconfigure.  When the executable terminates, \pconfigure\ resumes
parsing the current file at the next line.  This is effectively C's
\texttt{\#include} but for \pconfigure.

The same goes for \texttt{Configfile.\$file}, which is read after
\texttt{Configfiles/\$file} when both exist.  Either one is enough on
its own, but when neither exists a fatal error occurs, naming the line
that wrote the \texttt{CONFIG}: a misspelled name would otherwise read
nothing at all and leave out everything the file was meant to declare.
This is also true of a \texttt{--config} on the command line.

A file that exists but can't be read, or that is a directory, is a
fatal error too, naming the file along with the line that wrote the
\texttt{CONFIG}, or the \texttt{--config} option when it came from the
command line.

A \texttt{CONFIG} that names a file whose lines are still being read
--- a file that names itself, two files that name each other, or
\texttt{CONFIG += ../Configfile} from the top-level \texttt{Configfile}
--- would read its own line again and never finish, so it is a fatal
error at that line, listing the \texttt{CONFIG} lines that led there.

A \texttt{CONFIG} that names a file already read, whether by an earlier
\texttt{CONFIG} or as one of the files every project reads, reads it
again, just as a second \texttt{\#include} would.  Since that declares
everything in the file a second time it is a warning at the repeated
line, naming the earlier one, and an error under \texttt{STRICT = v0.13}
(Section~\ref{cmd:strict}).  The same goes for a \texttt{--config}
option, which is read before any \texttt{Configfile}: naming one of
the files every project reads, such as \texttt{--config main}, reads
it a second time when its own turn comes, and is warned about at the
option.  Several \texttt{--config} options stand side by side, each
read in turn, so one naming a file another also \texttt{CONFIG}s is a
repeat and never a cycle.

\subsection{\texttt{CONFIG\_DEPS += \$path} \label{cmd:config_deps}}

Names something the configuration reads that is not itself a
\texttt{Configfile}, so that changing it re-runs \pconfigure\ under
\texttt{AUTORECONFIGURE} (Section~\ref{cmd:autoreconfigure}).

The case it exists for is an executable \texttt{CONFIG}
(Section~\ref{cmd:config}) that enumerates a directory --- one that
globs a directory of tests and prints a \texttt{TESTSRC} line for each
file it finds.  \pconfigure\ watches every \texttt{Configfile} a run
looked for lines in, and the directory is not one of them: nothing in
it is a \texttt{Configfile}, so nothing opens it, so it never reaches
that list.  Adding a file to it therefore changes nothing the build is
watching, and the build goes on using a \texttt{Makefile} written
before the file existed.

A directory is the useful thing to name, because a directory's
modification time moves when an entry is added or removed and for
nothing else, which is exactly the event an enumeration cares about.  A
file may be named too, though it is less interesting: a file can
already say that it changed, while nothing but a directory can say
that something appeared next to it.

A relative path is relative to the project whose \texttt{Configfile}
the line was in, the same as a \texttt{CONFIG}.  An absolute path ---
a tool or a \texttt{pkg-config} file outside the tree --- is watched
exactly where it names.  Either way it goes through the same
\texttt{\$(wildcard)} as every other name in that rule --- so naming
something that does not exist yet is allowed rather than fatal, and it
is noticed the day it appears.  It is not read: everything else in that
list got there by being opened for lines, and a directory has none.

Both of these mean the same thing, and are the same line by the time
\pconfigure\ parses them:
\begin{verbatim}
CONFIG      += tests
CONFIG_DEPS += test/suite
\end{verbatim}
and, inside the executable \texttt{Configfiles/tests} itself,
\begin{verbatim}
echo "CONFIG_DEPS += test/suite"
\end{verbatim}
The second is worth preferring: it keeps the dependency next to the
glob it describes, where whoever changes one is already looking at the
other.

A file that a vendored tree in the same build installs --- one named
by a \texttt{SUBPROJECT\_TARGETS} (Section~\ref{cmd:subproject_targets}),
like the \texttt{llvm-config} a \texttt{CONFIG} asks for LLVM's flags
--- is the exception to the \texttt{\$(wildcard)}.  It is written as a
plain prerequisite, so \texttt{make} builds the tool before it decides
whether to reconfigure, and the first build of a fresh tree configures
against the tool it is about to build rather than against whatever the
\texttt{CONFIG} found in its absence.  A file \pconfigure\ itself
links keeps the \texttt{\$(wildcard)}: \texttt{make} remakes the
\texttt{Makefile} before it has read the dependency fragments that say
what such a file is linked out of, so it is noticed once it exists and
not built from there.

Without \texttt{AUTORECONFIGURE} only a project that keeps its own
committed \texttt{Makefile} beside the generated one --- a
\texttt{BOOTSTRAP} project (Section~\ref{cmd:bootstrap}) --- gets the
prerequisite, and its committed \texttt{Makefile} supplies the recipe
(Section~\ref{cmd:autoreconfigure}), so a file appearing in the named
directory reconfigures it.  Only the \texttt{CONFIG\_DEPS} paths are
named there, not the \texttt{Configfile}s, which stay unwatched without
\texttt{AUTORECONFIGURE}.  A project with no committed \texttt{Makefile}
gets no prerequisite at all: with no recipe it could never reconfigure,
and \texttt{make} would still remake whatever the line names before
looking at the goal, so \texttt{make clean} or \texttt{make -n} would
rebuild a binary or a vendored tree the line points at.

\subsection{\texttt{TESTSRC += \$name} \label{cmd:testsrc}}

This is just a macro that generates
\begin{verbatim}
TESTS   += $name
SOURCES += $name
\end{verbatim}

The test is named by the same path its source is, so
\texttt{t.bash} and \texttt{./t.bash} are one test and run once.

\texttt{TESTSRC[\$suite]} generates \texttt{TESTS[\$suite]} and a
plain \texttt{SOURCES}, since a test suite is a thing tests are in
rather than a thing source files are in.

\subsection{\texttt{HEADERSRC += \$name} \label{cmd:headersrc}}

This is just a macro that generates
\begin{verbatim}
HEADERS += $name
SOURCES += $name
\end{verbatim}
which installs \texttt{\$SRCDIR/\$name} as
\texttt{\$PREFIX/\$HDRDIR/\$name} --- the case where a header is
installed under the name it already has.  It stands in the same
relation to \texttt{HEADERS} that \texttt{TESTSRC} stands in to
\texttt{TESTS}.

A \texttt{HEADERSRC} may be written above or below the targets whose
sources read the copy: like a \texttt{GENERATE}, every one is copied
before \pconfigure\ looks through any source for the headers it
includes, so the dependency on the copy is found either way.

The copy is build output: it is written over whenever its source is
newer, and \texttt{make distclean} removes it (see
Section~\ref{make:distclean}).  So a \texttt{HEADERSRC}, or a
\texttt{HEADERS} with a \texttt{SOURCES} under it, is refused when
its copy would land on a file that isn't one.  That is the source
itself, as with \texttt{SRCDIR = include}, where the source and the
copy are one path; and it is a file already in \texttt{HDRDIR} that
nothing in this build made --- one with no record of its recipe in
\texttt{OBJDIR} from an earlier configure, and that doesn't say
exactly what its source says.  \texttt{make clean} removes that
record along with the copy, so a header written into \texttt{HDRDIR}
after a clean is one nothing vouches for.  A copy whose record was
lost, as when \texttt{OBJDIR} is deleted after its source was edited,
can't be told apart from a header somebody wrote and is refused too;
deleting the copy and configuring again is the fix for that one.  A
header that is meant to be installed from where it already is wants a
\texttt{HEADERS} with nothing under it instead
(Section~\ref{cmd:headers}).

\subsection{\texttt{GENERATE += \$name.proc}}

Allows for the generation of arbitrary targets.  The file
\texttt{\$name} will be generated somewhere in \texttt{\$OBJDIR}.
Some languages (C and C++, for example) will place this directory in
the global include path, but the exact semantics are defined by the
language.  Every \texttt{GENERATE} output is placed in one directory
shared by the whole project, rather than with any one target, so a
source anywhere in the project can include it.  A \texttt{GENERATE}
may be written above or below the targets that read its output:
\pconfigure\ generates every \texttt{GENERATE} before it looks
through any source for the headers it includes, so the dependency on
the generated file is found either way.  Writing one below a target
is what lets that target be the tool the script runs.

The output is named by the path \texttt{\$name} reaches rather than by
how the line spelled it, so \texttt{GENERATE += ./gen.h} writes the
same \texttt{gen.h} that a source's \texttt{\#include "gen.h"} finds,
and that source is rebuilt when it is regenerated.

\texttt{\$SRCDIR/\$name.proc} is expected to be an executable that has
two calling formats:

Either call is made from the top of the project that owns the script,
rather than from wherever \pconfigure\ or \texttt{make} happens to be
standing, so a script in a subproject reads and prints the same paths
whether the build was started there or in a parent that pulled it in.
With \texttt{--srcpath} (see Section~\ref{cl:srcpath}) or a
\texttt{SRCPATH} that top is the top of the source tree rather than
the build directory, so a script reads the files beside it and a
project generates the same way built in place or out of it.

Calling \texttt{\$SRCDIR\$name.proc --deps} prints out the
dependencies of \texttt{\$name} to \texttt{/dev/stdout}.  It's up to
the user to keep this dependency list complete and to ensure that all
these dependencies are eventually handled by \pconfigure.  Everything
it prints is named relative to the project the script belongs to,
which is also the directory it was run from.
Whitespace separates paths, as it does in a \texttt{make} prerequisite
list, so a line may name several of them and a blank line names none.
Each relative path is rooted in the script's project one at a time,
and an absolute path is left as written, so a script declares the same
inputs whether its project is built on its own or as a subproject.
Before that each path is tidied the way \texttt{make} would need it
spelled to match the rule that builds it: a run of slashes becomes one,
a \texttt{.} component is dropped, and a component followed by
\texttt{..} is dropped along with it, so \texttt{./obj/proc/a.h} and
\texttt{src/../obj/proc/a.h} both name the generated
\texttt{obj/proc/a.h}.  The tidying is purely by name and never
reaches through a symbolic link, a component is only dropped when
something follows it, and a \texttt{..} that climbs out of the
directory the path started in is left as written.
A \texttt{\#}, a \texttt{\$} or a \texttt{:} in a path is spelled
for \texttt{make} on the way into the \texttt{Makefile}, so it names
the file the script printed.  A \texttt{;} cannot be: on a rule line
it starts a recipe, and \texttt{make} has no spelling for one that is
part of a file name.  A script that prints one is refused, by
\pconfigure\ naming the \texttt{GENERATE} line or, when the answer
changes after a configure, by the build, and the input has to be
renamed.

A line whose first character is a \texttt{?} names an \emph{optional}
dependency: an input the script reads when it is there and does without
when it is not, which is the shape of a script that asks whether some
toolchain or other generated tree exists yet.  The \texttt{?} is not
part of the path, whitespace between the two is a separator rather than
part of the path, and the path may contain \texttt{make}'s glob
characters.  An input that is genuinely required should still be named
without the \texttt{?}, so that a build missing it says so rather than
generating something quietly wrong.

What makes an input mandatory is that the script names it \emph{now}.
The build asks the script again whenever the script or a directory its
answer named changes, so a script that globs a directory and stops
naming a file once it is deleted needs no reconfigure: the next
\texttt{make} regenerates the output from what is left.  A file the
script still names and that is not there stops the build with
\texttt{make}'s ``No rule to make target'', however long ago
\pconfigure\ was run.

\pconfigure\ records such a line as a glob filtered by
\texttt{\$(realpath ...)} rather than naming it outright, which is what
makes both halves work.  While the file is absent the glob expands to
nothing, so the line is not the hard error that an absent prerequisite
no rule builds would be.  Once the file appears \texttt{make} treats it
as an ordinary prerequisite --- a file nothing in the \texttt{Makefile}
knows how to build but which is nonetheless there is, to \texttt{make},
simply up to date --- so it joins the graph with no reconfigure.  The
\texttt{\$(realpath ...)} is what covers a \emph{dangling symlink}:
a glob answers out of the directory listing rather than by stat, so
without the filter a link whose target is gone is reported as present
and \texttt{make} is handed a prerequisite it can neither stat nor
build.  That is the very hard error the glob was chosen to avoid, and
it stops every target in the tree rather than just the generated one.

One thing the \texttt{?} deliberately does not promise is that an
optional input which \emph{arrives} regenerates the output.  What
\texttt{make} promises for an ordinary prerequisite is that a
\emph{newer} one regenerates the target, and that is all the
\texttt{?} inherits: an input that lands older than the output it should
have fed leaves that output stale, and \texttt{make} exits 0 saying
there was nothing to be done.  This state cannot arise for a mandatory
input, where an absent prerequisite is a hard error and so there is no
earlier output for a late arrival to be older than; the \texttt{?}
creates it by making absence legal.  It is reachable in practice and not
only in principle, because \texttt{tar} restores mtimes --- a prebuilt
toolchain unpacked into a watched directory arrives carrying whatever
timestamps the machine that rolled the tarball had.  The recovery is a
\texttt{touch} of the arrived file, not a reconfigure: the file really is
on the rule, and only its timestamp is wrong.  Closing the limitation
instead of documenting it would mean beating mtime, which is all
\texttt{make} has to go on, and so would mean a check that runs on every
\texttt{make} whether or not anything moved.  That price was measured.
Hanging the dependency fragment's rule off a \texttt{FORCE} does not
merely cost time: the fragment is \emph{included}, so \texttt{make}
remakes it, re-executes, finds it out of date again and re-executes
again, and the build never finishes --- 1818 \texttt{--deps} runs in the
twenty seconds before the measurement was killed.  Spelling it
carefully, so that the recipe keeps the existing fragment when the
answer has not changed and \texttt{make} therefore has no reason to
re-execute, does terminate, and costs one \texttt{--deps} subprocess per
generated file per \texttt{make}: a no-op \texttt{make} in a tree with
one generated file went from 1.7 ms to 13 ms.  That is paid by every
incremental build in order to catch a backdated arrival, and the trade
has not been made --- but it is a trade and not an impossibility, and
the numbers are recorded here so that it can be made without being
re-derived.

Calling \texttt{\$SRCDIR\$name.proc --generate} prints the generated
file to \texttt{/dev/stdout}.  Note that \pconfigure\ may call this
when \pconfigure\ is run in addition to when \texttt{make} is run, as
opposed to \texttt{--deps} which will only be called when
\pconfigure\ is run (and never when \texttt{make} is run).  This means
it's possible that the script will be run before its dependencies are
ready, so plan accordingly!

\pconfigure\ runs it when \texttt{make} would: when there is no output
yet, or when the script or any input its \texttt{--deps} answer names
is newer than the output there is --- and, as below, when the output
was written by a different script.  That is what makes rerunning
\pconfigure\ after editing a script enough on its own.  The headers a
generated file includes are read off the output on disk, to work out
what a program links and what its objects depend on, so an output left
over from before the edit would answer those questions for the old
script.  An output that is up to date is left alone, and the script is
not run.

What the script prints is compared against the file already on disk, and
the output is replaced only when the two differ.  A regeneration whose
answer is the bytes that were already there therefore leaves the
output's mtime exactly where it was, and nothing downstream of it is
rebuilt.  That matters because a script whose answer is a function of
its inputs' \emph{content} has inputs whose mtime can move without their
content moving --- a cache repacked, a lock file rewritten, an archive
unpacked over itself --- and \texttt{make} cannot tell any of those from
an edit.  Measured in the tree \pconfigure\ is vendored into: a stamp
holding a submodule's revision is declared against that submodule's
\texttt{HEAD}, branch ref and \texttt{packed-refs}, \texttt{git
pack-refs} rewrites \texttt{packed-refs} for a revision that did not
move, and what hung off the stamp was a conformance suite measured in
hours.

The cost of that is paid in the other direction, and it is worth
planning for: such a rule no longer \emph{settles}.  The output stays
older than the prerequisite that was touched, so \texttt{make} asks
again on the next build and on every build after it, and the script runs
each time until something actually changes its answer.  A script that is
expensive \emph{and} insensitive to its inputs' timestamps will
therefore run on every \texttt{make} once one of those inputs has been
rewritten in place.  This is the only trade available: mtime is all
\texttt{make} has, and one file cannot be newer than its prerequisites
while staying older than its consumers.  It is made this way round
because what it buys back is bounded by the cost of the consumers rather
than of the script.

Which script writes the output is the \texttt{Configfile}'s to say,
and changing it --- a \texttt{GENERATE} turned into a
\texttt{TGENERATE}, or moved under a different \texttt{SRCDIR} ---
regenerates the output on the next \pconfigure\ run, even though the
new script is older than the output the old one wrote.  The new script's
answer goes through the same comparison as any other, so one that
prints what the old one did leaves the output, and everything built
from it, alone.

Beside \texttt{\$name} \pconfigure\ keeps a few files of its own, all
named after it: \texttt{\$name.tmp}, which the output is written
through before it is moved into place, \texttt{\$name.recipe-inputs},
which records the recipe that wrote it, and \texttt{\$name.d},
\texttt{\$name.d.raw}, \texttt{\$name.d.tmp},
\texttt{\$name.d-context} and \texttt{\$name.d.answer}, which hold
and record the dependency fragment that keeps \texttt{--deps} current
during the build.  No
other \texttt{GENERATE} in the project may have one of those as its
output, since the two would then be fighting over one file: a
\texttt{GENERATE += gen.h.d} next to a \texttt{GENERATE += gen.h} is
refused, at whichever of the two lines comes second, naming the other.
A name that merely ends the same way --- \texttt{rules.d} with no
\texttt{rules} beside it --- is fine.

Nor may one of those files, or the output itself, need another's path
to be a directory: \texttt{GENERATE += sub/x.h} needs \texttt{sub} in
the generated-files directory to be a directory, so a
\texttt{GENERATE += sub} beside it is refused, and so is a
\texttt{GENERATE += gen.h.d/inner.h} beside a \texttt{GENERATE +=
gen.h}, whose dependency fragment is \texttt{gen.h.d}.  Again it is
the second of the two lines that is refused, naming the first.  Names
that only start the same way --- \texttt{sub.h} or \texttt{sub-x.h}
next to \texttt{sub/x.h} --- are fine.

A \texttt{\$name} may have a directory in it, which carries over to
both the script and its output.  \texttt{GENERATE += sub/gen.h} calls
\texttt{\$SRCDIR/sub/gen.h.proc} in the two ways above and writes its
output to a \texttt{sub} directory inside the generated-files
directory, which \pconfigure\ makes, so that the source asking for it
includes it as \texttt{"sub/gen.h"} --- the same spelling it would use
for a header of its own in that directory.

The \texttt{\$name} has to end in a file name, since it names both the
output and the script.  One that ends as a directory ---
\texttt{gen.h/}, \texttt{sub/.} or \texttt{sub/..}, or \texttt{.}
itself --- is refused at its line rather than having its trailing
\texttt{/} dropped the way a target's is: the script is something
you wrote, and guessing which one a directory was meant to name could
only send you looking for the wrong file.

\subsection{\texttt{TGENERATE += \$name}}

Exactly the same as \texttt{GENERATE}, but runs
\texttt{test/\$name.proc} instead of \texttt{\$SRCDIR/\$name.proc}:
a generator that exists only to build a fixture for the tests can live
next to them rather than among the program's sources.  The
\texttt{test} directory is the one of the project the line is in, so a
\texttt{TGENERATE} in a subproject looks in that subproject's
\texttt{test}.  Everything else is \texttt{GENERATE}'s: where the output
is written, the two calling formats, and that the script is run from
the top of its project --- so the paths its \texttt{--deps} prints and
the files it reads are spelled from there, \texttt{test/} included.

\section{Source File Directives \label{directive}}

A source file can say something to \pconfigure\ about itself, on a
line that begins \texttt{\#pconfigure} and carries a command:

\begin{verbatim}
#pconfigure TESTDEPS += testexec/mkfs
\end{verbatim}

This is the same shape as the \texttt{\#include} that \texttt{pbashc}
expands (see Section~\ref{lang:bash}): a statement about the file it
is written in, read by whatever is building that file.  It is read out
of whatever the file includes as well, which is where it belongs once
several tests share the code that needs the thing --- the helper knows
what it needs, and a test that pulls the helper in gets the dependency
along with the code it came for.

\subsection{What can be written in one}

A \texttt{TESTDEPS} (see Section~\ref{cmd:testdeps}), and nothing
else.  Anything else a \texttt{Configfile} can say is about a target
rather than about one of its tests, and what a directive would put it
on is the one test whose source it was read from --- so it is a fatal
error rather than a line that means something different depending on
where it was written.

\texttt{\$path} is spelled exactly the way the \texttt{Configfile}
spells it: from the top of the project, rather than from the test's
own directory.  Where a project builds a program is not a question
about which of its tests is doing the asking, so the answer had better
not depend on where the test happens to live.  Everything
Section~\ref{cmd:testdeps} says about what a \texttt{TESTDEPS} may
name holds here too, including that it may not climb out of the
project.

\subsection{Where one may be written}

In the source of a test --- a file a \texttt{TESTS} or a
\texttt{TESTSRC} named (see Sections~\ref{cmd:tests}
and~\ref{cmd:testsrc}), or a file that one of those includes.  Nothing
else is read for directives: a program's sources are about the
program, and a \texttt{TESTDEPS} found in one would have to land on
every test of the target, which is what writing it in the
\texttt{Configfile} already does.

In practice that means the tests written in \texttt{bash} or
\texttt{perl} (see Section~\ref{lang:bash}).  The \texttt{\#} has to
be in the first column with \texttt{pconfigure} written against it,
which is the one spelling a shell script can use --- a \texttt{\#}
anywhere else on a line of shell starts a comment --- and it is not a
line a C compiler would accept at all.

That last point is worth writing down, because it is also how a
directive gets written by accident.  A note about \pconfigure\ at the
top of a test, with no space after the \texttt{\#}, is a directive;
\pconfigure\ says so, and says to put the space in.

A test whose source BASH or Perl claims is read for its directives
the way \texttt{pbashc} and \texttt{pperlc} read it, a line at a
time with none of C's comments or backslash-newlines, so a glob ending
in \texttt{/*} or Perl's \texttt{//} hides nothing below it.  Any
other test is read as C, and a directive inside one of its comments is
commented out like the rest of the comment.

A directive is read whether or not \texttt{AUTODEPS} (see
Section~\ref{cmd:autodeps}) is on.  \texttt{AUTODEPS} turns off the
dependencies \pconfigure\ works out for itself, and a directive is
not one of those: it is a line somebody wrote down on purpose.

\section{Supported Languages \label{lang}}

A number of \pconfigure\ specifics are determined

\subsection{\texttt{asm}: Assembly}

This is almost exactly the same as C (see Section~\ref{lang:c}),
except that it expects source files are called \texttt{*.S} and that
it compiles using \texttt{cc -xassembly}.

It's expected that \texttt{cc} accepts the same command-line arguments
as GCC does.  Note that a wrapper for \texttt{nasm} is provided that
adapts it to use the GCC command-line arguments.  See
Section~\ref{prog:pnasm} for more information.

\texttt{asm} supports linking against C.

\subsection{\texttt{bash}: BASH (\texttt{pbashc} compiler) \label{lang:bash}}

This uses \texttt{pbashc}, a dummy BASH compiler to build BASH code.
See Section~\ref{prog:pbashc} for more information.  BASH parses
\texttt{pbashc} \texttt{\#include} directives to discover a list of
implicit dependencies, searching the \texttt{-I} directories in its
\texttt{COMPILEOPTS} the way \texttt{pbashc} does.  Under
\texttt{AUTORECONFIGURE} that list is worked out by the build rather
than by \pconfigure\ (see Section~\ref{cmd:autoreconfigure}).  A relative one a
subproject names is written from that subproject's own directory and
gets the subproject's directory put on the front, just as it does for
C (see Section~\ref{cmd:compileopts}).  A test written in BASH is also the one place a
\texttt{\#pconfigure} directive (see Section~\ref{directive}) can be
written, since a \texttt{\#} against the first column is a line the
shell reads as a comment and every other language reads as something
it does not understand.

A \texttt{BASH} target is compiled from exactly one \texttt{SOURCES},
since \texttt{pbashc} takes one input and that file is the whole
program.  A second \texttt{SOURCES} under the same target is a fatal
error naming its line.  The way to make two files into one script is
to \texttt{\#include} the second from the first, which \texttt{pbashc}
expands and the dependency scan follows; the error says which
\texttt{\#include} to write, spelled from the first file's directory,
which is where \texttt{pbashc} looks a quoted name up first.  The same
file listed twice is refused too, with a message saying to delete the
repeated line.

The files a script includes become prerequisites of what it is
compiled into under the names the \texttt{\#include} gave them, spelled
so that \texttt{make} reads each back as one file: \texttt{\#include
"my helper.bash"} is a file with a space in its name, the way
\texttt{pbashc} reads it.  The same handful of characters a C header
can't have (see Section~\ref{lang:c}) can't be in an included file's
name either, and one that has one is a fatal error at the script's
\texttt{SOURCES} line.

\texttt{bash} supports linking against BASH.

\subsection{\texttt{c}: C \label{lang:c}}

This is the canonical language.  Implicit dependency resolution is
handled by parsing C proprocessor macrcos to discover a list of
\texttt{\#include}ed files.  This list is then mapped to the source
files that implement those headers, which are then recursively added.
C and C++ share their headers, so what is found next to one can be
either (see Section~\ref{lang:cxx}).

The directives are read the way the compiler reads them, including the
ones it only warns about.  A directive may be spelled with the
\texttt{\%:} digraph in place of its \texttt{\#}, as in
\texttt{\%:include "extra.h"}, and a UTF-8 byte order mark at the very
start of a file is skipped, as \texttt{gcc} and \texttt{clang} skip
it; the same bytes anywhere else are part of the line they are on.
Neither is true of a script, which \texttt{pbashc} reads with a
\texttt{\#} in the first column or not at all.  An \texttt{\#ifdef}
or \texttt{\#ifndef} asks about the identifier it starts with, so
\texttt{\#ifdef VERBOSE(x)} is a question about \texttt{VERBOSE}, and
anything written after an \texttt{\#else} or \texttt{\#endif} is
passed over.  An \texttt{\#elif} chain takes the first branch whose
test holds, and C23's \texttt{\#elifdef NAME} and \texttt{\#elifndef
NAME} are branches of it like any other, read as \texttt{\#elif
defined(NAME)} and \texttt{\#elif !defined(NAME)}.  The
names that start out defined are the ones the target's
\texttt{COMPILEOPTS} hand the compiler, with every \texttt{-D} and
\texttt{-U} taken in the order the compiler takes them: a target
whose \texttt{-UTRACE} follows a \texttt{-DTRACE} from its
language's \texttt{COMPILEOPTS} has \texttt{TRACE} undefined, both
to the compiler and to the scan.  A
computed include, \texttt{\#include NAME} with \texttt{NAME} a macro
naming the header, is passed over too: what the scan keeps is which
names are defined, not what they are defined as, so it has no way of
knowing which header that is.  That costs two things.  The header is
not a prerequisite of the object, so an edit to it alone rebuilds
nothing.  And the source that implements it is never found, since that
is found through the header, so unless something else brings it in the
project configures without complaint and then fails to link.  Including
the header by name as well, somewhere the scan reads, fixes both.
Listing the source behind it in \texttt{SOURCES} fixes only the link:
the header is still not a prerequisite.

A header becomes a prerequisite under the name the scan found it by,
which is whatever the \texttt{\#include} said and wherever the
\texttt{-I} directories led, and it is spelled so that \texttt{make}
reads it back as that one file.  A header called \texttt{my extra.h},
\texttt{notes\#1.h}, \texttt{ver:1.h} or \texttt{v\$1.h}, or one found
through \texttt{-I/opt/my\textbackslash\ dir/include} --- which is how
\texttt{pkg-config} spells a directory with a space in it --- builds,
and an edit to it rebuilds what reads it, with or without
\texttt{AUTORECONFIGURE}.  A few characters have no spelling on a
\texttt{make} rule line at all: a \texttt{;}, an \texttt{=}, a
\texttt{|}, a tab and a newline.  A header with one of those in its
name is a fatal error at the \texttt{SOURCES} line for the file that
reads it, since nothing in the \texttt{Configfile} names the header
itself; under \texttt{AUTORECONFIGURE} it is \texttt{pdeps} that says
so, while the build runs, naming the two files.

The source found behind a header is held to more than the header,
because it is built: its name goes everywhere a \texttt{SOURCES}
line's does, on the left of rules and bare into the compile recipe.
So it can't have any of the characters a \texttt{SOURCES} name can't
(see Section~\ref{cmd:make-special}), nor whitespace, and one that
does is a fatal error naming the header and the source, even where the
header alone would have built.  Renaming the source fixes it, and so
does \texttt{AUTODEPS = false} when the source was never meant to be
built into the target.

C is compiled and linked by \texttt{\$\{CC\}}, C++ by
\texttt{\$\{CXX\}}, and static libraries of either are archived by
\texttt{\$\{AR\}}, so the toolchain is picked when \texttt{make}
runs: \texttt{make CC=clang} builds with \texttt{clang}.  The
generated \texttt{Makefile} gives them defaults of \texttt{cc},
\texttt{c++} and \texttt{ar} with \texttt{?=}, which only matter
when \texttt{make}'s own built-in variables are gone -- under
\texttt{make -R}, or below a parent build with \texttt{-R} in its
\texttt{MAKEFLAGS}, as kbuild has.  A value from the command line or
the environment still wins.  A \texttt{CROSS\_COMPILE} replaces all
three (see Section~\ref{cmd:cross_compile}).

A source is C when it is called \texttt{.c}.

C supports linking against C.

\subsection{\texttt{chisel}: Chisel C++ Backend \label{chisel}}

This language builds a set of Scala files, runs them to procude some
C++ code, and then builds that C++ code into an object.  Additionally,
the generated header file is added to all the other C++ files built.
This means that your Chisel code has to come before your C++ code in
the \texttt{Configfile}.

Chisel implicit dependency detection works in the same manner as Scala
(see Section~\ref{lang:scala}): an entire directory of files is built
and linked together.

Note that specificying a library that ends in \texttt{.so} will
generate a Chisel library from the generated C++ code, but specifying
a library that ends in \texttt{.jar} will generate a Scala library
directly.

The Chisel C++ backend supports linking against C (for binaries and
C++ libraries), and against Scala (for Scala libraries).

What chisel builds is a Verilog file, elaborated from the Scala and
copied into the library directory under the target's name, so it
builds only a \texttt{LIBRARIES}; a \texttt{BINARIES} made of Scala
is refused, naming its line.  There is no link step, so a
\texttt{LINKOPTS} is refused too.  Its \texttt{COMPILEOPTS} go to its
phases rather than to a compiler: \texttt{-W<phase>,<arg>} sends one
argument to the phase called \texttt{compile} or \texttt{rtl} (in
either case), and \texttt{-Wdriver,<arg>} sends it to all of them.
\texttt{-Wrtl,-top,<name>} names the top module the RTL phase
elaborates.  Any other option, or a phase that doesn't exist, is
refused naming the line of the target it landed on.

\subsection{\texttt{c++}: C++ \label{lang:cxx}}

C++ is almost exactly the same as C, except that a wider set of file
extensions is supported and that the code is compiled and linked with
\texttt{c++} instead of \texttt{cc}.

A source is C++ when it is called \texttt{.c++}, \texttt{.cpp},
\texttt{.cxx}, \texttt{.cc}, or \texttt{.C}.  \texttt{.c} is
deliberately not in that list: it belongs to C (see
Section~\ref{lang:c}), and keeping it out is the whole of what stops
the two languages from both claiming the same file.  Which of the
other spellings a project picked is its own business and none of them
mean anything different here.

A header is C or C++ when it is called \texttt{.h++}, \texttt{.hpp},
\texttt{.hxx}, \texttt{.hh}, or \texttt{.h}.  That list is what the
search for the source behind a header runs through: a header and the
source that implements it are the same name with a different ending,
and nobody ever writes down that the two go together.  Every source
that exists is built, so a project keeping both a \texttt{foo.c} and a
\texttt{foo.c++} next to \texttt{foo.h} gets both.

What is found is compiled by the target's own language when that
language can compile it, and otherwise as whatever its own name says.
C++ can compile C, so a \texttt{.c} behind a header a C++ program
reads is compiled as C++, with C++'s compiler and options: that is
what lets one C source be built a second time into a C++ library
whose header wraps the same declarations in a namespace.  C can't
compile C++, so a \texttt{.c++} behind a C program's header is
compiled as C++, with C++'s compiler and the options given to C++.
A \texttt{COMPILER} written on the C program was said to C and isn't
used for it, though the program's \texttt{CROSS\_COMPILE} is.
That takes C++ being in the project's \texttt{LANGUAGES}; when it
isn't, the target's own language compiles the file, there being
nothing else to hand it to.  The order of
the \texttt{LANGUAGES} lines has nothing to do with it, because no
other language claims these endings: SWIG is built on C++, but only
its \texttt{.i} files are its own.  The target is
still linked by its own language, so a C program whose header is
implemented in C++ links without the C++ runtime unless it asks for
it.

Chisel implicit dependency detection works in the same manner as Scala
(see Section~\ref{lang:scala}): an entire directory of files is built
and linked together.

C++ supports linking against C.

\subsection{\texttt{flo}: Chisel Flo Backend}

This language is almost exactly the same as the Chisel C++ language
(see Section~\ref{chisel}) but it generates Flo code instead of C++
code.

The Flo backend supports linking against Flo.

\subsection{\texttt{h}: C/C++ Header}

This is a simple dummy language that just copies header files for
installation.  The headers it recognizes are the ones C++ recognizes:
\texttt{.h++}, \texttt{.hpp}, \texttt{.hxx}, \texttt{.hh}, and
\texttt{.h}.  See Section~\ref{lang:cxx}.

A \texttt{HEADERS} is installed from exactly one \texttt{SOURCES}, as
a \texttt{BASH} target is, and a second one is a fatal error naming
its line.  Unlike \texttt{pbashc}, the header compiler is a plain copy
that leaves \texttt{\#include} alone, so a header that includes
another does not bring it along: each header to be installed needs a
\texttt{HEADERS} of its own.

Headers support linking against headers.

\subsection{\texttt{perl}: Perl (\texttt{pperlc} compiler)}

This is almost exactly the same as the BASH language (see
Section~\ref{lang:bash}, but it compiles Perl instead by using
\texttt{pperlc} (see Section~\ref{prog:pperlc}).
Like a \texttt{BASH} target, a perl target takes exactly one
\texttt{SOURCES}, and a second is refused with the \texttt{\#include}
to write instead.

Perl supports linking against perl.

\subsection{\texttt{pkgconfig}: \texttt{pkg-config}}

This generates \texttt{pkg-config} files by passing them through
\texttt{sed} a number of times.  There's a few rules:

\begin{itemize}
\item Most \pconfigure\ variables are availiable under the format
  \texttt{@@pconfigure\_VARIABLE@@}
\item Passing \texttt{-Sscript} as a compile option runs \texttt{sed}
  with the contents of that file as an argument
\item Passing any other string simply runs \texttt{sed} with that as
  an argument
\end{itemize}

Either way it is a single argument, holding exactly what was written:
spaces, quotes and a \texttt{\$} reach \texttt{sed} as they are,
without the shell splitting them or \texttt{make} expanding them.
The one exception is an option that starts with a backtick, which is
a command for the shell to run, and whose output is split into
arguments the way the shell would split it.

Note that one \texttt{sed} process is run for each argument provided
as a compile option.

Each \texttt{.pc} --- in the tree, and under the prefix for
\texttt{make install} --- is built up in files beside its target and
only moved into place once every \texttt{sed} has worked.  A rule
whose \texttt{sed} fails leaves no \texttt{.pc} behind, empty or
otherwise, and none of those intermediate files either, so the next
\texttt{make} tries again rather than taking a leftover file for a
finished one.

The template is the target's one \texttt{SOURCES}; a \texttt{-S}
script is only ever run over it, never used in its place.  A second
\texttt{SOURCES} is a fatal error naming its line, since a
\texttt{pkg-config} file has no \texttt{\#include} to bring it in:
put its contents into the first, or give it a \texttt{LIBRARIES} of
its own.  A target with no \texttt{SOURCES} gets the usual warning,
and its rules then fail when \texttt{make} reaches them rather than
writing out an empty \texttt{.pc}.

The values \pconfigure\ substitutes itself ---
\texttt{@@pconfigure\_prefix@@}, \texttt{@@pconfigure\_libdir@@} and
\texttt{@@pconfigure\_hdrdir@@} --- are written into the file as
\texttt{pkg-config} values rather than as bare text, which matters for
the copy that describes the build tree: its prefix is the absolute path
of the checkout, and that is whatever directory somebody chose.  A
space, a \texttt{\#}, a quote or a backslash in it gets a backslash in
front, the way \texttt{pkg-config} spells those inside a value, so
\texttt{/home/me/my checkout} is written
\texttt{/home/me/my\textbackslash\ checkout} and comes back out of
\texttt{ppkg-config} as one flag.  A \texttt{.pc} that pastes one of
these into something other than a path --- a \texttt{Description},
say --- shows the backslashes too.  Characters only \texttt{sed} cares
about, such as \texttt{\&} and \texttt{\^{}}, are passed through as
themselves.

The prefix, the options and the template are all part of how a
\texttt{.pc} is built, so changing any of them in the
\texttt{Configfile} rebuilds it on the next \texttt{make}, and the
next \texttt{make install} replaces the installed copy, the same as
editing the template or a \texttt{-S} script does.  A reconfigure
that changes none of them rebuilds nothing.

pkgconfig supports linking against pkgconfig.

\subsection{\texttt{scala}: Scala \label{lang:scala}}

The Scala language uses \texttt{pscalac} (see
Section~\ref{prog:pscalac}) and \texttt{pscalald} (see
Section~\ref{prog:pscalald}) to build Scala in a manner that's mostly
compatible with a UNIX-style C toolchain.

Implicit dependency handling in the Scala language is handled by
assuming that whole directory subtrees are all interdependent and by
allowing the Scala compiler to handle all build dependencies.  For example, passing
\begin{verbatim}
BINARIES += target
SOURCES += dir/file.scala
\end{verbatim}
will include every scala file listed by \texttt{find \$SRCNAME/dir
  -iname *.scala} in \texttt{target}.  Note that this behavior leads
to some added complexity and should be eventually fixed, but it'll be
tough because it's hard to parse Scala code in a timely fashion.

Scala supports linking against scala.

\section{Supported Build Systems \label{buildsys}}

These are the build systems that \texttt{BUILD\_SYSTEMS}
(Section~\ref{cmd:build_systems}) can make available to a
\texttt{SUBPROJECTS}, along with what each one looks for when it is
deciding whether a directory is its kind of tree and which
\texttt{CONFIGUREOPTS} it understands.

\subsection{Where a vendored tree installs \label{buildsys:prefix}}

Four of the build systems below install what they built, and all
four ask the same thing of the directory they are pointed at,
whatever they spell the option --- a \texttt{--prefix} for
\texttt{autotools}, \texttt{cmake} and \texttt{meson}, an
\texttt{--install} for \texttt{cargo}.  An install prefix is a directory \emph{inside the
object directory of the project that vendored the tree}, named
relative to that project.  Anything else is a fatal error, and it
quotes back the line that wrote the prefix --- even a prefix written
after a \texttt{BUILD\_SYSTEMS}, which cannot be checked until a
\texttt{SUBPROJECTS} gives it a project to be inside.

Half of that is the rule every path a \texttt{Configfile} writes keeps
to.  \pconfigure\ works in paths relative to the directory it ran in,
and which directory that is depends on whether a project was
configured on its own or pulled in by a parent.  A path that stays
inside the project names the same directory either way, because the
\texttt{Makefile} names it through that project's own prefix variable
and that variable is what changes between the two runs.  A path that
climbs out has nothing for that variable to attach to, so it quietly
names two different directories --- and which of them it names depends
on who ran \pconfigure, which is not something the line says.

The other half is the object directory, and it is there because that
is the one directory a build owns outright.  What is under it is build
output and nothing else: no checked-in file, no other project, no
vendored tree.  So \texttt{make distclean} removes every install
prefix by removing the object directory, without naming one or knowing
that any exist, and \texttt{make cache-clean}
(Section~\ref{make:cache_clean}) can be handed the prefixes and told
to leave them alone.

That second target is why this is enforced rather than merely
suggested.  \texttt{make cache-clean} reclaims everything in the
object directory that the \texttt{Makefile}
has stopped naming as a target, and what a vendored tree installs is
exactly that: the tree's rules all hang off one stamp, so the headers,
the libraries and the programs that land in the prefix have no rules
at all --- only the files a \texttt{SUBPROJECT\_TARGETS} named outright
get one.  A prefix cache-clean could not be told about is therefore a
toolchain deleted underneath a stamp that still says the tree is
installed, so no later \texttt{make} puts any of it back, and the
first thing to fail is a compile against a header that was there
yesterday.

Two kinds of directory inside the object directory are refused as
well, which is the same sentence one level down.  The object directory
itself is one: cache-clean spares a prefix whole, so a prefix that is
the whole of \texttt{\$obj\_dir} is a cache-clean that reclaims
nothing at all and says nothing about it, since it still runs and
still finishes.  The other is anywhere \pconfigure\ writes into
itself --- \texttt{\$obj\_dir/src} and the rest of the directories the
objects, the programs and a \texttt{GENERATE}'s output land in --- for
the same arithmetic.  Owning every byte of the object directory is
what lets a prefix be in there; it is not the same as having none of
it spoken for.

So \texttt{obj/toolchain} is the shape of a prefix, while
\texttt{/usr/local}, \texttt{../staging}, \texttt{obj} and
\texttt{obj/src} are each refused, with a diagnostic that says which
of these it fell foul of.  A \texttt{Configfile} that says nothing
gets a default prefix of that tree's own, inside that tree's own
output directory; each subsection below says what its default is.

Pointing several trees at one prefix is the usual reason to write the
option at all --- a toolchain is found by looking one \texttt{bin} up
--- and is meant to work.  They install into it concurrently under a
\texttt{make -j} and nothing serializes them, since the files each of
them writes are its own.  What two of them may not do is claim the
same file: two \texttt{SUBPROJECT\_TARGETS} naming one path in a
shared prefix is a fatal error, because only one tree can be the one
that builds it.  Sharing does change what may be deleted, though, so a
prefix somebody wrote down is treated more carefully than a default
one --- a peer may be living in it, and a peer whose stamp says it is
built will not install again.  Each subsection below says what its own
rules do with the directory.

\subsection{Saying it a second time \label{buildsys:second_answer}}

A vendored tree is run with a command line \pconfigure\ composed, and
three questions are settled before any \texttt{CONFIGUREOPTS} is read:
which tree is being configured, where it builds, and where what it
builds is installed --- which for a tree that installs nothing is
settled by there being nowhere.  A \texttt{CONFIGUREOPTS} or a
\texttt{MAKEOPS} that answers one of them a second time is refused
while the \texttt{Configfile} is being read, rather than composed
onto the same command line: which of the two answers the tree obeyed
would then be decided by the order \pconfigure\ happens to write them
in, which is not something the \texttt{Configfile} says.

For the two directories that is the whole of the reason, and what it
buys is a build directory this project can still find and a tree that
is the one a \texttt{SUBPROJECTS} named.  For the install there is
more at stake, because the install of a vendored tree runs during
\texttt{make} rather than during \texttt{make install}: a destination
this build system did not decide is a plain \texttt{make} writing
wherever that line pointed, and \texttt{/usr/local} is one character
away.

Every channel that reaches the tree is asked the same question, so a
name refused in one of them is refused in all: the flags and the
variables handed to the tree's own configuration, the variables a
\texttt{--make-var} or a \texttt{MAKEOPS} puts on the
sub-\texttt{make}'s command line, the \texttt{--target} that goes on
that same command line --- where \texttt{make} reads a word with an
\texttt{=} in it as a variable rather than as a goal --- and the
environment an \texttt{--env} writes.  What is asked is every
whitespace-separated word of the option rather than the first, since
an option that reaches the tree as written can be several arguments;
and the shell's quoting is taken off a word before it is looked at,
since such an option is read by the shell before the tree ever sees
it.  A name \texttt{make}
works out rather than one written down --- \texttt{-D\$(WHATEVER)=1}
--- is refused for being a name nothing here can read.

The names are the tree's own, so each build system knows its own list:

\begin{itemize}
\item \texttt{autotools} refuses \texttt{prefix},
  \texttt{exec\_prefix} and \texttt{DESTDIR}, which say where the
  whole install goes; the directory variables the GNU coding standards
  define --- \texttt{bindir}, \texttt{libdir}, \texttt{mandir} and the
  rest of that list --- which say where part of it goes; and
  \texttt{srcdir}, which says which tree gets configured.  Each of
  them in every spelling a generated \texttt{configure} reads: the
  \texttt{--bindir=DIR} flag, the single-dash \texttt{-bindir=DIR},
  the bare \texttt{bindir=DIR} variable, the two-word \texttt{--bindir
  DIR}, and the truncations autoconf writes out for every option it
  takes, so that \texttt{--pre=} is \texttt{--prefix=} and
  \texttt{--bi=} is \texttt{--bindir=}.  A \texttt{-} inside one of
  these names is the \texttt{\_} of the variable it sets, since
  \texttt{--exec-prefix} and \texttt{exec\_prefix} are one thing.

\item \texttt{cmake} refuses \texttt{CMAKE\_INSTALL\_PREFIX},
  \texttt{CMAKE\_STAGING\_PREFIX} and \texttt{DESTDIR}, along with
  cmake's own \texttt{--install-prefix}, which is the first of those
  spelled as an option; the \texttt{GNUInstallDirs} variables ---
  \texttt{CMAKE\_INSTALL\_BINDIR}, \texttt{CMAKE\_INSTALL\_LIBDIR}
  and the rest of that module's list; and the \texttt{-B} and
  \texttt{-S} that say where the tree builds and which tree gets
  configured.  Written as a \texttt{-D} with or without its
  \texttt{:TYPE}, as a bare \texttt{NAME=VALUE}, or as the \texttt{-U}
  that deletes a cache variable --- which is the one worth spelling
  out, since a \texttt{-U} of the prefix takes back the one this build
  system wrote and leaves cmake's own default, and cmake's own default
  is \texttt{/usr/local}.

\item \texttt{kconfig} refuses the kbuild variables that say where an
  install of the tree lands: \texttt{INSTALL\_MOD\_PATH},
  \texttt{MODLIB}, \texttt{INSTALL\_PATH}, \texttt{INSTALL\_HDR\_PATH}
  and \texttt{INSTALL\_DTBS\_PATH}, plus \texttt{DESTDIR}, and the
  \texttt{O} and \texttt{KBUILD\_OUTPUT} that say where the tree
  builds.  \texttt{buildroot} inherits those and adds its own; see
  Section~\ref{buildsys:buildroot}.  Neither of them has an option
  that says where an install goes, because neither installs anything
  unless a \texttt{--target} asks it to, so what the refusal says is
  that there is no other spelling to write instead.

\item \texttt{cargo} asks the same question in its own words, since
  nothing it reads is a decorated \texttt{NAME=VALUE}: what says where
  it installs takes the next word, and its one-letter flags cluster.
  Section~\ref{buildsys:cargo} says what an \texttt{--arg} and an
  \texttt{--env} may not say there.

\item \texttt{meson} refuses \texttt{prefix}, \texttt{DESTDIR} and
  \texttt{destdir}, and meson's directory options ---
  \texttt{bindir}, \texttt{libdir} and the rest --- by value, the way
  \texttt{cmake} refuses its \texttt{GNUInstallDirs} variables.
  Written as a \texttt{-D}, as a bare \texttt{NAME=VALUE}, or as a
  \texttt{--} option, shortened or not, since meson's command line
  takes any unambiguous prefix of a long option as the option.  See
  Section~\ref{buildsys:meson}.
\end{itemize}

Where part of an install goes is refused by name for
\texttt{autotools} and by value for \texttt{cmake}, and the difference
is what the two trees do with a relative one.  cmake joins a relative
\texttt{GNUInstallDirs} value to \texttt{CMAKE\_INSTALL\_PREFIX}, so
it cannot name anything outside the prefix and there is no reason to
refuse it: \texttt{--define CMAKE\_INSTALL\_LIBDIR=lib/mine} is a tree
told to use the layout this project reads.  What counts as relative
there is an ordinary relative path and nothing else --- one that
starts at the root, one with a \texttt{..} in it, and one carrying a
character \texttt{make} or the shell would act on before cmake read it
are each a value nothing out here can say stays inside.  An autotools
tree's own \texttt{make} reads a relative one from the directory it
builds in rather than from the prefix, so ``under the prefix'' is not
a thing that spelling can say there, and all of them are refused.

A name that is not on a build system's list is a name \pconfigure\ has
no opinion about.  The lists are written out rather than matched by
shape because there is no shape that tells these apart:
\texttt{--sbindir} says where a program lands and
\texttt{--with-sysroot} does not, and from a distance they are the
same word.  Nor does any of this read what the vendored tree itself
says --- an absolute \texttt{DESTINATION} in a
\texttt{CMakeLists.txt}, a toolchain file that sets a staging prefix,
a \texttt{CMakePresets.json}.  Each of those is the tree saying where
it installs, in the tree.  This is about a second answer written in a
\texttt{Configfile}, where there is a line to quote back and somebody
to tell.

\subsection{What an option reaches the tree as \label{buildsys:quoting}}

Every value a \texttt{CONFIGUREOPTS} or a \texttt{MAKEOPS} writes is
one word by the time the tree sees it.  It is quoted where it lands in
a recipe, so one option is one thing however many spaces, semicolons
or asterisks are in the middle of it: one argument to
\texttt{configure} or to cmake, one variable on a sub-\texttt{make}'s
command line, one target, one defconfig goal, one \texttt{.config}
option name and one \texttt{.config} value, one argument to cargo.  A
\texttt{--define LLVM\_ENABLE\_PROJECTS=clang;lld} is therefore one
cmake list of two rather than a cmake run followed by an attempt to
run a program called \texttt{lld}.

The quoting is the shell's and not \texttt{make}'s, which is the half
that has to go on working: \texttt{make} expands a recipe before any
shell reads it, so \texttt{\$(abspath x)} and \texttt{\$(PATH)} inside
one of these still mean what they say --- note \texttt{\$(PATH)} and
not \texttt{\$PATH}, since \texttt{make} reads a lone \texttt{\$} as
naming a one-character variable.  Nothing takes a value apart.

Four things reach a recipe unquoted, and that is the whole of the
list:

\begin{itemize}
\item The name in front of the \texttt{=} of an \texttt{--env}, in
  every build system that has one.  It has to be bare: a shell reads
  \texttt{NAME=VALUE cmd} as an assignment in front of a command, and
  the same text quoted whole stops being an assignment and becomes the
  name of a program nobody has.  So what a shell counts as a name is
  enforced where the line was written --- a letter or a
  \texttt{\_}, then letters, digits and \texttt{\_} --- rather than
  left to fail in the middle of a build, or not to fail at all on a
  machine that happens to have a program of that name.  The value
  after the \texttt{=} is quoted like everything else.

\item A cmake or meson \texttt{--configure-arg}, deliberately: it is
  written the way it will appear on the tree's command line, so
  somebody who needs two arguments writes two words and somebody who
  needs one word with a space in it writes the quotes themselves.
  That is also why every word of one is asked about rather than the
  first, and why the quoting comes off before it is asked
  (Section~\ref{buildsys:second_answer}).

\item The command an autotools \texttt{--autoreconf} names, which is a
  command line rather than a word: it is run inside the tree as it was
  written, so \texttt{--autoreconf autoreconf -i} is a program and a
  flag rather than a program with a space in its name.

\item A \texttt{--jobs}, for \texttt{cmake} and for \texttt{cargo}.
  It is digits all the way through or it was refused where it was
  written, so there is nothing left in it for a shell to find.
\end{itemize}

The two of those written as free text, a \texttt{--configure-arg} and
an \texttt{--autoreconf}, have to be quoting a shell can read to the
end, and are refused where they were written when they are not: a
single or double quote that never closes, which would be a recipe
every \texttt{make} stops at with ``unexpected EOF'', or a backslash
with nothing after it, which would escape the space the recipe puts
after it and glue the next argument on.  A quote or backslash meant
for the tree itself is escaped, as it would be typed at a shell.

And one thing that is not a quoting question at all.  A path an option
names becomes a prerequisite in the generated \texttt{Makefile} --- a
\texttt{--depend}, a \texttt{--merge-config}, a
\texttt{SUBPROJECT\_TARGETS} --- and a prerequisite is a word of
\texttt{make} rather than a word of shell, which has no quoting for
one.  So a path written in a \texttt{Configfile} may not have a space
in it, and may not be a \texttt{make} expansion: either is refused
where it was written rather than split in half somewhere downstream,
where nothing is left to say which line caused it.  A quote or another
shell metacharacter in a path is Section~\ref{odd:quoting}.

\subsection{\texttt{pconfigure}: \texttt{pconfigure} Itself
\label{buildsys:pconfigure}}

Recognizes a directory with a \texttt{Configfile} or a
\texttt{Configfiles/main} in it, and is the build system a
subproject gets when nothing else is going on.  Every project has
this one available without asking, and it is always asked first.

It is also the only one that isn't run as a build system at all: a
\texttt{pconfigure} subproject is read into this run and built out of
its own contexts, which is what Section~\ref{cmd:subprojects}
describes.  It takes no \texttt{CONFIGUREOPTS}, since a
\texttt{pconfigure} project is configured by its own
\texttt{Configfile}.

\subsection{\texttt{kconfig}: Linux's Build System \label{buildsys:kconfig}}

Linux's build system, and everything else that copied it: a
configuration that comes out of \texttt{Kconfig} files, and a build
that comes out of \texttt{Makefile}s that read that configuration.
It recognizes a directory with a \texttt{Kconfig} in it alongside a
\texttt{Makefile} or a \texttt{Kbuild}, which is what such a tree
looks like from outside.

Two rules come out of this.  The first produces a \texttt{.config},
by running the tree's own \texttt{defconfig} target and then setting
whatever options were asked for on top of it.  The second runs the
tree's own \texttt{make} against that configuration.  Both build into
\texttt{\$obj\_dir/\$dirname/build} in the project that pulled
the tree in, using an out-of-tree build (\texttt{O=}), so the vendored
tree itself is never written to.  The \texttt{build} on the end is
where the tree is handed its \texttt{O=}, which makes it the tree's:
what \pconfigure\ keeps for itself --- the stamp, and the record of
what the tree was configured with --- sits in
\texttt{\$obj\_dir/\$dirname} beside it rather than in there
with the tree's own output.

The options are:

\begin{itemize}
\item \texttt{--defconfig \$name} picks the \texttt{make} target that
  produces the starting configuration.  This is a target rather than
  a filename because that is how these trees spell it:
  \texttt{x86\_64\_defconfig}, not
  \texttt{arch/x86/configs/x86\_64\_defconfig}.  It defaults to
  \texttt{defconfig}.

\item \texttt{--configure \$option=\$value} sets one option on top of
  that defconfig, using the tree's own \texttt{scripts/config}, and
  then re-runs \texttt{olddefconfig} so that whatever the option
  turned on gets its dependencies filled in.  A \texttt{\$value} of
  \texttt{y}, \texttt{m} or \texttt{n} means what it means in a
  \texttt{.config}; a \texttt{\$value} written with quotes around it
  is a string, and goes in with the quotes back on; anything else is
  used as the option's value.  Later options win, so the order they
  are given in matters.  A value with no \texttt{=} in it, or with
  nothing in front of the \texttt{=}, is a fatal error: the tree's
  \texttt{scripts/config} would turn \texttt{--configure =y} into a
  \texttt{CONFIG\_=y} that Kconfig throws away.  \texttt{\$option}
  may be written with or without its \texttt{CONFIG\_}, as
  \texttt{scripts/config} takes either.

\item \texttt{--merge-config \$file} merges a configuration fragment
  on top of that defconfig, using the tree's own
  \texttt{scripts/kconfig/merge\_config.sh}, and then re-runs
  \texttt{olddefconfig}.  Merging is not appending: a fragment that
  sets an option the base file already set has to replace it rather
  than be read twice, and working out which lines those are is a job
  for the tree's own program the same way editing one is.  This is
  the option to reach for when the configuration you want is already
  written down, rather than transcribing a fragment into a wall of
  \texttt{--configure} lines and keeping the two in step forever.

  \texttt{\$file} is named relative to the project that asks for it,
  not to the vendored tree, because a fragment is that project's own
  statement about how it wants somebody else's tree built.  A
  fragment that does live inside the tree is named through it:
  \texttt{--merge-config linux/arch/arm64/configs/virt.config}.  Any
  fragment named this way is a prerequisite of the
  \texttt{.config}, so changing one re-configures.  Fragments are
  merged before any \texttt{--configure} is set, on the grounds that
  the more specific statement should get the last word.

\item \texttt{--make-var \$name=\$value} puts a variable on the
  sub-\texttt{make}'s command line, where it beats whatever the
  tree's own \texttt{Makefile} has to say about it.  This is how a
  tree gets told something it never asked to be told:
  \texttt{--make-var ARCH=arm64}.

  This is the same thing \texttt{MAKEOPS} (see
  Section~\ref{cmd:makeops}) says, spelled the way the options are.
  The two share one list and one order, so whichever of them was
  written last is the one \texttt{make} hears last.

\item \texttt{--env \$name=\$value} puts a variable in the environment
  the tree is built in, where the tree's own \texttt{Makefile} is
  allowed to disagree with it.  That difference is the whole reason
  both options exist, and it is the difference you want for a
  \texttt{PATH}: \texttt{--env
  PATH=/opt/homebrew/opt/coreutils/libexec/gnubin:\$(PATH)}, to put
  the GNU tools a kbuild-derived tree expects in front of the BSD
  ones macOS ships.

  Either of these reaches the generated \texttt{Makefile} spelled
  exactly the way it was written, so \texttt{\$(abspath tests/x)} and
  \texttt{\$(PATH)} mean what they say and are worked out by
  \texttt{make}.  Note that this is \texttt{\$(PATH)} and not
  \texttt{\$PATH}: \texttt{make} reads a lone \texttt{\$} as naming a
  one-character variable.  Both apply to every invocation of the
  tree -- the defconfig, the \texttt{olddefconfig} and the build --
  because a tree told \texttt{ARCH=} for two of the three writes a
  configuration for one machine and then builds for another.

\item \texttt{--target \$name} asks the tree for a target rather than
  for whatever it builds when it is asked for nothing.  May be given
  more than once, in which case they are asked for one at a time in
  the order they were written: \texttt{make -j} handed several goals
  is allowed to run them at once, and neither \texttt{kbuild} nor
  anything that copied it is safe against that at the top of the
  tree.  A \texttt{\$name} with an \texttt{=} in it is a variable on
  \texttt{make}'s command line rather than a goal, and one with nothing
  in front of the \texttt{=} is a fatal error.

\item \texttt{--depend \$path} names something the tree has to wait
  for, and \texttt{--depend-config \$path} names something only its
  configuration has to wait for.  \texttt{\$path} is relative to the
  project that names it, and is either a file, or the directory of
  another vendored subproject of the same project -- in which case
  the wait is for that tree to have been built, rather than for its
  directory to change.

  A \texttt{--depend} is waited for by the configuration as well as by
  the build.  Configuring a \texttt{kbuild} tree is a sub-make of that
  tree with the project's \texttt{CROSS\_COMPILE} on its command line,
  and \texttt{Kconfig} asks the compiler what it can do while it is
  working out what the \texttt{.config} says -- so a kernel whose
  toolchain this build produces needs that toolchain before it can be
  configured, not just before it can be compiled.  Hanging it off the
  build alone is how a fresh checkout ends up needing two passes of
  \texttt{make}, the first of which writes down the answers
  \texttt{Kconfig} gives when it cannot run a compiler at all.  A
  \texttt{--depend-config} reaches the build for the same reason from
  the other direction: the build already waits for the configuration.

  Both exist because nothing else can find these edges.  Every other
  dependency between two things \pconfigure\ builds comes from
  reading a command line, and a vendored tree has no command line to
  read: it says nothing about what it reads outside itself, and
  nothing at all about another vendored tree.  So a kernel that can't
  be built until a \texttt{buildroot} has produced a toolchain says
  \texttt{--depend buildroot}, and a root filesystem that has to be
  rebuilt when a file of your own outside the tree changes says
  \texttt{--depend \$that\_file}.  Without them, \texttt{make -j}
  races.

  A \texttt{pconfigure} subproject can't be named this way: it has no
  one file that says it has been built, so name the file you actually
  need instead.
\end{itemize}

A vendored tree is also told the \texttt{CROSS\_COMPILE} the project
was configured with (see Section~\ref{cmd:cross_compile}), since
\texttt{kbuild} is where that spelling comes from and a project that
has said which machine it is building for has already said this.  A
\texttt{--make-var CROSS\_COMPILE=} of your own overrides that, for a
vendored tree that has to be built with a different toolchain than the
project around it.

Where the tree builds is something this build system has already said
on the sub-\texttt{make}'s command line, and where an install target
of the tree would write is a thing no line of this build says at all,
so a \texttt{--make-var}, a \texttt{MAKEOPS} or an \texttt{--env}
that says either of them is refused while the \texttt{Configfile} is
read --- as is a \texttt{--defconfig} or a \texttt{--target}
carrying one, since a goal on that command line is a word on it like
any other.
Section~\ref{buildsys:second_answer} says which names those are and
why.  Each of the options above reaches the tree as a single word ---
one target, one defconfig goal, one option name, one option value ---
which is Section~\ref{buildsys:quoting}.

Alongside those two rules \pconfigure\ writes a third file, which has
no rule of its own:

\begin{verbatim}
obj/linux/configure-opts
\end{verbatim}

It holds what the tree was configured with: one
\texttt{CONFIGUREOPTS} line per line, exactly as it was written and in
the order it was written, followed by a
\texttt{CROSS\_COMPILE=\$prefix} line for a build system that is told
one.  A \texttt{kconfig} tree's file carries the project's
\texttt{CROSS\_COMPILE} and a \texttt{buildroot} tree's does not, for
the same reason \texttt{buildroot} isn't told it in the first place
(see Section~\ref{buildsys:buildroot}): a tree that has no use for the
prefix this project was configured with has no business being
reconfigured over it.  The file sits beside the tree's output
directory rather than inside it, since that directory is handed to the
vendored tree as its \texttt{O=} and nothing of ours belongs in there.

\pconfigure\ writes it, at configure time, and it is a prerequisite of
the \texttt{.config}.  It has to exist because nothing else here can
do its job: every other prerequisite these two rules have is a file
that belonged to the tree or to the project before \pconfigure\ ran,
and a recipe changing is not a reason for \texttt{make} to run a rule.
So a tree re-configured with different \texttt{CONFIGUREOPTS} would
find every file it depends on exactly as it left it, do nothing, and
sit there configured and built the old way underneath a
\texttt{Makefile} that says otherwise.  This is the one prerequisite
that changes when the answer changes.

It is rewritten only when its contents change, so a \pconfigure\ run
that says the same thing as the last one leaves the mtime where it was
and the vendored tree is not disturbed -- which is the whole point,
since re-running \pconfigure\ is something a build does on its own
whenever a \texttt{Configfile} is touched.  It hangs off the
configuration rather than off the build stamp because the build
already waits for the configuration, so one file covers both; the
price is that an option only the build reads, a \texttt{--target},
reconfigures too, which costs one sub-\texttt{make} of a defconfig
that writes back the file that was already there.

\texttt{make clean} leaves it alone.  It is a prerequisite that
nothing knows how to build, so a \texttt{clean} that removed it would
leave \texttt{make} with no rule to make it and no way forward.
\texttt{make distclean} does remove it, along with the whole object
directory, which is the same thing as never having configured the tree
at all.

The one consequence worth knowing about is the first run after
upgrading: a tree that an older \pconfigure\ configured has no such
file, so writing one gives the \texttt{.config} a prerequisite it has
never seen before and every vendored tree in the build reconfigures
exactly once.

The dependency guess described in Section~\ref{cmd:build_systems}
works by following every \texttt{source} out of a \texttt{Kconfig} and
every \texttt{include} out of a \texttt{Makefile}, treating every word
of every \texttt{Makefile} line as a possible path, and keeping the
ones that name a file that exists.  A word ending in a \texttt{/} is a
directory \texttt{kbuild} descends into, so its \texttt{Makefile},
\texttt{Kbuild} and \texttt{Kconfig} get followed too; a word ending
in \texttt{.o} is an object, so the sources it could have been built
from get picked up.

None of that pays any attention to the conditionals around it: a file
that is only read when some option is set is still a file this
configuration might read tomorrow, and a path a variable made
unreadable -- \texttt{arch/\$(SRCARCH)/Kconfig} -- becomes a glob, on
the grounds that it names a real file for every value that variable
could take.  A \texttt{make} function that just hands back the paths
it was given -- \texttt{sort}, \texttt{wildcard}, \texttt{strip},
\texttt{abspath}, \texttt{realpath} -- is looked through rather than
thrown away, so a whole directory of \texttt{Makefile}s that is
included at once still gets followed.

\subsubsection{What the tree says it read}

The guess is a seed rather than the answer.  A kconfig tree decides
which files it reads by reading them, and it writes down what it read
--- \texttt{kbuild} into
\texttt{include/config/auto.conf.cmd} under its output directory, and
the older writer Buildroot carries into a \texttt{..config.tmp} beside
the \texttt{.config}.  Both hold one assignment with one path a line,
which is a far more rigid thing to read than a \texttt{Kconfig}.

That file exists only once the tree has been configured, so reading it
is a job for the build rather than for \pconfigure.  What does it is
\texttt{psubdeps}, which lives next to \pconfigure\ and is not
something to run by hand: \pconfigure\ writes it a context file at
configure time, and \texttt{psubdeps} turns the tree's list into a
piece of \texttt{Makefile} that the build includes, naming those
files as prerequisites of the \texttt{.config}.

It happens whether or not the project asked for
\texttt{AUTORECONFIGURE} (Section~\ref{cmd:autoreconfigure}).  On a
clean checkout the tree has not said anything yet, so there is no
answer to be had at configure time, and gating this would be choosing
whether to be right rather than when.  A tree that has never been
built gets a fragment saying so, and the same command runs again at
the end of the rules that configure and build the tree --- so the
first \texttt{make} finishes with the fragment already saying what the
tree just said, rather than what it said last time.

Three kinds of path in such a list are dropped.  An absolute one names
nothing on anybody else's machine; one that climbs above the directory
\texttt{make} runs in names nothing either; and one that lands inside
the tree's own output directory is a clock rather than a dependency
--- Buildroot rewrites its \texttt{.br2-external.in.*} every time
\texttt{make} is run, so a rule waiting on one would never be up to
date again.  A path that merely leaves the vendored tree is kept: it
is still somewhere in this build.

\subsubsection{What the tree says its build read}

The same argument one step further along, and a larger hole.  The
guess finds what a tree \emph{compiles} and almost none of what it
\emph{includes}: walking the makefiles of the kernel this manual's
own project vendors names 34,312 prerequisites and 132 headers, out of
the five and a half thousand the compiler actually read.  So editing
\texttt{include/linux/sched.h} left the build up to date, and said
nothing about it --- from \texttt{make}'s side nothing was wrong, the
stamp really was newer than everything it had been told about.

\texttt{kbuild} writes that answer down as it goes.  Beside every
object it compiles it leaves a file naming the source and every header
that was read, in the same shape as the configuration's list, which is
why the same \texttt{psubdeps} reads both.  \pconfigure\ writes it a
second context file at configure time, naming the directory those are
scattered through, and gets back a second fragment --- hung off the
build stamp rather than off the \texttt{.config}.

Two contexts rather than one because they are two answers that arrive
from different places at different times.  The configuration's is one
file written while configuring; the build's is ten thousand files
written while building, and collecting them is a walk of the output
directory.  One fragment would make the rule that wants the cheap
answer pay for the expensive one every time it was asked.

What gets dropped is most of it.  Half those lines name config stamps
the tree keeps for itself, through a \texttt{\$(wildcard)} they are
allowed not to satisfy: whether one of those changed is decided by the
\texttt{.config} the rule already waits on.  The rest are headers the
tree generated into its own output, which is the clock argument again,
and absolute paths outside the directory \texttt{make} runs in, which
belong to a toolchain this build neither builds nor installs.  Nine
million lines come to eleven thousand prerequisites.

The guess stays, and has to.  A tree that has never been built has
written nothing down, so the first build is one the guess has to be
good enough to start --- and it is, because what it does find is the
files that get compiled.  What it was never good enough for is the
second build.  Naming files the tree has already read does not make
anything out of date, since the stamp was written after all of them,
so the fragment appearing for the first time costs one run of
\texttt{psubdeps} and no rebuild.

Only \texttt{kbuild} writes anything of the kind, so only a
\texttt{kconfig} tree is asked.

\subsection{\texttt{buildroot}: Buildroot \label{buildsys:buildroot}}

Buildroot, which builds a whole embedded Linux system out of a
kconfig-derived tree.  It took Kconfig and the shape of
\texttt{kbuild}'s command line from Linux and then spelled almost
everything else differently, so this is the \texttt{kconfig} build
system with the names changed: the top of the configuration is a
\texttt{Config.in} rather than a \texttt{Kconfig}, the program that
edits a \texttt{.config} is \texttt{utils/config} rather than
\texttt{scripts/config}, the one that merges a fragment into a
\texttt{.config} is \texttt{support/kconfig/merge\_config.sh} rather
than \texttt{scripts/kconfig/merge\_config.sh}, and the build
description is a \texttt{.mk} file per package rather than a
\texttt{Makefile} per directory.  It recognizes a directory with a \texttt{Config.in} and a
\texttt{Makefile} in it alongside a \texttt{package} directory of
its own, which is what such a tree looks like from outside.

Everything else is as Section~\ref{buildsys} describes for
\texttt{kconfig}: the same two rules, the same out-of-tree build
(\texttt{O=}) into \texttt{\$obj\_dir/\$dirname}, and the
same dependency guess.  It says what its configuration read and
nothing about what its build read, so it gets the first fragment and
not the second --- and its output directory is not searched for one.
That is not merely tidiness about a tree with nothing to say: a
Buildroot output holds whole source trees of its own, a kernel among
them, so going to look would cost minutes to collect a list that would
then be discarded for belonging to the output.  Every option listed there means what it means
there, and there is one more:

\begin{itemize}
\item \texttt{--external \$dirname} adds a \texttt{BR2\_EXTERNAL}
  tree: a directory of packages, defconfigs and \texttt{Config.in}
  fragments of your own that Buildroot builds alongside the ones it
  came with.  It may be given more than once, and Buildroot searches
  them in the order they were given.  The directory is named relative
  to the project that pulled the subproject in, the same way a
  \texttt{SUBPROJECTS} is, because an external tree is that project's
  own code rather than part of the tree that was vendored.
\end{itemize}

The directory variables Buildroot gives names of its own are refused
on that command line alongside kbuild's, for the reason
Section~\ref{buildsys:second_answer} gives: \texttt{TARGET\_DIR},
\texttt{STAGING\_DIR}, \texttt{HOST\_DIR} and
\texttt{BINARIES\_DIR} for where what it builds is assembled, and
\texttt{BASE\_DIR}, \texttt{BUILD\_DIR}, \texttt{TOPDIR} and the
\texttt{BR2\_EXTERNAL} an \texttt{--external} has already written
for where it builds and which tree gets built.  The download cache,
\texttt{BR2\_DL\_DIR}, is not one of them: it holds nothing the
build produced, and pointing several builds at one of them on purpose
is a thing Buildroot's own manual tells people to do.

An external tree is only ever reached through a variable that names
it, so no amount of reading the vendored tree finds it.  What it holds
is therefore named directly: its \texttt{external.desc},
\texttt{external.mk} and \texttt{Config.in}, and the
\texttt{Config.in} and \texttt{.mk} of every package in it.  Touching
any of those runs Buildroot again, which is what you want from code
that is yours.

Buildroot is also the one kconfig-derived tree that is not told the
project's \texttt{CROSS\_COMPILE}: it builds the toolchain it is going
to use before it builds anything with it, so a prefix naming some
other compiler is at best noise, and Buildroot's own manual says in so
many words not to set it.  Which compiler builds the target is
something its \texttt{.config} says instead.

\subsection{\texttt{autotools}: \texttt{./configure} and \texttt{make}
\label{buildsys:autotools}}

Autoconf, automake and libtool.  They have been spelled a dozen
different ways over thirty years, but the part anybody outside the
tree has to know has never changed --- run \texttt{configure}, run
\texttt{make}, run \texttt{make install} --- and that is the whole of
what this drives.  It recognizes a directory with a \texttt{configure}
in it, or with a \texttt{configure.ac} (or the older
\texttt{configure.in}) that one can be made out of.  Those are the two
states such a tree shows up in: a release tarball ships the generated
\texttt{configure}, and a checkout of the same project usually does
not, because a generated file in version control is a merge conflict
waiting to happen.  Nothing is asked about \texttt{Makefile.am} or
\texttt{Makefile.in}, since which of those a tree has says more about
its vintage than about what has to be done to it.

Four rules come out of this, and the first of them only for a tree
that needs it.

The first makes the tree's own \texttt{configure}, by running whatever
that tree wants run --- see \texttt{--autoreconf} below.  This is the
one thing \pconfigure\ writes inside a vendored tree, and it is the
one thing that cannot be arranged otherwise: autoconf has no
out-of-tree mode and writes \texttt{configure} beside the
\texttt{configure.ac} it was made from.  A tree that ships no
\texttt{configure} has already agreed to that, and its
\texttt{.gitignore} usually says so.  Nothing removes the file
afterwards: \texttt{make clean} takes the stamp and \texttt{make
distclean} takes this project's object directory, and neither of those
is a licence to delete a file out of somebody else's checkout.

The second runs \texttt{configure}, always out of tree.  The build
directory is \texttt{\$obj\_dir/\$dirname/build} in the project that
pulled the tree in, and \texttt{configure} is run from inside it by its
absolute path --- a relative one would make the tree's own
\texttt{srcdir} relative too, and then every generated
\texttt{Makefile} in every subdirectory would be pointing at a
different number of \texttt{..}.  What the rule produces is the
\texttt{config.status} that \texttt{configure} leaves behind, which is
the one file every such tree writes: which \texttt{Makefile}s exist
depends on what the tree's \texttt{AC\_CONFIG\_FILES} asked for.
There is no in-tree fallback, and that is a decision rather than an
omission.  A tree that cannot do \texttt{VPATH} can only be built by
scattering objects, \texttt{Makefile}s and a \texttt{config.status}
through somebody else's checkout, with no way to take them back out
that is not that tree's opinion about what it owns; and two projects
vendoring one such tree would quietly overwrite each other's builds.
A tree that really cannot be built out of tree wants a copy of its
own, which is something the project vendoring it can arrange and this
cannot.

The third runs the tree's \texttt{make}, and then its \texttt{make
install} unless \texttt{--no-install} says otherwise, and writes a
stamp to say it did.  The install is part of building the tree rather
than part of \texttt{make install}, because a tool tree is vendored so
that the rest of this build can run the tool and the rest of this
build happens during \texttt{make} --- putting it on \texttt{make
install} instead would produce a \texttt{make} that looked like it
worked and a build one step further on that could not find the tool.
The fourth is one rule per \texttt{SUBPROJECT\_TARGETS}, which every
build system gets.

The tree's \texttt{make} is a recursive \texttt{\$(MAKE)}, so a
\texttt{make -n} runs it to have it say what it would build, while
only printing the \texttt{configure} line that creates the build
directory.  On a tree that has never been configured, then, there
is no directory for the sub-make to go into.  Under \texttt{-n}, and
only then, the sub-make is skipped when its directory is missing, so
a dry run of a fresh tree prints the \texttt{configure} and the
\texttt{make} it would run and exits successfully.  Once the tree has
been configured, a dry run goes into it as usual.

What is installed goes into \texttt{--prefix}, which defaults to
\texttt{\$obj\_dir/\$dirname/prefix}: beside the build directory
rather than inside it, since the build directory is the tree's and the
tree's own \texttt{make clean} is entitled to an opinion about what is
under it.  Where else it may point is
Section~\ref{buildsys:prefix}.  A \texttt{SUBPROJECT\_TARGETS} is
named relative to the prefix for a tree that installs, and relative to
the build directory for one told \texttt{--no-install}, which is the
tree's last word about what it produced either way: a build directory
is objects and libtool wrappers whose layout is nobody's business but
the tree's, while \texttt{bin}, \texttt{lib} and \texttt{include} is
the one thing an autotools tree really does promise.

The options are:

\begin{itemize}
\item \texttt{--prefix \$dirname} says where the tree installs to,
  named relative to the project that asked for it the same way a
  \texttt{SUBPROJECTS} is: \texttt{--prefix obj/toolchain}.  It
  reaches \texttt{configure} as an absolute path, because autotools
  bakes a prefix into what it builds, from libtool's rpaths to the
  paths a program looks its own data up under.  See
  Section~\ref{buildsys:prefix} for where it may point.

\item \texttt{--configure-flag \$arg} puts one argument on
  \texttt{configure}'s command line, passed on exactly as written:
  \texttt{--configure-flag --enable-foo}.  One option is one argument
  however many spaces are in it, so \texttt{--configure-flag
  --with-solver=z3 --in} asks for a solver whose name has a space in
  it rather than for two things.  A value that does not start with a
  \texttt{-} is a fatal error, on the grounds that it is a
  \texttt{--configure-var} written under the wrong name.

\item \texttt{--configure-var \$name=\$value} puts a variable on
  \texttt{configure}'s command line.  Writing
  \texttt{--configure-var YACC=/opt/bin/bison} is how autoconf is
  told to use a program it would otherwise have gone looking for.  A
  value with no
  \texttt{=} in it is a fatal error, since \texttt{configure} would
  read it as a flag it has never heard of and carry on without it.
  So is one whose \texttt{\$name} is not a shell variable name --- a
  letter or a \texttt{\_}, then letters, digits and \texttt{\_} ---
  since that is the rule a generated \texttt{configure} holds it to,
  and it stops with ``invalid variable name'' on anything else.
  This is spelled apart from \texttt{--configure-flag} because the two
  go wrong in different ways, not because they end up anywhere
  different: they share one command line, in the order they were
  written.

\item \texttt{--make-var \$name=\$value} puts a variable on the
  command line of the \texttt{make} that builds and installs the tree,
  where it beats whatever the tree's own \texttt{Makefile} has to say
  about it: \texttt{--make-var V=1}.  This is the same thing
  \texttt{MAKEOPS} (Section~\ref{cmd:makeops}) says, spelled the way
  the options are; the two share one list and one order.

\item \texttt{--env \$name=\$value} puts a variable in the environment
  the tree is bootstrapped, configured, built and installed in:
  \texttt{--env PATH=/opt/gnubin:\$(PATH)}.  An environment variable
  and a \texttt{--configure-var} are not the same thing, which is why
  both exist: \texttt{configure} records what it was handed on its
  command line into \texttt{config.status} and uses it again on a
  rerun, while something out of the environment is only true for the
  run that saw it.  The value reaches the generated \texttt{Makefile}
  spelled exactly as written, so \texttt{\$(abspath x)} and
  \texttt{\$(PATH)} mean what they say --- note \texttt{\$(PATH)} and
  not \texttt{\$PATH}, since \texttt{make} reads a lone \texttt{\$} as
  naming a one-character variable.  The value is one word however many
  spaces are in it: \texttt{--env CFLAGS=-O2 -g} is one variable with
  two flags in it.  The name in front of the \texttt{=} has to be
  something a shell reads as a variable name, since it is one of the
  few pieces of a \texttt{CONFIGUREOPTS} that reach a recipe unquoted
  --- quoted, it would stop being an assignment and become the name of
  a program nobody has.  Section~\ref{buildsys:quoting} has the rest
  of that list, and says what everything else arrives as.

\item \texttt{--target \$name} asks the tree for a target rather than
  for whatever it builds when it is asked for nothing:
  \texttt{--target hello}.  May be given more than once, in which case
  they are asked for one at a time in the order they were written,
  since \texttt{make -j} handed several goals is allowed to run them
  at once.  A \texttt{\$name} with an \texttt{=} in it is a variable on
  \texttt{make}'s command line rather than a goal, and one with nothing
  in front of the \texttt{=} is a fatal error.

\item \texttt{--install} and \texttt{--no-install} say whether
  \texttt{make install} is part of building the tree.  It is, unless
  it is turned off.  The two are one setting said two ways, so the
  last one written wins.

\item \texttt{--autoreconf \$cmd} says what to run inside the tree to
  make its \texttt{configure}, as in \texttt{--autoreconf
  ./autogen.sh}.  Left off, it is worked out by looking at the tree --- an executable
  \texttt{autogen.sh} or \texttt{bootstrap} is what a tree that has one
  wants run, a tree with a \texttt{Makefile.am}, an
  \texttt{aclocal.m4} or an \texttt{m4} directory wants
  \texttt{autoreconf -i}, and anything else with a
  \texttt{configure.ac} wants plain \texttt{autoconf}, which is also
  the only one of those that works on a machine with no automake on
  it.  A tree with no \texttt{configure.ac} and no
  \texttt{configure.in} has nothing to make a \texttt{configure} out
  of, so nothing is run.

\item \texttt{--no-autoreconf} says that nothing makes it, because the
  tree ships one and the machine doing the building has no autoconf.
  A tree that then turns out to have no \texttt{configure} is a fatal
  error rather than a build that gets halfway.  This and
  \texttt{--autoreconf} are one setting said two ways, so the last one
  written wins --- which is what the arrangement somebody actually
  writes depends on: a \texttt{--no-autoreconf} under the
  \texttt{BUILD\_SYSTEMS}, inherited by every autotools subproject,
  and then an \texttt{--autoreconf} under the one
  \texttt{SUBPROJECTS} that does have to be bootstrapped.

\item \texttt{--depend \$path} names something this tree has to wait
  for: either a file, or the directory of another vendored subproject
  of the same project --- in which case the wait is for that tree to
  have been built rather than for its directory to change.  It is
  waited for by the configuration as well as by the build, since
  \texttt{configure} runs the compiler to find out what it can do, and
  that is most of what it does.  A \texttt{pconfigure} subproject
  cannot be named this way: it has no one file that says it has been
  built, so name the file you actually need instead.
\end{itemize}

Where the tree installs to is one question with one answer, so a
\texttt{CONFIGUREOPTS} that answers it a second time is refused rather
than composed onto the same command line, where which of the two won
would be decided by the order \pconfigure\ happens to write them in.
That covers every spelling: the GNU directory variables ---
\texttt{prefix}, \texttt{exec\_prefix}, \texttt{bindir},
\texttt{libdir}, \texttt{mandir} and the rest of the list the GNU
coding standards define, plus \texttt{DESTDIR} --- said as a
\texttt{--configure-flag}, as a \texttt{--configure-var}, as a
\texttt{--make-var}, as a \texttt{MAKEOPS}, as an \texttt{--env}, or
as a \texttt{--target} --- which is a word on the same
\texttt{make} command line a \texttt{--make-var} is, so that
\texttt{--target DESTDIR=/tmp/x} names no goal and sets a variable
---
and in each of the spellings a generated \texttt{configure} reads,
the truncations autoconf writes out for its own options among them.
The \texttt{--srcdir} that would say which tree gets configured goes
with them, for a reason of its own.  The whole of it is
Section~\ref{buildsys:second_answer}.  The reason to refuse
rather than to pass it along is that the install here runs during
\texttt{make}: a destination this build system did not decide is a
plain \texttt{make} writing wherever that line pointed, and
\texttt{/usr/local} is one character away.  A tree whose install
layout really has to be rearranged is a tree to vendor with its own
\texttt{--prefix} and read out of afterwards.

\texttt{make clean} takes the stamp, and takes the install with it
when the tree installs into a default prefix --- which costs nothing
it was not already costing, since the next \texttt{make} re-enters the tree and
installs again, and which buys a way out of a prefix full of something
nobody can account for.  It leaves the build directory where it is:
what the tree built is the tree's, and throwing it away would make a
\texttt{clean} cost an hour of somebody's day rather than a second.
Re-configuring empties the default prefix for the same reason, so that
a file the previous configuration installed and this one does not stops
being found by things that look one \texttt{bin} up.  A prefix a
\texttt{--prefix} named is left alone by both, since peers may be
living in it.  The build directory goes on \texttt{make distclean},
which is the target that says the object directory as a whole is no
longer wanted.

Unlike a \texttt{kconfig} tree, an autotools tree is not told the
project's \texttt{CROSS\_COMPILE} (Section~\ref{cmd:cross_compile}).
A \texttt{CROSS\_COMPILE} is a program-name prefix and an autoconf host
is a triple; the two look alike for the usual toolchain and stop
looking alike the moment the prefix is a path.  A tree that has to be
told which machine it builds for is told once, with
\texttt{--configure-flag --host=...}.

What this run told the tree is written into
\texttt{\$obj\_dir/\$dirname/configure-opts}, beside the build
directory rather than inside it, and is a prerequisite of the
configuration.  It works exactly the way
Section~\ref{buildsys:kconfig} describes, with one addition: the
command that bootstraps the tree goes in as well when there is one,
since that command is worked out by looking at the tree rather than
written in the \texttt{Configfile}, and a tree that grew a
\texttt{Makefile.am} since it was last configured would otherwise be
bootstrapped by a different command than the \texttt{Makefile} says.

\subsection{\texttt{cmake}: CMake \label{buildsys:cmake}}

A \texttt{CMakeLists.txt} that a \texttt{cmake} run turns into a build
system of some other kind, which is then what actually builds the
tree.  It recognizes a directory with a \texttt{CMakeLists.txt} in it,
which is the whole of what such a tree looks like from outside ---
\texttt{cmake -S \$dir} reads exactly that file, and nothing else
decides whether a directory is a cmake project.

A tree whose \texttt{CMakeLists.txt} is one directory down ---
\texttt{llvm-project}, whose top level holds nothing but the
subprojects --- is named all the way down in the
\texttt{SUBPROJECTS}, since which build system builds a directory is
decided by looking in it and that happens before a single
\texttt{CONFIGUREOPTS} has been read.  A tree with both a
\texttt{CMakeLists.txt} and a \texttt{configure.ac} in it --- Verilator
is one --- really can be built both ways, so it is claimed by
whichever of the two build systems the \texttt{BUILD\_SYSTEMS} named
first.  That is what the ordering is for, and it is the only thing
that can say which of two right answers was meant.

Out of tree is the only way a tree gets built here, which cmake makes
easy: \texttt{-S} says where the sources are, \texttt{-B} says where
the output goes, and neither the tree nor its \texttt{CMakeLists.txt}
has to know.  The build directory is
\texttt{\$obj\_dir/\$dirname/build}, so a \texttt{make distclean}
leaves the vendored tree exactly as it was found and nothing this
writes goes anywhere near it.

Three rules come out of this, plus one per
\texttt{SUBPROJECT\_TARGETS}.  The first configures, and what it
produces is the build directory's \texttt{CMakeCache.txt} --- a real
file the tree writes rather than a stamp of ours, which is what makes
it worth hanging the build off, since a half-finished configure leaves
no cache and the next \texttt{make} configures again rather than
building something that was never configured.  The second builds, and
installs unless \texttt{--no-install} says otherwise, and writes a
stamp to say it did; as with \texttt{autotools}, the install is part
of building the tree because a vendored tool tree is vendored so that
the rest of this build can run the tool.  A build by a recursive
\texttt{\$(MAKE)} behaves under \texttt{make -n} the way an
\texttt{autotools} one does, skipping a build directory the cmake it
has only printed has not yet created.  The third writes down the
build-side options, and is explained below.

Configuring is starting over, and that is the one thing about this
build system worth reading twice.  A cmake cache remembers a
\texttt{-D} that has been deleted from the \texttt{Configfile},
forever, and it refuses outright to be reconfigured with a generator
other than the one it was made with --- so re-running cmake in the
directory that is already there is not a way of getting what the
\texttt{Configfile} now says.  The configure rule therefore removes
the build directory and starts again, and its only prerequisites are
the things for which starting again is the right answer: the file this
run's configure-side options were written into, and whatever a
\texttt{--depend} or a \texttt{--depend-config} named.  An edit to a
\texttt{CMakeLists.txt} is deliberately not one of them, and does not
have to be: every build system cmake generates knows how to re-run
cmake itself when one of its inputs changes, so an edit is picked up
by the build rule re-entering the tree, at the cost of a regenerate
rather than of a rebuild from scratch.

Starting over takes the default install prefix with it, and for the
same reason it takes the build directory: what a configuration
installed does not stop existing when the line that asked for it is
deleted.  Change \texttt{--define LLVM\_ENABLE\_PROJECTS=clang;lld} to
\texttt{clang} and the \texttt{lld} in the prefix outlives the
configuration that built it --- still on the path of anything that
looks one \texttt{bin} up, and still enough to satisfy the check
behind a \texttt{SUBPROJECT\_TARGETS} --- so the build reports success
while shipping a tool it no longer builds.  \texttt{make clean} takes
the default prefix for the same reason, beside the stamp it already
took.  A prefix a \texttt{--prefix} named is left where it is by both,
since the reason anybody writes one is that several trees install into
it and a peer whose stamp still says it is built will not install
again.  A tree told \texttt{--no-install} has no prefix to take at
all.

That is also why the build-side options --- what to build, how many
jobs, whether to install --- are written into a file of their own
rather than into the one the configure hangs off.  They reach a
recipe, so something has to notice when they change; but noticing them
the way the configure-side options are noticed would spend a whole
rebuild of LLVM on somebody adding a \texttt{--target}.  So there are
two files beside the build directory:

\begin{verbatim}
obj/llvm/configure-opts
obj/llvm/build-opts
\end{verbatim}

The first is written by \pconfigure\ and works exactly the way
Section~\ref{buildsys:kconfig} describes.  The second is written by
\texttt{make}, out of the recipe that reads it, and that difference is
deliberate rather than an accident of where the code happens to be.
\pconfigure\ can safely write the first because it writes it after the
\texttt{Makefile}: a run that dies part way through leaves neither, so
the file and the recipe it guards are always two halves of the same
run.  A build system writes its rules long before that, though, so a
file written from there can get ahead of the \texttt{Makefile} --- and
then a \texttt{make} builds the tree the old way and stamps it newer
than a file that already says the new thing, and the next run finds
the file saying exactly what it was about to write, leaves the mtime
alone, and the tree stays built the old way with nothing anywhere to
say so.  A file \texttt{make} writes out of the recipe cannot get
ahead of the recipe.  The rule that writes it hangs off a name that is
never a file, so it is asked on every \texttt{make}; it rewrites the
file only when what it has to say differs from what is already there,
so the mtime moves exactly when an option really moved.  The price is
a \texttt{mkdir}, a \texttt{printf} and a \texttt{cmp} per vendored
tree on every \texttt{make}, which is the cheapest of the three ways
to close that hole.

What is installed goes into \texttt{--prefix}, which defaults to
\texttt{\$obj\_dir/\$dirname/prefix}; where else it may point is
Section~\ref{buildsys:prefix}.  There is exactly one such path: the
\texttt{CMAKE\_INSTALL\_PREFIX} the tree is configured with, the
directory the install lands in and the directory a
\texttt{SUBPROJECT\_TARGETS} is named from are the same string, so
there is nothing for them to disagree about.  A tree told
\texttt{--no-install} has only its build directory to offer, so a
\texttt{SUBPROJECT\_TARGETS} is named from there instead.

The options are:

\begin{itemize}
\item \texttt{--generator \$name} picks the build system cmake writes,
  spelled the way cmake spells it: \texttt{--generator Ninja}.  It
  defaults to \texttt{Unix Makefiles}, which is the one that gets
  built by a recursive \texttt{\$(MAKE)} --- and so the only one that
  shares the jobserver of the \texttt{make} that ran it, instead of
  starting a second, uncoordinated pool of its own.  Anything else is
  built by \texttt{cmake --build}.  Which of the two it is also
  decides whether a \texttt{MAKEOPS} or a \texttt{--jobs} means
  anything here.  A generator whose name ends in \texttt{Unix
  Makefiles} counts as the first kind, which is what puts
  \texttt{CodeBlocks - Unix Makefiles} and the rest of the extra
  generators on the right side of the line: they write an IDE project
  beside a perfectly ordinary \texttt{Makefile}.

\item \texttt{--build-type \$name} sets
  \texttt{CMAKE\_BUILD\_TYPE}: \texttt{--build-type Release}.  This is
  a cache variable like any other and could have been left to
  \texttt{--define}; it has a name of its own because almost every
  tree wants one and a build with an empty build type is the classic
  way to end up with an unoptimized compiler.  Saying nothing leaves
  the tree with whatever it defaults to, which is cmake's business
  rather than ours.

\item \texttt{--define \$var=\$value} sets a cache variable, which
  reaches cmake as \texttt{-D\$var=\$value}.  So a tree is told what
  to build with a line like this one:

\begin{verbatim}
CONFIGUREOPTS += --define LLVM_TARGETS_TO_BUILD=RISCV
CONFIGUREOPTS += --define LLVM_ENABLE_PROJECTS=clang;lld
\end{verbatim}

  The whole thing is handed over as one argument however many spaces
  or semicolons are in it, since a cmake list is semicolon-separated
  and a semicolon in a recipe would otherwise end the command: the
  second of those is one variable holding a list of two.  \texttt{\$var:\$type=\$value} works too, being just another
  spelling of the same argument.  A value with no \texttt{=} in it is
  a fatal error, and so is one with no \texttt{\$var} in front of the
  \texttt{=} or the \texttt{:}, which cmake would refuse as a parse
  error only once the tree was being configured.

\item \texttt{--prefix \$dirname} says where the tree installs to,
  named relative to the project that asked for it the same way a
  \texttt{SUBPROJECTS} is: \texttt{--prefix obj/toolchain}.  It
  reaches cmake as an absolute path, because cmake bakes a prefix into
  its cache and into what it builds.  See
  Section~\ref{buildsys:prefix} for where it may point.

\item \texttt{--configure-arg \$arg} puts one more argument on the
  command line of the cmake that configures the tree:
  \texttt{--configure-arg -Wno-dev}.  This is the way out for anything
  cmake grew that the options above do not cover.  Unlike everything
  else here it is not quoted on its way into the recipe --- it is
  written the way it will appear on the command line, so somebody who
  needs two arguments writes two words and somebody who needs one word
  with a space in it writes the quotes themselves.  There is no other
  way to spell \texttt{--toolchain x.cmake} as one option.  Being raw
  is also why each of its words, rather than the first, is asked
  whether it says something this build system has already said: see
  Section~\ref{buildsys:second_answer}.

\item \texttt{--target \$name} asks the tree for a target rather than
  for whatever it builds when it is asked for nothing:
  \texttt{--target install-clang}.  May be given more than once, in
  which case they are asked for one at a time in the order they were
  written --- which is why one of them reaches the build as a single
  argument however many spaces or semicolons are in it: two targets
  are two of these rather than one with a space in the middle.

\item \texttt{--jobs \$n} says how many jobs the build runs at once:
  \texttt{--jobs 8}.  A value that is not digits all the way through
  is a fatal error, as is a zero, which \texttt{cmake --build} refuses
  as a parallel level; and so is writing this at all for a generator
  whose build is a \texttt{make} --- a sub-\texttt{make} takes its
  parallelism from the \texttt{make} that ran it, and telling it a
  number of its own is how a \texttt{make -j8} turns into sixty-four
  compilers.  Refusing it is the alternative to a number that silently
  did nothing, which the next person would read as the reason the
  build is slow.

\item \texttt{--install} and \texttt{--no-install} say whether the
  tree's install target is part of building it.  It is, unless it is
  turned off.

\item \texttt{--env \$name=\$value} puts a variable in the environment
  the tree is configured, built and installed in, where the tree is
  allowed to disagree with it: \texttt{--env
  PATH=/opt/gnubin:\$(PATH)}.  A cache variable is written into the
  build directory and is still true tomorrow, while something out of
  the environment is only true for the run that saw it, and that
  difference is exactly the one you want for a \texttt{PATH}.  It
  reaches the generated \texttt{Makefile} spelled exactly as written,
  so \texttt{\$(abspath x)} and \texttt{\$(PATH)} mean what they say,
  and it arrives as one word however many spaces are in it.  The name
  in front of the \texttt{=} has to be something a shell reads as a
  variable name, for the reason
  Section~\ref{buildsys:quoting} gives.

\item \texttt{--depend \$path} names something the build has to wait
  for, and \texttt{--depend-config \$path} names something only the
  configuration has to wait for.  \texttt{\$path} is relative to the
  project that names it, and is either a file or the directory of
  another vendored subproject of the same project --- in which case
  the wait is for that tree to have been built rather than for its
  directory to change.  A \texttt{--depend} is waited for by the
  configuration as well as by the build, since cmake runs the compiler
  while it is deciding what the tree can do; the price of that is that
  a dependency which has been rebuilt reconfigures this tree, and a
  reconfigure here is a rebuild.  A \texttt{pconfigure} subproject
  cannot be named either way.
\end{itemize}

A \texttt{MAKEOPS} (Section~\ref{cmd:makeops}) puts a variable on the
command line of the sub-\texttt{make}, for the generators that have
one.  There is no \texttt{--make-var} spelling of it the way
\texttt{kconfig} has: a \texttt{MAKEOPS} already lands wherever a
\texttt{CONFIGUREOPTS} does, including under a
\texttt{BUILD\_SYSTEMS}, so the second spelling would buy nothing and
cost a second list to keep in step with the first.  Written for a
generator that does not build by running \texttt{make} it is a fatal
error --- a variable this would have set is a cache variable here, so
write \texttt{--define} instead --- and it is refused rather than
dropped, since a dropped one is a build that is wrong in exactly the
way the variable was meant to prevent.

Where the tree installs is the one thing a cache variable may not say,
for the reason \texttt{autotools} refuses the same statement: this
build system puts one path into the cache, into the install and into
whatever a \texttt{SUBPROJECT\_TARGETS} names, so a second answer wins
in the cache and loses everywhere else.  That covers
\texttt{CMAKE\_INSTALL\_PREFIX}, \texttt{CMAKE\_STAGING\_PREFIX},
cmake's own \texttt{--install-prefix}, the
\texttt{CMAKE\_INSTALL\_} directory variables ---
\texttt{CMAKE\_INSTALL\_BINDIR}, \texttt{CMAKE\_INSTALL\_LIBDIR}
and the rest of them --- and \texttt{DESTDIR}, each said as a
\texttt{--define}, as a \texttt{--configure-arg}, as a
\texttt{MAKEOPS} or as an \texttt{--env}, and each whether it is
being set with a \texttt{-D} or deleted with a \texttt{-U}.  With a
generator that builds by running \texttt{make} a \texttt{--target}
is asked too, since it is a word on that \texttt{make}'s command line
and one with an \texttt{=} in it is a variable there; that is asked
once the \texttt{--generator} is known, wherever in the
\texttt{CONFIGUREOPTS} it was written.  With any other generator a
\texttt{--target} reaches \texttt{cmake --build --target}, which
reads it as the name of a target and nothing else, so it is not.  The
\texttt{-B} and \texttt{-S} this build system already wrote go with
them, a second answer to either being the same escape one option
across.  A \texttt{--configure-arg} is looked at one
whitespace-separated word at a time, since it reaches cmake's command
line exactly as written and so may be several arguments.  What a
relative value of one of the directory variables does here, which is
the one place cmake and \texttt{autotools} answer this differently,
is in Section~\ref{buildsys:second_answer}.

Unlike a \texttt{kconfig} tree, a cmake tree is not told the project's
\texttt{CROSS\_COMPILE} (Section~\ref{cmd:cross_compile}).  cmake has
no such notion and does not want one: a cmake cross build is a
toolchain file that says which system is being built for as well as
which compiler, written \texttt{--define CMAKE\_TOOLCHAIN\_FILE=...},
which says one thing once.

\subsection{\texttt{cargo}: Rust Crates \label{buildsys:cargo}}

Cargo, which is how a Rust crate gets built.  It recognizes a
directory with a \texttt{Cargo.toml} in it.  That one file is the
whole test because it is the whole of what a Rust tree looks like from
outside: nothing else is called that, a crate that has one always has
it at the top, and a crate that has not got one is not a crate.

Cargo is the odd one out among the vendored build systems here, and it
is worth saying how before saying anything else.  It is not
\texttt{make}: nothing written out of here says \texttt{\$(MAKE)}, so
there is no sub-\texttt{make} command line for a \texttt{MAKEOPS} to
land on, and a \texttt{MAKEOPS} under a \texttt{cargo}
\texttt{SUBPROJECTS} is a fatal error rather than a line that is
quietly dropped --- everything one would have said is said with
\texttt{--env} or \texttt{--arg} instead.  There is no configure step
either: cargo reads its \texttt{Cargo.toml}, works out what has to
happen and does it, all in the one command, so there is one rule here
rather than two and the stamp it writes is what everything else hangs
off.  It does its own dependency tracking and its own incremental
builds, and it is better at both than any guess made out here would
be, so the file list \pconfigure\ hangs the rule off is not there to
decide what gets recompiled --- it is there so that a \texttt{make} in
a tree that is already built has a reason not to run cargo at all.
And it wants a network: a crate with dependencies it has not already
downloaded needs either a populated \texttt{CARGO\_HOME} or a registry
to fetch from, and \texttt{--locked} and \texttt{--offline} are how a
project that has made its own arrangements says so rather than a way
of conjuring a crate that is not there.

What cargo insists on is managing its own build directory, which is a
thing this wants anyway.  The directory is
\texttt{\$obj\_dir/\$dirname/target}, handed over with
\texttt{--target-dir}, and that is what keeps a vendored crate from
writing a \texttt{target} into somebody else's checkout.
\pconfigure's own bookkeeping --- the stamp, and the record of what
this run was told --- sits beside it rather than inside it, since what
is inside is cargo's: it keeps a fingerprint database in there and has
every right to throw away anything it does not recognize.

Cargo is run from inside the crate, which is the one thing a
\texttt{--manifest-path} is not a substitute for: cargo looks for its
own configuration in \texttt{.cargo/config.toml} by walking up from the
directory it was started in, and never beside the manifest it was
pointed at.  A vendored crate pins its rustflags, its linker and the
replaced registry an offline build resolves against in that file, so a
cargo run from anywhere else would read the vendoring project's copy
instead, or nothing at all.  That file is watched for changes for the
same reason, and it is the one name beginning with a \texttt{.} that
is.  Running from in there is also the one thing that moves what a
relative path means, so every path this build system hands to cargo is
absolute by the time \texttt{make} is done with the line: the
manifest, the target directory, the crate an install is pointed at,
the install root, and a \texttt{--cargo} that names a path.  The
paths that stay relative are the ones \texttt{make} reads rather than
cargo --- the \texttt{cd} into the crate, the directories the recipe
makes, the stamp it writes --- which is what lets this
\texttt{Makefile} be included by a parent's and go on naming the same
files.

Every one of them is quoted where it lands, and so is every other
path in the recipe --- which here goes for the paths \pconfigure\
worked out as well as for the ones a \texttt{Configfile} wrote, since
a \texttt{--cargo}, an \texttt{--install} and the directory the
\texttt{SUBPROJECTS} named are each somebody's spelling.  The quotes
go round the whole \texttt{\$(abspath ...)} rather than round the
path inside it, because what the shell reads is the recipe and the
expression is what is written there: \texttt{make} expands it before
any shell sees it, so what the shell is finally handed is the absolute
path and nothing else.  What a value out of a \texttt{Configfile}
gets is Section~\ref{buildsys:quoting}.  The two things not made
absolute are the two written by hand and passed on as they were
written --- the text of an \texttt{--arg} and the value of an
\texttt{--env} --- and a path in one of those is the writer's to
spell.

Where a built program lands is the target directory above, then the
profile, and then the program --- with a directory named after the
triple in front of the profile when a \texttt{--target} asked for one:

\begin{verbatim}
$obj_dir/$dirname/target/$profile/$name
$obj_dir/$dirname/target/$triple/$profile/$name
\end{verbatim}

Neither of those middle components is a name anybody chose: \texttt{--profile
dev} makes a directory called \texttt{debug}, which is a mapping
nobody should have to remember, and most people do not know the triple
component is there at all.  So the directory a
\texttt{SUBPROJECT\_TARGETS} is named from is the whole of that path,
and a \texttt{SUBPROJECT\_TARGETS} names the program ---
\texttt{wavediff}, rather than \texttt{release/wavediff}.  The
\texttt{Configfile} then says what the tree produces rather than where
cargo happens to put it, and a project that moves from release to
debug moves one line rather than two.  Cargo's own mapping is not
one-to-one, and this follows it: \texttt{dev} and \texttt{test} build
into \texttt{debug}, \texttt{release} and \texttt{bench} into
\texttt{release}, a profile somebody wrote themselves builds into a
directory of its own name, and saying nothing is \texttt{dev}.

The price of that is an ordering rule, and it is a real one.  The
options that decide the path --- \texttt{--release},
\texttt{--profile} and \texttt{--target} --- have to be written above
anything that names an output, because a \texttt{SUBPROJECT\_TARGETS}
and a \texttt{TESTDEPS} are both resolved where they are written.
Writing them directly under the \texttt{SUBPROJECTS} that pulled the
tree in, above the \texttt{SUBPROJECT\_TARGETS} that names what it
built, is what keeps that from ever coming up.

Nothing is installed unless an \texttt{--install} says where to, so
there is no default prefix here: a crate with nothing to install has
no directory for the cleaning targets to spare or to take.  An
\texttt{--install} is the same kind of directory every other vendored
build system's prefix is --- see Section~\ref{buildsys:prefix} ---
and the programs land in \texttt{bin} underneath it.  Whether one is
given or not, a \texttt{SUBPROJECT\_TARGETS} is named from the build
directory described above rather than from the install root.

The options are:

\begin{itemize}
\item \texttt{--cargo \$path} picks which cargo to run.  It defaults
  to \texttt{cargo}, found on the \texttt{PATH}, and exists for a
  project that pins a toolchain rather than taking whatever rustup
  last pointed at: \texttt{--cargo tools/cargo}.  A word with no
  \texttt{/} in it is a program name rather than a path and is not
  made absolute, since the \texttt{PATH} is searched the same way
  from every directory.  Anything else is a path, read the way the
  project that vendored the tree spells it and written into the recipe
  absolutely --- it has to be, since the command runs from inside the
  crate, where a \texttt{tools/cargo} would name a file in somebody
  else's checkout.  Being read the project's way, it may not climb out
  of the project either.  Either way it reaches the recipe as one
  quoted word, which a program name survives --- a shell takes the
  quotes off before it searches the \texttt{PATH} --- and which a
  directory with a space in its name needs.  So this is one word: a
  value with a space in it is a fatal error rather than a program
  called \texttt{cargo +nightly} that nobody has, and a toolchain is
  picked with \texttt{--env RUSTUP\_TOOLCHAIN=nightly} or by pointing
  this at a script of your own that says the rest.  A value with a
  \texttt{\$} in it is a fatal error rather
  than something passed through: \pconfigure\ cannot resolve what
  \texttt{make} has not expanded yet, and wrapping somebody else's
  \texttt{\$(abspath ...)} in one of our own builds a path out of two
  absolute halves, which \texttt{make} hands to the shell without
  complaining and the shell then cannot find.

\item \texttt{--profile \$name} picks the cargo profile, and
  \texttt{--release} is the same thing said the way everybody writes
  it: \texttt{--profile release}.  Saying neither takes cargo's own
  default, which is \texttt{dev}.  A profile is a directory name as
  much as it is a setting, so a value with a \texttt{/} or a space in
  it is a fatal error.  Left off, the build says nothing and takes the
  default, but an install is told the profile outright: \texttt{cargo
  install} defaults to \texttt{release} where \texttt{cargo build}
  defaults to \texttt{dev}, and two halves of one recipe that disagree
  are two builds landing in two directories, only one of which
  anything here goes looking in.

\item \texttt{--target \$triple} builds for another machine:
  \texttt{--target riscv64gc-unknown-linux-gnu}.  This is rustc's
  spelling of a machine rather than a toolchain prefix, so the
  project's \texttt{CROSS\_COMPILE} (Section~\ref{cmd:cross_compile})
  says nothing about it and is not passed on ---
  a \texttt{CROSS\_COMPILE} of
  \texttt{riscv64-linux-gnu-} and a triple of
  \texttt{riscv64gc-unknown-linux-gnu} are two different kinds of
  name, and guessing either from the other gets it wrong.  A triple is a
  directory name too, so a value with a \texttt{/} or a space in it is
  a fatal error.

\item \texttt{--package \$name} picks which member of a workspace to
  build: \texttt{--package wavediff}.  May be given more than once.  A
  crate that is not a workspace has no use for it, and neither has one
  that installs: \texttt{cargo install} has no \texttt{--package}, it
  installs whatever its \texttt{--path} names, so a \texttt{--package}
  and an \texttt{--install} written together are a fatal error rather
  than a command line cargo rejects halfway through a build.  A
  workspace member that is meant to be installed is named by pointing
  the \texttt{SUBPROJECTS} at the member's own directory.

\item \texttt{--bin \$name} picks which program to build, for a crate
  that builds several and only one of them is wanted:
  \texttt{--bin wavediff}.  May be given more than once.

\item \texttt{--features \$list} turns on cargo features, separated by
  spaces or commas: \texttt{--features one two}.  May be given more
  than once, and the list is handed over as one word because cargo is
  the thing that knows how to read one.  \texttt{--all-features} and
  \texttt{--no-default-features} are cargo's own, and mean what they
  mean there; they add up the way cargo adds them up.

\item \texttt{--locked} builds against the committed
  \texttt{Cargo.lock} rather than whatever resolves today, and
  \texttt{--offline} builds without asking the network.  A vendored
  crate built as part of somebody else's build wants both: a lock file
  that silently moves is a build that is not reproducible, and a build
  that reaches the network is a build that fails on a machine that has
  not got one.

\item \texttt{--jobs \$n} bounds how many jobs cargo runs at once:
  \texttt{--jobs 4}.  A value that is not digits all the way through
  is a fatal error, and so is a zero, which cargo refuses.  Cargo does
  not take part in \texttt{make}'s jobserver, so a \texttt{make -j8}
  that reaches one of these has two pools rather than one, and this is
  the only thing that bounds the second.

\item \texttt{--arg \$text} puts one more argument on the command
  line of the \texttt{cargo build} that builds the crate, verbatim:
  \texttt{--arg --message-format short}.  May be given more than
  once, and each arrives as a single argument however many spaces are
  in it.  This is the escape hatch
  for everything cargo can be told that is not worth a flag of its
  own.  The few arguments \pconfigure\ has to decide for itself are
  refused here rather than silently fought over:
  \texttt{--manifest-path} and \texttt{--target-dir}, which decide
  where cargo reads and writes; \texttt{--profile},
  \texttt{--release} and \texttt{--target}, which decide the
  directory a built program lands in and so what a
  \texttt{SUBPROJECT\_TARGETS} resolves to; \texttt{--artifact-dir}
  and the \texttt{--out-dir} it used to be called, which copy what
  was built out of the object directory altogether; and
  \texttt{--config}, which says any setting cargo has --- three of
  them being the questions above under cargo's own names --- and takes
  the name of a file to read them out of as readily as it takes one of
  them, so it is refused whatever is written after it.  Two of those
  have one-letter spellings and are refused in them as well, wherever
  in a cluster of flags they turn up: a \texttt{-r} is a
  \texttt{--release} and a \texttt{-m} is a
  \texttt{--manifest-path}.  A cluster is read the way a shell reads
  one, left to right and stopping at the first flag that takes a
  value, so a \texttt{-prand} is a \texttt{--package rand} rather
  than a \texttt{--release} on account of the letter in the crate's
  name.  None of them is a thing left unsaid: the
  \texttt{SUBPROJECTS} named the crate and its object directory is
  where cargo's output goes, the profile and the machine are each a
  \texttt{CONFIGUREOPTS} of their own, and what an
  \texttt{--artifact-dir} would have done is what \texttt{--install}
  does, into a directory this project owns.  An \texttt{--arg} goes
  on the build alone and not on the install, since the two take
  different sets of arguments.  A relative path written in one is read
  from inside the crate, since that is where cargo runs;
  \texttt{\$(abspath x)} is how to mean one that is not.

\item \texttt{--env \$name=\$value} puts a variable in the environment
  cargo runs in, which is how \texttt{RUSTFLAGS} and
  \texttt{CARGO\_HOME} get said: \texttt{--env RUSTFLAGS=-C
  target-cpu=native}.  The value reaches the generated
  \texttt{Makefile} exactly as written, so \texttt{\$(abspath x)}
  means what it says, and it arrives as one word however many spaces
  are in it --- which is the other half of saying that a plain
  relative path in one is read from inside the crate, the same as one
  in an \texttt{--arg}.  The name gets no such latitude: it reaches
  the recipe bare, because a quoted one would stop being a shell
  assignment, so it has to be what a shell reads as a variable name
  and anything else is refused where it was written.
  Four variables are refused outright, each being the environment's
  spelling of something already written on cargo's own command line:
  \texttt{CARGO\_TARGET\_DIR} and
  \texttt{CARGO\_BUILD\_TARGET\_DIR}, which would undo the thing
  keeping a vendored crate's output out of the vendored crate;
  \texttt{CARGO\_BUILD\_TARGET}, which moves every program cargo
  builds into a directory named after the triple while the rest of
  this build goes on looking where it was; and
  \texttt{CARGO\_INSTALL\_ROOT}, which is where the install lands.
  Three of those cargo happens to shadow with the flags this writes,
  and they are refused anyway: a \texttt{Configfile} that says where
  cargo builds and is silently overruled says something that is not
  true, and the day this recipe stops writing one of those flags is
  the day it starts being a build in somebody else's directory.

\item \texttt{--install \$dirname} runs \texttt{cargo install --root}
  into the named directory after building, which is where the programs
  end up in \texttt{bin}: \texttt{--install obj/toolchain}.  The
  directory is named relative to the project that asked for it rather
  than to the crate, since it is that project's statement about where
  it wants its tools, and where it may point is
  Section~\ref{buildsys:prefix} --- which among other things is what
  keeps an install root from being aimed back into the vendored crate,
  leaving a repository nobody here owns with programs in it.  Left
  off, nothing is installed and what was built is named with a
  \texttt{SUBPROJECT\_TARGETS} instead, which is the cheaper answer
  when the only consumer is this build.

\item \texttt{--depend \$path} names something the build has to wait
  for: either a file, or the directory of another vendored subproject
  of the same project --- in which case the wait is for that tree to
  have been built rather than for its directory to change.  A
  \texttt{pconfigure} subproject cannot be named this way.
\end{itemize}

The install is a re-install of what was just built rather than a
second build of the same crate: it is handed the same target directory
and the profile spelled out.  It is run with \texttt{--no-track}, so
that cargo does not write a \texttt{.crates.toml} beside the
\texttt{bin} directory saying what it thinks lives there --- which is
wrong the moment anything else installs into the same prefix, and a
prefix shared between several vendored trees is the normal case rather
than the odd one.  It is run with \texttt{--force}, because a second
install of the same crate is the normal case here too: this is the
build rule's recipe, so it runs again for every source that changes
and every option that moves.

\texttt{make clean} takes the stamp and nothing else.  What cargo
built is cargo's, and throwing away a target directory cargo would
have reused is minutes of somebody's day in exchange for nothing;
losing the stamp is enough to make the next \texttt{make} run cargo
again, which is all a clean has to promise, and that run installs over
whatever is in the install root.  \texttt{make distclean} removes the
object directory and takes the target directory and the install root
with it, without naming either.

What this run told cargo is written into
\texttt{\$obj\_dir/\$dirname/configure-opts}, which works the way
Section~\ref{buildsys:kconfig} describes and is the one prerequisite
of the build rule that is not a file somebody already had.  There is
nothing to add to it here: everything that reaches cargo arrived as a
\texttt{CONFIGUREOPTS}, there are no \texttt{MAKEOPS} because there is
no \texttt{make}, and this build system deliberately reads nothing
else off the project around it.

The files the build rule waits on are the ones that decide what cargo
does: every \texttt{.rs}, \texttt{.toml} and \texttt{.lock} under the
crate, plus cargo's own \texttt{.cargo/config} and
\texttt{.cargo/config.toml}.  A crate can read anything at all through
\texttt{include\_str!}, and chasing that would mean naming every byte
in the tree --- which for a crate with test fixtures in it is a
\texttt{Makefile} made mostly of fixtures.  Being wrong in the
direction of running cargo when it need not have is cheap, because
cargo then decides nothing changed and says so in well under a second.
A \texttt{target} directory is skipped on the way down, and so is any
directory holding a \texttt{CACHEDIR.TAG}, since both are output
wearing an input's clothes.

\subsection{\texttt{meson}: Meson \label{buildsys:meson}}

A \texttt{meson.build} that a \texttt{meson setup} turns into a ninja
build directory, which ninja then builds.  It recognizes a directory
with a \texttt{meson.build} in it, which is what \texttt{meson setup}
looks for.  Like a \texttt{CMakeLists.txt}, that is a file plenty of
trees ship beside some other build system's --- QEMU has a
\texttt{meson.build}, a hand-written \texttt{configure}, a
\texttt{Cargo.toml} and a \texttt{Makefile} at its top level --- and
which build system claims such a tree is the \texttt{BUILD\_SYSTEMS}
order's to say.

Almost everything about how a meson tree is driven is the answer
\texttt{cmake} gives (Section~\ref{buildsys:cmake}), because almost
everything about the problem is cmake's problem: a meson build
directory remembers a \texttt{-D} that has been deleted from the
\texttt{Configfile} exactly the way a cmake cache does.  So the build
directory is \texttt{\$obj\_dir/\$dirname/build}; configuring is
starting over, taking the build directory and the default prefix with
it; the configure-side and build-side options are written into the
same two files by the same two writers; and \texttt{make clean} and
\texttt{make distclean} take the same things.  The configure rule
hangs off the build directory's \texttt{build.ninja}, which meson
writes last and a failed setup does not write at all, so it plays the
part a \texttt{CMakeCache.txt} plays for cmake.  An edit to a
\texttt{meson.build} is the build rule's to notice rather than the
configure rule's, because \texttt{build.ninja} re-runs meson itself
when one of meson's inputs changes.

The build is \texttt{ninja -C} and the install is the build
directory's own \texttt{install} target, rather than \texttt{meson
compile} and \texttt{meson install}.  Both of those are wrappers that
find the build directory's ninja and run it, which would make no
difference except for which meson does the wrapping: the
\texttt{meson} on the \texttt{PATH} is not necessarily the meson that
set the tree up, and a meson handed a build directory that a
different version of it wrote refuses it.  \texttt{build.ninja}
records the meson that set it up by its absolute path and calls that
one for the regenerate and the install.

ninja also decides how parallel the build is.  A ninja new enough to
be a jobserver client --- 1.13 onwards --- takes its jobs from the
\texttt{make} that ran it when it is given no \texttt{-j} of its own,
and a GNU \texttt{make} that passes its jobserver through a fifo hands
it to every recipe, so a \texttt{make -j8} is eight jobs in total.
The recipe has no leading \texttt{+}, which would also run the build
under a \texttt{make -n}.  There is no \texttt{make} anywhere in the
build, so a \texttt{MAKEOPS} is a fatal error; what a tree would take
as a variable it takes here as a \texttt{--define}.

The options are:

\begin{itemize}
\item \texttt{--build-type \$name} sets meson's \texttt{buildtype}:
  \texttt{--build-type release}.  It reaches the tree as
  \texttt{-Dbuildtype=\$name}, which meson reads the same as its
  \texttt{--buildtype} and which, being a \texttt{-D} like any other,
  is the spelling a \texttt{--setup-script} is most likely to pass
  through unchanged.

\item \texttt{--define \$name=\$value} sets a build option, which
  reaches the tree as \texttt{-D\$name=\$value} and as one argument
  however many spaces or commas are in it.  A value with no
  \texttt{=} in it is a fatal error, and so is one with no
  \texttt{\$name} in front of the \texttt{=}.

\item \texttt{--prefix \$dirname} says where the tree installs to, as
  it does for cmake.  It reaches the tree as an absolute
  \texttt{--prefix=}, rather than as a \texttt{-Dprefix=}, because
  meson refuses to be handed both and a \texttt{--configure-arg} is
  far more likely to be written the first way.

\item \texttt{--configure-arg \$arg} puts one more argument on the
  command line of whatever sets the tree up, raw, as it does for
  cmake: \texttt{--configure-arg --wrap-mode=nofallback}.  This is
  also how a \texttt{--setup-script} is handed options of its own.

\item \texttt{--setup-script \$path} names a script inside the tree
  that sets the tree up in place of \texttt{meson setup}:
  \texttt{--setup-script configure}.  This is for a tree whose
  \texttt{meson.build} reads files that only its own script writes.
  QEMU is one: its \texttt{meson.build} starts by loading a
  \texttt{config-host.mak} out of the build directory, and the only
  thing that writes one is QEMU's \texttt{configure}, which then runs
  \texttt{meson setup} itself with a meson it installed into a Python
  venv of its own.  The script is run from inside the build directory
  and by its absolute path, which is how a configure of that kind is
  told where to build and where its sources are, and it is handed
  everything \texttt{meson setup} would have been handed except the
  two directories.  It has to leave a meson build directory behind,
  since everything after it is ninja's.  A \texttt{--configure-arg}
  that names a relative path is relative to the build directory here.
  \texttt{\$path} is relative to the top of the tree, may not leave
  it, and is made of letters, digits and \texttt{.\_/+-}, since it
  lands in a recipe as a bare word; anything else is a fatal error,
  and so is a \texttt{\$path} that is not an executable file.

\item \texttt{--target \$name} asks ninja for a target rather than for
  its default.  May be given more than once, in which case they are
  asked for one at a time in the order they were written.

\item \texttt{--jobs \$n} says how many jobs ninja runs at once.
  Zero is taken, and is ninja's own way of saying no limit at all.
  Leave it off to have a new enough ninja share the jobserver of the
  \texttt{make} that ran it instead.

\item \texttt{--install} and \texttt{--no-install} say whether the
  build directory's install target is part of building the tree.  It
  is, unless it is turned off.

\item \texttt{--env \$name=\$value}, \texttt{--depend \$path} and
  \texttt{--depend-config \$path} mean what they mean for cmake.
\end{itemize}

Where the tree installs is refused from a \texttt{--define}, a
\texttt{--configure-arg} and an \texttt{--env} alike: meson's
\texttt{prefix}, \texttt{DESTDIR}, which the install reads out of the
environment, and \texttt{meson install}'s own \texttt{destdir}; and
meson's directory options --- \texttt{bindir}, \texttt{libdir},
\texttt{sysconfdir} and the rest --- when they are given anything but
an ordinary relative path, since meson joins a relative one to the
prefix the way cmake does.  Each of those as a \texttt{-D}, as a bare
\texttt{NAME=VALUE}, and as a \texttt{--} option in full or in any
shortened form: meson's command line takes an unambiguous prefix of a
long option as the option, so \texttt{--prefi=} is
\texttt{--prefix=} there just as it is to a generated
\texttt{configure}.

\section{Warnings \label{warn}}

These are the \texttt{Configfile} lines that are accepted and then
quietly do something nobody meant.  Each one prints the file and line
that wrote it, what actually happens, what to write instead, and the
version that turns it into an error; \texttt{STRICT} (see
Section~\ref{cmd:strict}) is what does the turning, and everything
listed here was found in \texttt{v0.13}, so \texttt{STRICT = v0.13}
promotes the lot.

What a warning means doesn't change when it becomes an error, and
neither does what \pconfigure\ does with the line it's about: the
build a project gets under the default is the build it has always
got.  All that changes is whether the run finishes and leaves a
\texttt{Makefile} behind it.

\subsection{An option that lands on a target that was already closed}

\texttt{COMPILER}, \texttt{LINKER}, \texttt{COMPILEOPTS} and
\texttt{LINKOPTS} all land on whatever target was opened last.
\texttt{SRCDIR}, \texttt{LIBDIR}, \texttt{BUILD\_SYSTEMS} and
\texttt{SUBPROJECTS} each go back to the top of the project, which
closes that target without opening another one:

\begin{verbatim}
BINARIES    += hello
SRCDIR       = hello
COMPILEOPTS += -Wall
\end{verbatim}

\texttt{-Wall} is still aimed at \texttt{hello}, which stopped
listening one line earlier, so nothing at all is built with it.  The
message names both ends and the line that closed the target, since
which of the four did it is the part that isn't obvious.

Three things that look like this and aren't: an opts target that came
from a \texttt{LANGUAGES} is never stale, because a language isn't a
context and never gets closed, so setting a language's options either
side of a \texttt{SRCDIR} means exactly what it looks like; a
\texttt{GENERATE} deliberately opens a source of its own on top of the
target it just aimed these at; and a \texttt{SOURCES} or a
\texttt{TESTS} closes the source above it and immediately aims at the
one it opened.  None of those warn.

\subsection{\texttt{LINKOPTS} written after a \texttt{SOURCES}}

\begin{verbatim}
BINARIES += hello
SOURCES  += hello.c
LINKOPTS += -lm
\end{verbatim}

A \texttt{LINKOPTS} written after a \texttt{SOURCES} lands on that one
file, and a source file is compiled rather than linked: every language
asks the target for its link options, and the target is the binary or
the library.  So nothing ever reads this one.  It wants to be above
the \texttt{SOURCES}, on the target the file gets linked into.

\subsection{\texttt{ENTITLEMENTS} under something that isn't linked}

\begin{verbatim}
BINARIES     += vmm
SOURCES      += vmm.c
ENTITLEMENTS  = vmm.plist
\end{verbatim}

Only a whole linked binary is signed, so an \texttt{ENTITLEMENTS} that
landed under a \texttt{SOURCES}, a \texttt{HEADERS} or a
\texttt{GENERATE} asks for nothing at all -- and asking for nothing
quietly is worse here than elsewhere, since what comes out is a
program that runs right up until it reaches the thing it wasn't
allowed to do.  See Section~\ref{cmd:entitlements}.

Directly under the \texttt{BINARIES} or \texttt{LIBRARIES} it's about
is where it belongs, and doesn't warn.  Neither does one written at
the top of a project, before any target: that one is inherited by
every target below it, which is a thing somebody meant.

Nor does one under a \texttt{TESTS}, which reads like it ought to.  A
test is built into a program of its own and that program is linked and
signed like any other, so an \texttt{ENTITLEMENTS} written there
reaches the test binary's own signature -- which is exactly how a test
that has to be allowed to do something says so.

\subsection{\texttt{SOURCES} with no target open above it \label{warn:sources-orphan}}

\begin{verbatim}
LANGUAGES += c
SOURCES   += hello.c
\end{verbatim}

A source file has to be compiled into something, and the something is
whatever target is open above it.  With nothing open the file hangs
off the project's own context, which is never asked for its targets
and never asks its children for theirs, so the line is read,
remembered and then dropped without a word.  The usual way to arrive
here is not writing the target at all, and the second usual way is a
\texttt{SRCDIR} or a \texttt{LIBDIR} between the target and its
sources.

A \texttt{SOURCES} under a \texttt{PHONY} (see
Section~\ref{cmd:phony}) arrives here too, and means the same thing: a
phony target is a name and has nothing to compile, so the
\texttt{SOURCES} closes it on the way past and lands on nothing.

\subsection{A value with a space in it}

\begin{verbatim}
SOURCES += a.c b.c
\end{verbatim}

Everything after the operator is one value, so that names a single
file called \texttt{a.c b.c}.  What comes out is a \texttt{Makefile}
rule that \texttt{make} splits back up on the space into targets
nobody meant.  One line per file.

Only the commands whose value is a path or the name of a target are
asked this question.  A \texttt{COMPILEOPTS}, a \texttt{LINKOPTS}, a
\texttt{CONFIGUREOPTS}, a \texttt{COMPILER} or a \texttt{LINKER} is a
command line, is meant to have spaces in it, and is left alone.

The question is asked once of the line as it was written, rather than
of each command that line turns into -- so a \texttt{TESTSRC}, which
is a \texttt{TESTS} and a \texttt{SOURCES} wearing one hat, warns once
about the \texttt{TESTSRC} rather than three times about three
different names for the same mistake.

\subsection{A name with a character \texttt{make} or the shell reads
  \label{cmd:make-special}}

\begin{verbatim}
BINARIES += hello:world
\end{verbatim}

The name of a target or a source goes onto a \texttt{Makefile} rule
line exactly as it was written, and into the recipes that build it as
a bare word.  Some characters mean something of their own in one place
or the other, so a name holding any of them is a fatal error that
names the line, rather than a \texttt{Makefile} that \texttt{make}
can't read or a build that quietly produces a file under a different
name:

\begin{itemize}
\item On a rule line, \texttt{make} reads a \texttt{\#} as the start of
  a comment, a \texttt{:} as the end of the targets, an \texttt{=} as a
  variable assignment, a \texttt{;} as the start of a recipe, a
  \texttt{|} as the start of the order-only prerequisites, a
  \texttt{\$} as an expansion, and \texttt{a(b)} as a member of an
  archive.
\item In a recipe, the shell reads a single or double quote as the
  start of a string that never ends, a \texttt{;}, \texttt{\&} or
  \texttt{|} as the end of a command, a \texttt{<} or \texttt{>} as a
  redirection, a parenthesis as a subshell, and a \texttt{\textbackslash}
  as an escape that disappears from the name.
\end{itemize}

A backquote never gets this far: \pconfigure\ runs what is between two
of them as a command when it reads the line.

The list is the characters that were found to break a build, not a
promise about every other one.  Letters, digits, \texttt{-},
\texttt{\_}, \texttt{.} and non-ASCII letters are ordinary characters
to both \texttt{make} and the shell, and a name made of those is safe.
\texttt{\%}, \texttt{*}, \texttt{?} and \texttt{[} aren't refused,
because names with them in do build today, but each of them is a
warning that names the line (see Section~\ref{warn:wildcard}).

The commands asked are the ones that name something the language
backends build: \texttt{BINARIES}, \texttt{LIBRARIES},
\texttt{LIBEXECS}, \texttt{TESTS}, \texttt{TESTSRC},
\texttt{TESTEXECS}, \texttt{HEADERS}, \texttt{HEADERSRC} and
\texttt{SOURCES} --- and the ones that name a target without building
it from sources, \texttt{PHONY}, \texttt{GENERATE} and
\texttt{TGENERATE}, whose names land on the left of a rule all the
same.  A
\texttt{SUBPROJECTS} and a \texttt{SUBPROJECT\_TARGETS} are not, since
the vendored build systems quote what they write, and neither is a
command line: \texttt{COMPILEOPTS += -DX=a:b\#c} means what it says.

Unlike a space, this is not a \texttt{STRICT} warning.  No
\texttt{Configfile} ever built with one of these in a name, so there is
nothing old for refusing it to break.

\subsection{A name with a \texttt{\%} or a glob character
  \label{warn:wildcard}}

\begin{verbatim}
BINARIES += 50%off
BINARIES += a?b
\end{verbatim}

These build, which is why they aren't refused with the characters in
Section~\ref{cmd:make-special}, but they build by luck.

A \texttt{\%} makes the rule for the name a pattern rule, which
\texttt{make all} happens to match.  The rules that remove it again
are phony, and \texttt{make} never looks for a pattern rule for a
phony target, so \texttt{make clean} and \texttt{make uninstall}
find nothing to do and leave the program where it is.

A \texttt{*}, \texttt{?} or \texttt{[} is expanded by \texttt{make}
in a rule's targets and by the shell in the recipes, against whatever
files exist.  On its own there is nothing for it to match; beside
another target whose name it does match --- \texttt{a?b} next to
\texttt{axb} --- the two programs' rules land on the same files.  The
warning doesn't wait for the second name to turn up, since it is
usually written long after the first.

Escaping them isn't on offer: \texttt{make} reads a
\texttt{\textbackslash\%} as a plain \texttt{\%} in some places and
not others.  Rename the target without the character.

\subsection{\texttt{COMPAT}}

\begin{verbatim}
COMPAT = 1.0
\end{verbatim}

\texttt{COMPAT} is read and then thrown away, and always has been: it
was going to be what \texttt{STRICT} is (see
Section~\ref{cmd:strict}) and never became anything.  A project that
wants to say which \pconfigure\ it was written against wants that
instead; a project that doesn't wants the line deleted.

\subsection{\texttt{VERBOSE} and \texttt{DEBUG} ignore what they're set to}

\begin{verbatim}
VERBOSE = false
\end{verbatim}

turns verbose output on, exactly as \texttt{VERBOSE = true} does:
writing either line at all turns the thing on, and it stays on for
everything below.  \texttt{DEBUG} is the same.  Anything that isn't
exactly \texttt{= true} warns, and the line goes on doing what it has
always done -- \texttt{VERBOSE = false} still turns verbose output on,
warning or no warning, since a line that changed its meaning under a
new release would be a worse problem than the one being pointed at.

\subsection{A second \texttt{SRCPATH}}

\begin{verbatim}
SRCPATH = a
SRCPATH = b
\end{verbatim}

A \texttt{SRCPATH} rewrites the source directories in place rather
than replacing them, so a second one is read relative to whatever the
first one already produced and the project goes looking under
\texttt{b/a}.  It's written with an \texttt{=} rather than a
\texttt{+=}, which is a promise that it replaces, so this is the rare
one where the line says the opposite of what happens.  Say it once, at
the top of the project, and remember that a source path given on the
command line has already said it.

\subsection{A target with nothing to build}

\begin{verbatim}
BINARIES += hello
SRCDIR    = hello
\end{verbatim}

A \texttt{BINARIES}, \texttt{LIBRARIES}, \texttt{LIBEXECS} or
\texttt{TESTEXECS} that no \texttt{SOURCES} ever landed on is a link
with nothing to link.  Without this it fails when \texttt{make}
finally gets there, with a message from the linker about a missing
\texttt{main} rather than anything that points at the
\texttt{Configfile}.  The usual cause is the one above: a
\texttt{SRCDIR} or a \texttt{LIBDIR} written between the target and
its sources, which goes back to the top of the project and ends the
target on its way.

It's a warning unless \texttt{STRICT} says otherwise, so the
\texttt{Makefile} is still written.  A BASH or Perl script and a
pkg-config file have no linker to complain about them, so their rules
fail instead when \texttt{make} gets there, with the
\texttt{Configfile} line and ``has no SOURCES to be made from'',
rather than leaving an empty file behind that would pass for a built
one.

A \texttt{HEADERS} and a \texttt{GENERATE} aren't asked, since a
header is installed rather than built and a \texttt{GENERATE} writes
its own source.

\subsection{Two targets that come out in the same place}

\begin{verbatim}
BINARIES += hello
SOURCES  += hello.c

BINARIES += hello
SOURCES  += other.c
\end{verbatim}

Two targets that come out in the same place are one target, and only
one set of rules can come out of that.  Which way it goes wrong
depends on whether the two were described the same way.  Rules that
match -- the same sources built with the same options -- are folded
together, so the second target does nothing and it looks exactly like
it worked.  Rules that don't match, as in the fragment above, stop
\pconfigure\ instead, with \texttt{Mismatched recipe for targets with
same name}, the file the two rules write and only the second of the two
lines.  The warning is worth having for that case alone, since it names
both of them.  The
message names the line that asked for the output first.

They're compared by where they come out rather than by what they're
called, which is the whole point: two \texttt{LIBRARIES} of the same
name written either side of a \texttt{LIBDIR} are two libraries with
one name and two homes, which is a thing somebody meant, and they
don't warn.  The comparison is within one project, since two projects
that both build a \texttt{libutil.so} each build it into their own
\texttt{LIBDIR}.

A target that comes out \emph{inside} another one's output is a
different matter: \texttt{BINARIES += tools} beside
\texttt{BINARIES += tools/run} asks for \texttt{bin/tools} to be both
the first program and the directory the second one lands in.  No
build can make both true, so that is always an error rather than a
warning, whatever \texttt{STRICT} says and whichever of the two lines
comes first.  The message names both lines; rename one of the
targets, to \texttt{tools-run} say, so that neither is the other's
directory.

\subsection{\texttt{AUTODEPS = false} where nothing is linked}

\begin{verbatim}
LANGUAGES += bash

BINARIES  += app
AUTODEPS   = false
SOURCES   += app.bash
\end{verbatim}

\texttt{AUTODEPS = false} keeps the sources sitting behind a target's
headers from being built and linked into it, and that is the whole of
what it is for (see Section~\ref{cmd:autodeps}).  A \texttt{BASH}
target has no such sources and links nothing at all --- what it has is
handed to \texttt{pbashc} and one file comes out --- so there is
nothing here for the line to take away.  What it does instead is stop
the target being rebuilt when a file it includes changes, which is a
cost with nothing on the other side of it.

The warning is about the line rather than about any of the targets
that read it, since one written at the top of a target is read by
every test underneath and saying it once is the only way it gets
read.  It is raised only when \textit{nothing} that line reached is
linked: one written over a compiled binary with \texttt{BASH} tests
under it was written for the binary, and the tests inherit it the way
they inherit everything else on that target.  What that costs the
tests is real, but it is not this warning --- this one is about a
line that bought nothing at all.

\section{Common Error Messages \label{err}}

\pconfigure\ will print a number of error messages to \texttt{stderr}.
Some of these messages are fatal and some aren't.  Fatal errors result
in the termination of \pconfigure\ without generating a valid
\texttt{Makefile}, while non-fatal errors are simply printed to
\texttt{stderr} while \pconfigure\ continues to run.  Note that some
non-fatal errors may mask or create others, so it's probably best to
only rely on the first error message (though this hasn't proved to be
a problem yet, it's a big problem with many other languages). %

\subsection{... failed, which is probably bad}

A shell-out exited with a non-zero exit code.  You should avoid using
commands that can fail but should instead handle these failures in
your code (ie, as opposed to your \texttt{Configfile}).

\subsection{\texttt{TESTS} with no target open above it has nothing to test}

A \texttt{TESTS} or a \texttt{TESTSRC} written with no
\texttt{BINARIES}, \texttt{LIBRARIES}, \texttt{LIBEXECS},
\texttt{TESTEXECS} or \texttt{PHONY} open above it.  A test belongs to
the thing it exercises, and with nothing open the thing above it is
the project's own context, which has no command behind it and no
binary to hand the test as \texttt{\$PTEST\_BINARY} (see
Section~\ref{cmd:tests}).

If what the test exercises isn't any one thing this project builds ---
an integration test that drives several subprojects at once, most of
all --- then a \texttt{PHONY} (see Section~\ref{cmd:phony}) is what to
hang it off.

This is a fatal error whatever \texttt{STRICT} says, rather than one
of the warnings in Section~\ref{warn}: what used to happen here was a
null dereference and a signal, with nothing printed at all, so there
is no behavior to stay compatible with.

\section{Useful Helper Programs \label{prog}}

The \pconfigure\ distribution includes a number of binaries in
addition to the \pconfigure\ binary.  What follows is a list of these
programs along with a short description of their functionality and
usage.

\subsection{\texttt{pclean} \label{prog:pclean}}

The simplest helper program: essentially it just performs \texttt{rm
  *~} recursively.  It's just a small wrapper around \texttt{find}.
Like \texttt{rm}, it tries every backup it finds and fails if any of
them couldn't be removed, not just the last one it tried.

\subsection{\texttt{ptest} \label{prog:ptest}}

In addition to being used internally by \pconfigure\ to run tests,
\texttt{ptest} prints the current set of test results to
\texttt{stdout}.  You will almost certainly just want to run
\texttt{ptest} with no arguments, which will print the entire current
set of test results along with a summary.

Run that way it reports on every project in the build, not just the
one it was run in: a build with subprojects has its results spread
across all of them, and \pconfigure\ writes the list of directories
they land in to \texttt{\$OBJDIR/check-dirs} at the same time as it
writes the \texttt{Makefile}.  Naming a directory with
\texttt{--check-dir} overrides that entirely, and may be given more
than once.  Directories are compared by where they are rather than by
how they are spelled, so \texttt{check}, \texttt{./check/} and its
absolute path name one directory, as does a symlink to it, and its
results are counted once.
A directory inside another one that was named too keeps its own
results: each is counted, labelled and scored by the nearest
directory that holds it, in a whole run and a suite report alike.

Only a project that builds something has a check directory: one that
does nothing but pull in subprojects runs no tests of its own, so a
\texttt{check/} at its top is somebody else's directory, which the
report doesn't read and \texttt{make distclean} doesn't remove.  A
build where no project has one writes an empty list, and the
\texttt{Makefile} says \texttt{--no-check-dirs} in place of any
\texttt{--check-dir}; either way \texttt{ptest} reports that there
are no tests rather than falling back to \texttt{check}.

It also says whether what it is reporting is current, by asking
\texttt{make} about the stamp that \texttt{make check} builds here.
Which stamp that is depends on whether the project named a
\texttt{DEFAULT\_TEST\_SUITE} (see
Section~\ref{cmd:default_test_suite}), so \pconfigure\ writes it
down in \texttt{\$OBJDIR/check-stamp} alongside the directories.
Both come back from \texttt{make} or \texttt{make check} run in the
project \pconfigure\ ran in, should the object directory holding them
be deleted, saying what the configure wrote; until one of those runs,
\texttt{ptest} reports on \texttt{check} alone.

A report about one test suite is asked for with
\texttt{--check-suite \$name} and the results to report, one
\texttt{--check-result} each.  The set has to arrive that way: a
result on disk records the exit status of the test that left it and
nothing about why the test was run, so there is nothing in
\texttt{\$CHECKDIR} to pick a suite out by.  This is what
\texttt{make report-\$name} runs, and it is easier to type that.

\texttt{--check-named} asks for the same thing without a suite: the
results named with \texttt{--check-result} and no others, and
\texttt{No tests} when there are none.  It is what \texttt{make report}
runs, so that a result left behind by a test nobody configures any more
is not counted.  A bare \texttt{ptest} still reads every result in the
directories, since what it is asked is what is on disk.

A result is scored by the exit status of the test that left it: zero
is a pass, one is a failure, and anything else is counted as an error.
The exception is a test that announced a skip (see
Section~\ref{cmd:tests}).  A line beginning \texttt{SKIP:} anywhere in
what such a test printed makes its result a skip rather than a pass,
and the report says so on the line that names the test, with the
reason the test gave --- which was otherwise reachable only by
untarring the result by hand, and so was never read, since nobody
untars a result that is reporting success.

Skips are counted as \texttt{NSKIP}, reported beside \texttt{NPASS}:
they are not in \texttt{NPASS}, so the four counts still add up to
\texttt{NRUN}.  Under \texttt{--quiet}, which prints a line only for a
result somebody has to act on, the count alone is printed and only
when it is not zero --- so the quiet report of a run with nothing to
excuse is still an empty file.  \texttt{make check} prints that
report whether or not the run passed, so a green run with skips in it
still shows the count, and a clean one prints nothing.  A skip does
not change what the report exits with: that status still answers only whether anything failed.

Anywhere in the output rather than on the first line, because a test
that got half way through before finding out it could not finish has
still not run.  A line of its own rather than a substring, because a
test is free to mention the convention in passing --- the ones that
audit other tests' results do --- and reading that as a verdict would
be the same mistake pointing the other way.

See Section~\ref{cmd:tests} for the environment a test is run in.

Each result is scored one of three ways, off the exit status left in
\texttt{ptest\_\_return}: \texttt{0} is a \texttt{PASS}, \texttt{1} is
a \texttt{FAIL}, and everything else -- a missing binary, a result
\texttt{tar} can't read, a test killed by a signal -- is an
\texttt{EROR}.  The distinction those two failing categories draw is
between the test running and finding something wrong, which is what
\texttt{FAIL} is for, and the harness never getting a straight answer
out of the test at all, which is what \texttt{EROR} is for.  A test
that crashes could be either: a fuzzer that corrupts memory on
purpose and wants to know when it worked is firmly in \texttt{FAIL}
territory, while a test that aborts because its fixture didn't build
is firmly in \texttt{EROR}'s.  \texttt{ptest} can't tell those two
apart from the exit status alone, so it doesn't try, and a test that
knows which one it is can say so itself by catching what it expects
and turning that into an \texttt{exit 1} before \texttt{ptest} ever
sees a signal.

A test that fails by calling a libc \texttt{assert()}, though,
crashes with \texttt{SIGABRT} on every single failure rather than on
some subset of them -- and a project built that way would rather see
those in \texttt{NFAIL} than in \texttt{NEROR} by default.
\texttt{ABRT\_IS\_FAIL} (see Section~\ref{cmd:abrt_is_fail}) is the
opt-in for exactly that project.  By hand, \texttt{--abrt-is-fail}
scores every \texttt{SIGABRT} in the run as a \texttt{FAIL};
\texttt{--abrt-is-fail-dir DIR} is a \texttt{--check-dir} that does
it for \texttt{DIR}'s results alone, which is what the generated
\texttt{Makefile} uses, and what a tab and \texttt{abrt-is-fail}
after a directory in \texttt{\$OBJDIR/check-dirs} means to a bare
\texttt{ptest}.

\subsection{\texttt{pinclude} \label{prog:pinclude}}

A small command-line tools that exposes \texttt{libpinclude.so},
\pconfigure's C preprocessor dependency handler, to BASH scripts.
This probably isn't actually useful because both \texttt{clang} and
\texttt{GCC} provide a more robust form of this functionality: the
only reason \texttt{libpinclude.so} exists in the first place is
because it's significantly faster than either of them.

\subsection{\texttt{ppkg-config} \label{prog:ppkg-config}}

A wrapper around \texttt{pkg-config} that adds the following
command-line options:

\begin{itemize}
\item \texttt{--optional}: returns success regardless of whether the
  given \texttt{pkg-config} invocation succeeds or fails, and keeps
  quiet about a failure.  Without it a package that isn't there is
  required: \texttt{pkg-config}'s explanation is passed through on
  stderr and \texttt{ppkg-config} exits with \texttt{pkg-config}'s
  status, which stops \pconfigure\ when it was run as a shell out in
  a \texttt{Configfile}.
\item \texttt{--have \$name}: adds \texttt{-DHAVE\_\$name} to the
  compile-time arguments if the given \texttt{pkg-config} invocation
  succeeds, otherwise does nothing.
\item \texttt{--ccmd \$command}: runs a different
  \texttt{pkg-config}-like command.  One example is
  \texttt{gpgme-config}.  You probably shouldn't be using this to run
  things like \texttt{gcc-config} or \texttt{llvm-config}, as their
  arguments are very different.
\end{itemize}

These two options combine to allow \texttt{pkg-config} to be
sufficient to do compile-time detection of features based on what is
currently installed on a system.  For example, the
\pconfigure\ \texttt{Configfile} uses the following snippit to decide
whether or not to use the system's talloc library or an internal
version based on which is availiable.

\begin{verbatim}
BINARIES    += pconfigure
COMPILEOPTS += `ppkg-config --optional --have TALLOC talloc --cflags`
LINKOPTS    += `ppkg-config --optional --have TALLOC talloc --libs`
SOURCES     += pconfigure/main.c
\end{verbatim}

\subsection{\texttt{pgcc-config} \label{prog:pgcc-config}}

This allows \texttt{Configfile}s to interrogate the installed C
compilers by version number in an attempt to mask flags that are not
supported on particular compilers.  It is meant to be run in a
backtick, like
\begin{verbatim}
COMPILEOPTS += `pgcc-config gcc 4.5 gt -Wno-trampolines`
\end{verbatim}
which prints the flag when \texttt{gcc -dumpversion} is newer than
4.5, and nothing otherwise; \texttt{lt} prints it when the compiler
is older.  Both are strict, so a compiler of exactly the named
version gets neither.  Versions are compared as numbers, the major
first and then the minor, so 4.9 is older than 5.1 and 4.10 is newer
than 4.9.  The patch level isn't compared: a 4.5.3 compiler is
exactly 4.5, and a version is written as \texttt{<major>.<minor>} or
a bare \texttt{<major>}, which is the same as \texttt{<major>.0}.
A version written any other way, or a compiler whose
\texttt{-dumpversion} isn't one, makes \texttt{pgcc-config} give up
with the reason on its standard error and nothing on its standard
output, which stops \pconfigure\ at the \texttt{Configfile} line.

\subsection{\texttt{pllvm-config} \label{prog:pllvm-config}}

A wrapper around \texttt{llvm-config} that does the same thing as
\texttt{ppkg-config}.

\subsection{\texttt{pbashc} \label{prog:pbashc}}

A bash ``compiler'', which really just does the following
\begin{itemize}
\item Allows \texttt{\#include} to be used from within BASH files.
  This is a way to avoid \texttt{source}ing BASH files, which can be a
  pain when you don't know where they'll end up installed.  Unlike the
  C preprocessor, which will take a directive with whitespace anywhere
  before or after the \texttt{\#}, this wants the directive written
  bare at the start of the line.  A \texttt{\#} is how BASH starts a
  comment, and a looser reading finds directives in prose.
  \pconfigure\ follows the same rule when it works out what a script
  depends on, so the files it writes down as dependencies are the ones
  that actually get pasted in.

  Every line is read as the line it is, which is how BASH reads it:
  a trailing backslash does not join it to the next one, and a
  \texttt{/*} or \texttt{//} is not a comment.  A glob like
  \texttt{ls dir/*}, a comment ending in a Windows path's backslash,
  or a heredoc line ending in one leaves the \texttt{\#include}s
  below it as they were.  \pconfigure\ reads a script the same way
  when it looks for its dependencies and, for a test written in BASH
  or Perl, its \texttt{\#pconfigure} lines (see
  Section~\ref{directive}); a test written in C or C++ is still read
  as C, so a directive inside one of its comments is commented out.

  Each file is pasted in at most once: an \texttt{\#include} of a
  file that is already in the output is skipped, so two helpers that
  include each other are fine, and each comes out once.  The script
  itself counts as in the output, so a helper that includes it back
  doesn't paste it a second time.  A file is the same file however
  its \texttt{\#include} spells it: \texttt{../common.bash} from a
  subdirectory, \texttt{./helper.bash}, or a path through a symbolic
  link all name what they lead to.  \pconfigure\
  doesn't keep the same list when it works out what a script depends
  on, or which headers a C or C++ source reads.  It only refuses to
  follow an \texttt{\#include} back into a file it is still in the
  middle of reading, which is enough to get it out of a cycle like
  that one, or of two headers guarded by \texttt{\#pragma once} that
  include each other.  A file reached again some other way is read
  again, since a header with no guard can include something different
  the second time; for a script that can mean a dependency listed
  twice, but never one left out.
\item Reads the \texttt{-I} and \texttt{-D} in the target's
  \texttt{COMPILEOPTS}, with the argument either stuck on or as the
  next word.  A \texttt{-I} adds a directory an \texttt{\#include} is
  looked for in, after the including file's own; an absolute name is
  looked for at that path and in none of them.  A directory that
  shares the include's name is passed over rather than pasted in as
  nothing, and the search carries on; an include found nowhere stops
  \texttt{pbashc} with an error naming its line.  A \texttt{-D}
  defines a name for \texttt{\#ifdef} and \texttt{\#ifndef}, which
  decide which \texttt{\#include}s are pasted in --- every other line
  is a comment to BASH and goes out as it came in.
  \texttt{-DNAME=value} defines \texttt{NAME} just as
  \texttt{-DNAME} does, and also replaces \texttt{NAME} with
  \texttt{value} wherever it appears in the output, taking the
  occurrences left to right without overlap: under
  \texttt{-DXX=y}, \texttt{XXX} comes out as \texttt{yX}.  These two are
  the only flags it knows: a \texttt{-isystem}, say, is not a
  directory it searches.  \pconfigure\ reads the same flags the same
  way when it works out what a script depends on, so a file found
  only through a \texttt{-I}, or included only under a defined name,
  is one whose edits rebuild the script.
\item Refuses an \texttt{\#if}, naming the file and line.  Its
  expression is never worked out, so \texttt{\#ifdef} and
  \texttt{\#ifndef} are the only conditionals a script has: to switch
  an \texttt{\#include} off, put it under an \texttt{\#ifdef} of a
  name nothing defines.  This applies in a branch that isn't taken
  too, and \pconfigure\ refuses the same line when it works out what
  the script depends on, or reads a test written in bash for its
  \texttt{\#pconfigure} lines.  A comment that starts with the word
  is caught as well, and is written \texttt{\# if} instead.
\item Refuses a NUL byte, naming the file and line it is on, in the
  script or in anything it includes.  Every line is read as text, and
  a NUL would end the line early with the rest of it lost, so an
  archive appended to a self-extracting script can't be carried
  through \texttt{pbashc} as it is: keep the binary data in a file of
  its own for the script to read, or write it into the script
  encoded, with \texttt{base64} for instance.  The same goes for
  \texttt{pperlc}.
\item Leaves a heredoc's body alone.  The lines between a
  \texttt{<<EOF} and the \texttt{EOF} that ends it are text the script
  writes out rather than script, so a C file written that way keeps
  the \texttt{\#include} lines it was written with, and \pconfigure\
  does not count them among the files the script reads.  This holds
  in a branch that isn't taken as well, so an \texttt{\#if} or
  \texttt{\#endif} written into a heredoc there is text too, and
  doesn't close or refuse anything around it.  What gets
  recognized is the shape of a redirection and nothing more: a
  \texttt{<<<} is a here-string and carries its body on its own line,
  a \texttt{<<} with a word character written against its left is a
  shift rather than a redirection, and a \texttt{<<} inside quotes is
  text.  Quoting is followed within a line and not across lines.  A
  \texttt{<<} written right where the delimiter before it ended, as in
  \texttt{<<A<<B}, opens a second heredoc rather than shifting.

  The delimiter is read with its quoting taken out, wherever in the
  word that quoting is and whichever of bash's spellings it uses, so
  \texttt{<<'EOF'}, \texttt{<<\textbackslash EOF}, \texttt{<<E"O"F}
  and \texttt{<<\$'EOF'} are all ended by a line saying \texttt{EOF}.
  The backslash escapes in a \texttt{\$'...'} are decoded as bash
  decodes them, with \texttt{\textbackslash u} and
  \texttt{\textbackslash U} written out as UTF-8.

  A heredoc that no line ever ends has taken the rest of the file for
  its body.  If a directive went down with it \texttt{pbashc} says
  which one and stops, because that is a file which would otherwise
  have come out with an include silently missing from it; if the body
  was nothing but text then it was going to be treated as text either
  way, and nothing is said.
\item Sets the correct shebang at the beginning of the file.  The
  interpreter is always \texttt{pbashc}'s own, but if the script
  starts with a \texttt{\#!} line of its own, whatever options it
  gave are carried onto the new one and the script's line is
  replaced rather than left below it as a comment --- so
  \texttt{\#!/bin/bash -e} still stops at the first failure, and
  every line of the program is on the line it has in the source.  In
  \texttt{\#!/usr/bin/env bash} the word after \texttt{env} names
  the program rather than an option, so nothing is carried from it.
  \texttt{env -S} splits what follows into separate arguments, but
  the new line names \texttt{bash} directly and can pass it only one,
  so \texttt{\#!/usr/bin/env -S bash -e -u} has its flags run
  together as \texttt{-eu}.  Options that can't be folded that way,
  such as \texttt{-o pipefail}, are refused with the source's
  \texttt{\#!} line named; set those inside the script instead.
\item Marks the output as executable
\end{itemize}

It is run as
\begin{verbatim}
$ pbashc -i $input -o $output [-I dir]... [-D name]...
\end{verbatim}
where \texttt{-I} adds a directory to search for included files and
\texttt{-D} a definition, and each of them may be written either
glued to what it carries or as a word of its own, the same as the C
languages take them.  There is exactly one input: a second one, an
input that is a directory, or a flag with nothing after it is an
error rather than something to guess at, since each of those used to
come out as a script with the real program missing from it.

\subsection{\texttt{phc} \label{prog:phc}}

The header ``compiler'', which copies its input to its output and
nothing else:
\begin{verbatim}
$ phc -i $input -o $output
\end{verbatim}

It exists so that installing a header goes through a program that can
be replaced, the same way compiling a source file does --- see
\texttt{PHC} (Section~\ref{cmd:phc}) for replacing it.  A project
whose headers need generating rather than copying puts its own
program here.

\subsection{\texttt{pperlc} \label{prog:pperlc}}

The same as \texttt{pbashc}, but for Perl files.  The directives are
the same, and so is leaving a heredoc's body alone; what differs is
which lines are Perl's text rather than its code:
\begin{itemize}
\item A \texttt{<<\textasciitilde EOT} heredoc ends at an
  \texttt{EOT} line indented with any spaces and tabs, as it does in
  Perl.  To \texttt{pbashc} that spelling is still a heredoc that
  ends at \texttt{\textasciitilde EOT}, because that is what it means
  to the shell.
\item A \texttt{<<} opens a heredoc only where Perl would read one:
  with a word written right against it, as in \texttt{<<EOT}, or a
  quoted terminator with or without blanks before it, as in
  \texttt{<< "EOT"}.  So \texttt{1 << 4} and \texttt{\$x <<= 2} are
  shifts, and the lines after them are still script.  The shell takes
  a bare word after blanks as a terminator too, and \texttt{pbashc}
  still does.
\item Everything after a \texttt{\_\_DATA\_\_} or
  \texttt{\_\_END\_\_} line is data rather than script, so it goes
  out as it came in, \texttt{\#include} lines and all, and
  \pconfigure\ does not count those among the files the script reads.
  That holds to the end of the file the marker is written in: one in
  an included file does not stop the includes after it in the file
  that included it from being expanded.
\end{itemize}

\subsection{\texttt{pscalac} \label{prog:pscalac}}

When combined with \texttt{pscalald}, this makes Scala look like a
regular compiled language.  Specifically this wraps \texttt{scalac} in
a manner such that it produces a JAR archive, much like GCC produces
ELF objects.

\subsection{\texttt{pscalald} \label{prog:pscalald}}

When combined with \texttt{pscalac}, this makes Scala look like a
regular compiled language.  Specifically, this allows the ``linking''
together of multiple Scala JAR archives into an ``executable''.  Here
``linking'' means just merging the ZIP files, and ``executable'' means
a self-extracting archive that then runs the result of its extraction
(and then cleans up after itself).

\subsection{\texttt{pnasm} \label{prog:pnasm}}

A wrapper for NASM that makes it take a command-line argument syntax
that looks more like what GCC's assembler takes.  If you're looking to
make NASM a drop-in replacement for GAS in some build script, this may
be what you're after.

\subsection{\texttt{pwinegcc} \label{prog:pwinegcc}}

A wrapper for the Wine project's modified GCC-based toolchain that
makes it behave in a manner more similar to stock GCC.  If you're
looking to make \texttt{winegcc} a drop-in replacement for
\texttt{gcc}, then this may be what you're after.

\section{Odd Behavior (ie, WONTFIX bugs) \label{odd}}

\pconfigure\ has some odd behaviors.  This section attempts to list
all of those behaviors and provide ana explination for them.  I'd
consider them all bugs, but fixing most of them will require imposing
some sort of breakage on some \texttt{Configfile}s, which I try to
avoid.

\subsection{A path with a quote in it breaks the build
  \label{odd:quoting}}

Every path \pconfigure\ writes into a recipe --- the file a
\texttt{SOURCES} named, the directory a \texttt{SUBPROJECTS} named,
the object directory built out of them --- is written as a bare word.
A path holding a character the shell reads specially is therefore read
specially, and an apostrophe is the one that bites.  A project with
\begin{verbatim}
SUBPROJECTS += it's
\end{verbatim}
configures without a word of complaint and then dies at the first
recipe that names it with
\begin{verbatim}
/bin/bash: -c: line 0: unexpected EOF while looking for matching `''
\end{verbatim}
which names neither the path nor the \texttt{Configfile} line that
wrote it.  A \texttt{SOURCES += it's.c++} with no subproject anywhere
near it would fail the same way, so this is about the character rather
than about any one command --- which is why a quote in the name of a
target or a source is now refused when the line is read (see
Section~\ref{cmd:make-special}), and only the directories are left to
fail later.

The obvious repair --- wrap every path in a recipe in single quotes,
which is what \pconfigure\ already does to everything a
\texttt{CONFIGUREOPTS} hands a vendored tree --- is not enough, and
the reason is where the path comes from rather than what the quotes
would do.  A subproject's paths reach a recipe through a \texttt{make}
variable, \texttt{\$(pconfigure\_subdir\_\$name)}, because the same
\texttt{Makefile} has to work when \texttt{make} runs inside the
subproject and when it runs in whatever included it.  Quoting the
reference quotes nothing that is in the variable:
\texttt{'\$(pconfigure\_subdir\_it\_s)src/tool.c++'} expands to
\texttt{'it's/src/tool.c++'}, which is the same unbalanced quote one
step later.  Making the variable hold a shell-escaped path instead is
no better, because that same variable names \texttt{make}
prerequisites, and a prerequisite is a word of \texttt{make} rather
than a word of shell.

So a real fix is two spellings of every project's directory, one for
\texttt{make} and one for the shell, carried through every recipe that
every language and every build system writes, and through the rewrite
that puts those variables in ---
\texttt{makefile::path\_prefix::rewrite()}, which would have to know
which of the two it was substituting into.  That is a great deal more
change than the problem is worth, and none of it works half-done: a
tree where the C++ recipes quote and the link recipes don't fails in
exactly the same place for exactly the same reason.

One thing that is \emph{not} the obstacle, since it has been written
down as one: quoting a path does not defeat
\texttt{path\_prefix::rewrite()}.  That rewrite reads a quote as the
end of a word, so a path inside single quotes is still found and still
rewritten to its variable --- which is what a vendored build system's
\texttt{'BR2\_EXTERNAL=\$(abspath \$(pconfigure\_subdir\_sub)ext/)'}
relies on.  The barrier is the expansion described above.

The vendored build systems (Section~\ref{buildsys}) do quote the paths
they write, so the failure above comes out of the language backends
(Section~\ref{lang}) and out of what little of a vendored tree's
recipe is a path of this project's own.  That is a difference in how
far each got rather than a promise: a project whose directory has an
apostrophe in it does not build, whatever is in it.

The workaround is the one every build system in this family has: don't
put quotes, spaces or shell metacharacters in the names of the
directories and files a build reads.

\subsection{Can't link C and C++ into one binary}

Building a single binary that consists of both C code compiled by
\texttt{\$(CC)} and C++ code compiled by \texttt{\$(CXX)} is flaky and
has a tendency to break between \pconfigure\ releases with pretty much
no warning.

This exists because the C++ backend allows C code to be built (as some
projects name their C++ source files \texttt{*.c}).  What this means
is that the C++ backend can't determine what is a C++ file and what is
a C file by looking at the filename alone.

The accepted workaround is to just build your C code with the C++
compiler when you're trying to link it with other C++ code.  This is
probably the safest thing to do anyway, as it avoids a bunch of
trouble related to C++ name mangling (though you'll have to fix that
to build a C library anyway, so it's not a strong argument).  This
workaround has the unfortunate consequence of requiring that you write
C code that can compile with a C++ compiler, which isn't always easy.

\subsection{Old Scala classes stick around}

Sometimes old Scala class files end up in the build output.

When you build a Scala binary or library, \pconfigure\ can't actually
determine which class files will be created.  Thus, it links every
class file that's in the Scala compiler's output directory into the
final binary.  If you make a source code change that causes a class
file to go away, an old version of it will still be in the output
directory and will therefor get linked in.

The way to fix this is to ``\texttt{make distclean; pconfigure;
  make}'', which clears out the whole cache.  This isn't ideal, but
I'd need to write a proper Scala parser to make this bug go away.

Note that this is kind of a regression: I used to run \texttt{strace}
to figure out which files the Scala compiler touched, but because
\texttt{zinc} runs in a background daemon I can't use that trick.  I
decided it'd be better to have \texttt{scalac} and \texttt{zinc}
produce exactly the same results rather than have \texttt{zinc}
sometimes break.

\subsection{\texttt{DEPLIBS} triggers a full rebuild}

When you depend on a library that's internal to this project by using
\texttt{DEPLIBS}, every dependency of that library will be rebuilt
whenever \pconfigure\ is run.

This is triggered because \pconfigure\ uses the library's short name
(ie, \texttt{lib/libLIB.so} as a dependency of theh binary when you
add a \texttt{DEPLIBS} command.  These short names all depend on
\texttt{Makefile} because of how the compiler flags hanling works.

Fixing this shouldn't actually be difficult: I believe we could just
depend on the full library name instead of the short library name, but
the easiest way to implement this would be to make some Configfiles
re-entrant that otherwise wouldn't be which will start to break things
in tricky ways.  A better way would be to store the long library names
for later, but that would require that all \texttt{LIBRARIES} commands
come before their relevant \texttt{DEPLIBS} commands, which is
probably the sanest way to do it.

\subsection{\texttt{PREFIX} must be the first line \label{err::prefix}}

The \texttt{PREFIX} variable is refered to twice: once when the
linking step is generated (to set \texttt{-rpath}, for example) and
once when the \texttt{make install} target is generated.  It's really
best if \texttt{\$PREFIX} is the same at both times, otherwise
unexpected things may happen.

A subproject read above the \texttt{PREFIX} is a third place it's
referred to, and the one case of this that is caught: a \texttt{PREFIX}
that would install a program somewhere other than a library from a
subproject already read is an error, as described with
\texttt{PREFIX} itself.
